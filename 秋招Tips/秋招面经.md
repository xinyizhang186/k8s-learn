# 0. 高频面试答题框架

## Q0.1 项目拷打时应该怎么答？

**背诵版：**

我一般按“业务问题 → 为什么原方案不够 → 我的方案 → 关键技术决策 → 指标 → 失败案例和迭代”来讲。  
重点不是把模块全部念一遍，而是说明我为什么这样设计，以及如果重新做一次会改什么。

例如一个 RAG 项目，我不会只说“用了向量库、Embedding、LangChain”，而会重点回答：

1. 为什么需要 RAG，而不是直接让大模型回答；
2. 文档怎么切分、为什么这么切；
3. 召回失败主要来自哪里；
4. 为什么选某个 Embedding / Reranker；
5. 怎么评估召回和最终答案；
6. 线上或离线出现过什么 bad case，怎么修。

**项目追问的本质：** 面试官是在判断这个项目到底是不是你做的，以及你是否具备“定位问题 → 提出假设 → 做实验 → 看指标 → 迭代”的能力。

**背诵版：**

# 1. OneRec 与生成式推荐

## Q1.1 了解 OneRec 吗？它解决了什么问题？

**背诵版：**

OneRec 是快手提出的端到端生成式推荐框架。传统推荐一般是“召回 → 粗排 → 精排”的级联系统，每一层目标不同，而且前面召回错了后面无法恢复。

OneRec 的核心思想是把推荐改造成自回归生成问题：输入用户历史行为，模型直接生成一组可能感兴趣的视频 Semantic ID，从而尝试把 retrieve 和 rank 统一起来。

它有三个关键点：

1. **Encoder-Decoder + Sparse MoE**：Encoder 编码用户历史行为，Decoder 自回归生成视频 Semantic ID，同时用稀疏 MoE 扩大模型容量。
2. **Session-wise Generation**：不是一个一个预测 next item，而是直接建模一组推荐 session，使列表内部能够联合考虑兴趣、连贯性和多样性。
3. **Iterative Preference Alignment**：先训练 Reward Model 给生成 session 打分，再从同一用户的多个候选中构造 chosen / rejected 对，用 DPO 做偏好对齐，而且会迭代更新模型和偏好数据。

论文报告其在快手主场景上线后 watch-time 提升约 1.6%。

**来源：** OneRec, arXiv:2502.18965。

---

## Q1.2 OneRec 的训练流程是什么？

**背诵版：**

我把 OneRec 训练分成四步：

**第一步，Item Semantic Tokenization。**  
先得到视频的多模态表示，再用多层 residual quantization，把一个视频编码成多级 Semantic ID。OneRec 为了避免 codebook 分布很不均衡，使用 Balanced K-means 做量化。

**第二步，Session-wise NTP 训练。**  
输入用户历史行为序列，目标不是只预测下一个视频，而是生成一个高价值 session。训练目标本质还是 next-token prediction 的交叉熵，先得到 seed model。

**第三步，Reward Model。**  
因为推荐系统不像 NLP 偏好数据那样天然有 chosen/rejected 对，所以 OneRec 用用户行为数据训练 session-level Reward Model，预测 session watch time、view、follow、like 等多目标价值。

**第四步，Iterative Preference Alignment。**  
当前模型对一个用户生成多组候选 session，Reward Model 打分，最高分作为 chosen、最低分作为 rejected，然后联合优化 NTP loss 和 DPO loss。模型更新后再重新采样，形成迭代式偏好对齐。

一句话总结就是：

**Semantic ID → Session NTP → RM 打分 → DPO 偏好对齐 → 重新采样继续迭代。**

---

## Q1.3 OneRec 为什么要 Reward Model？

**背诵版：**

因为推荐系统的偏好反馈具有“曝光稀疏性”。同一次请求最终只展示一组推荐结果，现实里拿不到同一用户、同一时刻对多个候选 session 的真实对比反馈。

所以 OneRec 先用历史交互训练一个 Reward Model，近似估计“如果给这个用户展示这个 session，用户会有多喜欢”，再用 RM 给多个生成候选排序，构造 DPO 的正负样本。

本质上 RM 在这里承担的是**反事实候选的价值估计器**。

---

## Q1.4 OneRec 和传统召回排序最大的区别是什么？

**背诵版：**

传统推荐是多阶段 cascade，每层解决一个局部目标；OneRec 试图把候选生成和排序偏好放到一个统一生成模型里优化。

优点是目标更统一、模型容量可以 scaling，而且 session 可以联合建模列表内部依赖。  
缺点是工业实现难度更大，包括海量 item tokenization、约束解码、在线时延、候选覆盖率、模型更新以及偏好对齐的稳定性。

所以它不是“生成模型一定替代传统推荐”，而是把生成式推荐做到了更完整的工业闭环。

# 2. SFT、RLHF、RLVR、GRPO、DAPO、GSPO

## Q2.1 为什么做完 SFT 还需要 RL？

**背诵版：**

SFT 和 RL 解决的问题不同。

SFT 本质是**行为模仿**：给模型标准答案，让它最大化这些答案的 likelihood。它能快速建立指令遵循、格式和基本任务能力，但它只是在模仿训练集中的轨迹。

RL 是**目标优化**：模型自己 rollout，再根据 reward 直接优化策略。它可以探索训练集里没有显式给出的解法，而且能直接针对“答案是否正确、工具调用是否成功、业务指标是否提升”等目标优化。

所以常见做法是：

**SFT 给一个稳定起点，RL 再把模型往真正目标上推。**

Qwen3 的后训练就是典型例子：长 CoT 冷启动 → 推理 RL → 思考/非思考融合 → 通用 RL。

---

## Q2.2 SFT 后的模型可以直接做 CPT 吗？

**背诵版：**

技术上当然可以，因为 CPT 本质还是 next-token pretraining，没有架构限制。

但是工程上通常更推荐：

**Base → CPT / Domain Pretraining → SFT → Preference / RL**

原因是如果 SFT 后再大量做无监督 CPT，模型可能把已经学到的 instruction-following 和 alignment 能力冲掉，也就是 catastrophic forgetting。

如果业务上必须在 SFT 后补充大量领域知识，我会：

1. 用较小学习率；
2. 混入一部分通用数据；
3. 控制训练步数；
4. CPT 后重新做一轮 SFT / alignment；
5. 同时监控领域能力和通用指令能力，避免只看领域 loss。

所以答案不是“不能”，而是“可以，但通常需要重新对齐”。

---

## Q2.3 RLVR 是什么？

**背诵版：**

RLVR 是 Reinforcement Learning with Verifiable Rewards。

它的特点是 reward 可以被客观验证，比如：

- 数学题最终答案是否正确；
- 代码是否通过测试用例；
- SQL 是否执行正确；
- JSON / XML 是否符合格式；
- Agent 是否真正完成目标动作。

这种 reward 不需要训练神经 Reward Model，通常更稳定、便宜，也更不容易出现 judge 偏差。

DeepSeek-R1 在数学、代码和逻辑推理任务中大量使用的就是规则型 accuracy reward 和 format reward。

---

## Q2.4 RLVR 中 reward 信号应该怎么设计？

**背诵版：**

我设计 reward 时会遵循三个原则：

**第一，能客观验证的尽量客观验证。**  
例如代码用单测，数学用答案 checker，结构化输出用 parser，工具调用看真实执行结果。

**第二，reward 尽量接近最终目标，但不能过于稀疏。**  
只给最终 0/1 容易导致学习信号太弱，所以可以增加过程中的可验证子目标，但这些子目标必须和最终目标一致。

**第三，防 reward hacking。**  
不能让模型通过“输出更长”“固定格式”“投机取巧”获得高 reward。需要做 hold-out verifier、异常样本、对抗测试、长度约束和多指标校验。

工程上经常写成：

`R = R_task + λ1 R_format + λ2 R_process - λ3 R_cost - λ4 R_violation`

但重点不是公式，而是每一项都必须能解释它和真实业务目标的关系。

---

## Q2.5 开放式任务没有明确 0/1 Reward 怎么办？

**背诵版：**

我会先把开放式目标拆成“可验证部分”和“主观部分”。

例如客服回答质量可以拆成：

- 是否回答了问题；
- 是否引用了正确事实；
- 是否违反政策；
- 语言是否清晰；
- 用户偏好是否满足。

其中事实一致性、格式、工具执行等可以用 rule / verifier；主观质量再用 Reward Model 或 LLM-as-Judge。

也就是说开放式任务通常不是只能用 RM，而是采用：

**Rule Reward + Learned Reward + 业务约束的混合奖励。**

同时要定期用人工评测校准 judge，防止模型对 reward model 过优化。

---

## Q2.6 什么时候用 Reward Model，什么时候不用？

**背诵版：**

我的判断标准是：**目标能不能低成本、稳定、客观地验证。**

能验证就优先不用 Reward Model，例如：

- 数学答案；
- 编译和测试；
- SQL 执行；
- 工具调用成功；
- 格式约束。

因为规则 reward 更稳定、成本低、可解释。

当目标是主观偏好或者难以形式化，比如：

- 写作质量；
- helpfulness；
- 审美；
- 多目标推荐价值；
- 用户满意度；

才考虑 Reward Model / LLM judge。

实际工业系统一般是混合的，不是二选一。

---

## Q2.7 规则 Reward 做不了时，Reward Model 怎么训练？

**背诵版：**

经典做法是准备 preference pair：

`(prompt, chosen, rejected)`

Reward Model 对每个回答输出一个 scalar reward，然后用 Bradley-Terry 型 pairwise loss：

`L = -log σ(r_chosen - r_rejected)`

让 chosen 的 reward 高于 rejected。

如果业务本身有连续标签，比如观看时长、CTR、满意度，也可以做回归、多任务学习或分类。

训练 RM 时我会特别关注：

1. 数据是否覆盖 policy 真正会生成的分布；
2. hard negative 是否足够；
3. 人工标注一致性；
4. reward 是否和最终业务指标相关；
5. policy 更新后 RM 是否发生 distribution shift；
6. 是否出现 reward hacking。

---

## Q2.8 最终业务指标离模型输出很远，Reward 怎么设计？

**背诵版：**

这种情况不能简单把最终业务指标直接当唯一 reward，因为它通常**延迟大、噪声大、归因困难**。

我会采用分层 reward：

1. **近端 reward**：模型马上可控、可验证的行为，比如答案正确率、工具调用成功率、推荐相关性；
2. **中间代理指标**：例如点击、完播、session quality；
3. **远端业务指标**：留存、GMV、长期时长，主要用于校准和在线实验。

训练阶段优化更稳定的近端 / 中间 reward，最终用在线 A/B 判断它是否真的推动远端业务指标。

如果代理指标提高但远端指标下降，说明 reward specification 有问题，要重新做目标分解，而不是继续加大 RL。

---

## Q2.9 GRPO 的核心是什么？

**背诵版：**

GRPO 可以理解成 PPO 的一个变体，它不训练额外的 value model。

对同一个 prompt 采样一组回答，每个回答得到 reward，然后用组内均值和标准差做标准化：

`A_i = (r_i - mean(r)) / std(r)`

这样直接得到相对 advantage，再配合 PPO-style clipping 更新策略。

它最大的工程价值是省掉 critic/value network，特别适合大模型推理 RL。

**来源：** DeepSeekMath, arXiv:2402.03300。

---

## Q2.10 DAPO 相比 GRPO 改了什么？

**背诵版：**

DAPO 是 ByteDance Seed 和清华 AIR 提出的，对 GRPO 做了四个关键工程改进：

1. **Clip-Higher**  
   把 PPO/GRPO 的对称 clipping 改成非对称，上界放得更宽，避免正向高优势 token 太早被 clip，提升 exploration，缓解 entropy collapse。

2. **Dynamic Sampling**  
   如果一个 prompt 的整组回答全对或全错，组内 advantage 基本没有有效区分度，就重采样或过滤，保证 batch 里有有效梯度的样本。

3. **Token-level Policy Gradient Loss**  
   长 CoT 场景不再简单按 sequence 平均，而是从 token 粒度聚合 policy gradient，避免不同长度样本权重失真。

4. **Overlong Reward Shaping**  
   对超过最大长度、被截断的答案做更平滑的惩罚，减少“突然 0 分”带来的 reward noise。

一句话：

**DAPO 主要解决 GRPO 的 entropy collapse、无效样本、长序列 loss bias 和超长回答噪声。**

DAPO 论文发表于 NeurIPS 2025。

---

## Q2.11 GSPO 相比 GRPO 改了什么？

**背诵版：**

GSPO 最大的变化是把 policy optimization 的重要性比率从 **token level 改成 sequence level**。

GRPO/PPO 通常对每个 token 计算 importance ratio。如果 rollout 使用的推理引擎和训练引擎数值不完全一致，或者 MoE 路由发生变化，token-level ratio 会非常敏感，长训练时容易不稳定。

GSPO 用整个 sequence 的 likelihood 构造 sequence-level importance ratio，并在 sequence 层面 clipping 和优化。

因此它的核心目标是：

**降低 token-level likelihood noise，提升大规模 RL，特别是 MoE RL 的稳定性。**

---

## Q2.12 DAPO 和 GSPO 怎么对比？

**背诵版：**

两者都从 GRPO 出发，但解决问题的方向不同。

- **DAPO：** 保留 token-level PPO/GRPO 框架，重点优化采样、clipping、长 CoT loss 和超长 reward；
- **GSPO：** 直接把 importance sampling 的核心单位从 token 提升到 sequence，重点解决训练稳定性和 MoE / 训推差异。

如果面试官问“谁更好”，不要直接下结论。  
我会说要看模型、RL infra 和任务。DAPO 是一组非常实用的 GRPO 改进；GSPO 则是在 objective 层面对 sequence-level optimization 做了更根本的调整。

**来源：** DAPO NeurIPS 2025；GSPO, arXiv:2507.18071 / Qwen Team。

---

## Q2.13 Reward Model 最大风险是什么？

**背诵版：**

最大风险是 **reward hacking / reward over-optimization**。

Reward Model 只是人类目标的 proxy。policy 越强、优化越久，越可能找到 RM 的漏洞，出现：

- 形式看起来很好但事实错误；
- 靠 verbosity 获高分；
- 迎合 judge；
- 使用 RM 未覆盖的 OOD 模式。

所以工业上不能只看训练 reward，必须有独立人工集、独立 verifier、hold-out judge 和真实业务指标。

DeepSeek-R1 也明确提到，在可验证推理任务中优先使用规则 reward，原因之一就是神经 RM 在大规模 RL 中容易出现 reward hacking。

# 3. Qwen3 训练流程、推理模式、MoE

## Q3.1 Qwen3 的预训练流程是什么？

**背诵版：**

Qwen3 官方技术报告给出的预训练大约是 **36T tokens、119 种语言和方言**，分三阶段：

**S1 General Stage：**  
超过 30T tokens，sequence length 4K，重点学习通用语言能力和世界知识。

**S2 Knowledge-Intensive Stage：**  
增加 STEM、代码、推理等高价值数据，再训练约 5T tokens。

**S3 Long-Context Stage：**  
加入高质量长文本，把上下文训练长度扩展到 32K。

数据上不仅使用网页文本，还从 PDF 类文档抽取高质量文本，并使用 Qwen2.5、Qwen2.5-Math、Qwen2.5-Coder 合成大量数学、代码、教材和 QA 数据。

注意：**预训练三阶段和后训练四阶段不要混。**

---

## Q3.2 Qwen3 的后训练流程是什么？

**背诵版：**

Qwen3 后训练是四阶段：

1. **Long-CoT Cold Start**：用长思维链数据做监督微调，让模型先具备基本推理轨迹；
2. **Reasoning RL**：对数学、代码、逻辑等任务做大规模 RL，主要利用可验证奖励；
3. **Thinking Mode Fusion**：把长 CoT 数据和普通 instruction 数据混合，让一个模型同时支持 thinking 和 non-thinking；
4. **General RL**：在 instruction following、format、Agent 等 20 多类任务上继续 RL。

所以 Qwen3 的核心不是“只有一个 reasoning 模型”，而是把“深度思考”和“快速回答”融合到了一个 hybrid 模型里。

**来源：** Qwen3 Technical Report, arXiv:2505.09388；Qwen3 官方博客。

---

## Q3.3 high / low reasoning mode 是什么？

**背诵版：**

high / low 本质上是**推理时给模型多少 reasoning compute / thinking budget**，不是简单换一个 temperature。

- low：少思考，时延低、token 少、成本低；
- high：允许更长的内部推理，通常复杂任务质量更高，但时延和成本更高。

不同厂商接口不完全一样，有的叫 reasoning effort，有的叫 thinking budget。

需要注意：**是否进行内部推理**和**是否把完整思维链展示给用户**是两个不同问题。生产系统通常不应该依赖解析模型的隐藏 CoT。

---

## Q3.4 think token 怎么理解？

**背诵版：**

在一些开放推理模型中，训练数据会显式区分 reasoning 区域和 final answer，例如使用 `<think>...</think>` 这类特殊 token。

它的作用是让模型知道“这里是推理轨迹”和“这里是最终回答”。

但工程上我不会把 think token 当成真正的算法本身。真正的 reasoning 能力来自：

**预训练能力 + CoT 数据 + 推理 RL + inference-time compute scaling。**

标签只是组织和控制训练/输出的一种方式。

---

## Q3.5 思维链能力是怎么来的？

**背诵版：**

不是一个单独的“CoT 模块”，而是多阶段共同形成的。

1. 预训练先学到大量模式、知识和基本推断能力；
2. CoT SFT / distillation 把隐式能力组织成长推理轨迹；
3. RL 用正确性 reward 强化有效推理路径；
4. inference-time 给更多 thinking budget，让模型在一次回答中做更多搜索和自我修正。

DeepSeek-R1-Zero 说明即使没有 SFT，RL 也能直接激发明显的推理行为；但加入 cold-start SFT 后，通常可读性、格式和稳定性更好。

---

## Q3.6 如果你设计“思考 / 不思考”统一模型，训练数据怎么做？

**背诵版：**

我会做成一个 controllable hybrid model。

1. 数据同时包含 thinking 和 non-thinking 样本；
2. 用显式 mode token / chat template 告诉模型当前模式；
3. thinking 样本重点覆盖数学、代码、规划等复杂任务；
4. 简单 QA、闲聊、分类等加入大量 non-thinking 数据，避免模型任何问题都过度推理；
5. 再用 RL 同时优化正确率和 reasoning cost，例如对无必要的超长推理增加轻度 cost；
6. 分别评测两个模式，防止融合后互相干扰。

Qwen3 的 Thinking Mode Fusion 就是很好的参考。

---

## Q3.7 MoE 和稠密模型有什么区别？

**背诵版：**

Dense 模型每个 token 都经过同一组 FFN 参数。

MoE 则把 FFN 换成多个 Experts，再由 router 对每个 token 只选择 Top-K 个 expert。

所以 MoE 可以做到：

**总参数很多，但每个 token 的激活参数和计算量相对小。**

优点是参数容量和计算量解耦；缺点是 routing、负载均衡、跨卡通信、训练稳定性和部署复杂度都更高。

---

## Q3.8 MoE 一定比 Dense 效果好吗？

**背诵版：**

不一定。

在相同 FLOPs 下，MoE 往往可以获得更大的参数容量，因此 scaling 很有优势。  
但是它引入了 router 和 expert specialization，如果负载不均衡、专家塌缩、通信成本过高，实际效果和吞吐可能都不好。

所以应该比较的是：

**同等训练计算、推理成本、显存和 latency 下的 quality，而不是只比较 total parameters。**

---

## Q3.9 MoE 专家数量多少合适？

**背诵版：**

没有通用最优值，专家数是质量和系统成本共同决定的。

我会看四个指标：

1. total parameters 是否需要继续扩大；
2. 每 token active parameters 能否接受；
3. expert utilization / load balance；
4. all-to-all 通信是否成为瓶颈。

不同模型差异很大：

- Mixtral 8x7B：8 个专家，每 token 选 2 个；
- Qwen3 MoE：128 个专家，每 token 激活 8 个；
- Switch Transformer 则采用更极端的单专家路由。

所以“专家越多越好”是错误的，最终需要用模型质量 + routing balance + 通信吞吐一起选。

---

# 4. MHA / MQA / GQA / MLA

## Q4.1 MHA、MQA、GQA、MLA 的区别？

**背诵版：**

它们最大的区别主要在 **K/V 怎么存和共享**，核心目的是减少 autoregressive decoding 时的 KV Cache。

### MHA
每个 Query head 都有自己的 K 和 V head。

`n_q = n_kv`

优点是表达能力强，缺点是 KV Cache 最大。

### MQA
所有 Query heads 共享同一组 K/V。

`n_kv = 1`

KV Cache 最小、decode 很快，但压缩太激进时可能损失模型质量。

### GQA
多个 Query heads 分成若干组，每组共享一个 K/V head。

`1 < n_kv < n_q`

它是 MHA 和 MQA 的折中：KV Cache 明显下降，同时质量通常更接近 MHA。Qwen3 就使用 GQA。

### MLA
DeepSeek-V2 提出的 Multi-head Latent Attention。

它不是简单“少几个 KV heads”，而是先把 K/V 联合压缩到低维 latent，再通过投影恢复 attention 所需表示，并对 RoPE 相关部分做专门处理。

核心是：

**缓存低维 latent，而不是完整 K/V，因此能进一步压缩 KV Cache。**

---

## Q4.2 为什么推理时 KV Cache 很重要？

**背诵版：**

自回归生成第 t 个 token 时，前面 token 的 K/V 不需要重新算，所以通常缓存起来。

问题是 KV Cache 大小基本随：

`batch × sequence_length × layers × kv_heads × head_dim`

线性增长。

当 context 很长、batch 很大时，decode 往往不是算力不够，而是显存容量和 memory bandwidth 被 KV Cache 卡住。

所以 MQA、GQA、MLA 本质上都在解决 **KV Cache 和 decode bandwidth**。

---

# 5. RoPE、FlashAttention、Linear Attention、SWA、长上下文

## Q5.1 RoPE 原理是什么？

**背诵版：**

RoPE 的核心是：把 hidden dimension 两两分组，然后根据 token 位置，对 Q 和 K 的每一对维度做二维旋转。

位置 `m` 的向量旋转角度是：

`m * θ_i`

其中不同维度使用不同频率。

最关键的性质是：

`<R_m q, R_n k>`

可以写成只依赖相对位置 `m-n` 的形式。

所以 RoPE 用**绝对位置的旋转**，在 attention 点积里自然产生**相对位置信息**。

另外旋转不会改变向量范数，因此比较稳定。

---

## Q5.2 手写 RoPE 怎么写？

```python
import torch

def apply_rope(x, base=10000.0):
    # x: [seq_len, dim]，dim 必须为偶数
    seq_len, dim = x.shape

    pos = torch.arange(seq_len, device=x.device).float()
    inv_freq = 1.0 / (
        base ** (torch.arange(0, dim, 2, device=x.device).float() / dim)
    )

    theta = pos[:, None] * inv_freq[None, :]
    cos = torch.cos(theta)
    sin = torch.sin(theta)

    x_even = x[:, 0::2]
    x_odd = x[:, 1::2]

    out = torch.empty_like(x)
    out[:, 0::2] = x_even * cos - x_odd * sin
    out[:, 1::2] = x_even * sin + x_odd * cos

    return out
```

**面试解释：**

每两个维度看成二维向量 `(x_2i, x_2i+1)`，乘一个旋转矩阵：

`[[cosθ, -sinθ], [sinθ, cosθ]]`

Q 和 K 使用对应位置角度旋转，最后 attention 点积就包含相对位置信息。

---

## Q5.3 FlashAttention 原理是什么？

**背诵版：**

FlashAttention 不是 approximate attention，它算的仍然是**精确 softmax attention**。

它优化的是 GPU 内存 IO。

普通 attention 往往会显式 materialize `N×N` attention matrix，在 HBM 和 SRAM 之间反复读写，长序列时 memory IO 很重。

FlashAttention 把 Q/K/V 分 block 搬到片上 SRAM，用 tiling + online softmax 边算边归一化，不把完整 attention matrix 写回 HBM。

所以它的核心收益是：

- 大幅减少 HBM IO；
- attention matrix 不需要完整驻留显存；
- 显存复杂度显著降低；
- wall-clock 更快。

但必须注意：

**FlashAttention 的计算复杂度本质仍然是 O(N²)，它不是 Linear Attention。**

**来源：** FlashAttention, arXiv:2205.14135。

---

## Q5.4 Linear Attention 原理是什么？

**背诵版：**

标准 attention：

`softmax(QK^T)V`

因为要构造 `N×N` attention matrix，所以序列维度是 O(N²)。

Linear Attention 用 feature map 近似或重新定义 attention kernel：

`φ(Q) φ(K)^T V`

利用矩阵乘法结合律，可以先算：

`φ(K)^T V`

再乘 `φ(Q)`，从而避免构造 N×N 矩阵，使复杂度对 sequence length 近似线性。

代价是：

1. 往往不再是完全等价的 softmax attention；
2. 数值稳定性和表达能力需要额外设计；
3. 某些 kernel approximation 在真实 GPU 上不一定比高度优化的 FlashAttention 更快。

---

## Q5.5 SWA 原理是什么？

> 这里 SWA 指 Sliding Window Attention。

**背诵版：**

标准全局 attention 每个 token 看所有 token，复杂度 O(N²)。

Sliding Window Attention 只让每个 token 看前后一个固定窗口 `w`，复杂度变成 O(Nw)。

优点是长序列效率高；缺点是单层无法直接看到窗口之外的信息。

通过堆叠多层、增加 global token、dilated window，或者和全局 attention 混合，可以让信息逐步跨更远距离传播。

Longformer、Mistral 等工作都使用过这类思路。

---

## Q5.6 Linear Attention、SWA、FlashAttention 有什么区别？

**背诵版：**

我会从“有没有改变 attention 数学形式”区分。

- **FlashAttention：** 不改变 full softmax attention，只优化实现和 IO，仍是 O(N²)；
- **SWA：** 改变连接图，只算局部窗口，复杂度 O(Nw)；
- **Linear Attention：** 改写 / 近似 attention kernel，通过结合律把序列复杂度降到近似 O(N)。

所以 FlashAttention 更像“精确算法的系统优化”；SWA 和 Linear Attention 属于“改变计算结构”。

---

## Q5.7 什么技术能让模型处理长上下文？

**背诵版：**

长上下文不是只改一个 max length 就行，我会分四层看：

**1. Position Encoding**  
RoPE interpolation、YaRN、LongRoPE 等，让模型能够外推到更长位置。

**2. Attention 计算复杂度**  
FlashAttention 降低 IO；SWA / sparse attention 减少 attention pair；Linear Attention / state-space 模型改变复杂度。

**3. KV Cache**  
使用 GQA、MQA、MLA、KV quantization、paged KV 等降低 decode 显存。

**4. 数据和训练**  
必须用长文本做 continued pretraining / long-context finetuning，否则“能输入 128K”不代表“真的会用 128K”。

最后还要用 Needle-in-a-Haystack、RULER、LongBench 或业务长文档测试，避免只看最大 context window。

---

## Q5.8 Lost in the Middle 是什么？

**背诵版：**

Lost in the Middle 指模型虽然支持长 context，但关键信息放在上下文中间时，利用率会明显下降。

论文发现很多模型对“开头”和“结尾”的信息利用更好，而中间位置性能显著下降。

解决思路包括：

1. RAG，只把真正相关证据放进上下文；
2. query-aware rerank / compression；
3. 把最相关证据放在更容易被关注的位置；
4. 分层摘要和 parent-child retrieval；
5. long-context training；
6. 用专门的长上下文评测，而不是只测长度上限。

**来源：** Lost in the Middle, TACL 2024 / arXiv:2307.03172。

---

# 6. RAG 高频面试题

## Q6.1 RAG 召回一般看哪些指标？

**背诵版：**

RAG 要把 retrieval 和 generation 分开评估。

### Retrieval
最常用：

- **Recall@K**：相关文档有多少被 Top-K 找到；
- **HitRate@K**：Top-K 里有没有至少一个正确文档；
- **Precision@K**：Top-K 有多少是相关的；
- **MRR**：第一个正确结果排名是否靠前；
- **nDCG@K**：多个相关结果且相关程度不同的时候评估排序质量。

### Generation
常见：

- Faithfulness / Groundedness；
- Answer Relevancy；
- Factual Correctness；
- EM / F1；
- 人工评价。

RAGAS 里最经典的四个指标就是：

**Context Precision、Context Recall、Faithfulness、Answer Relevancy。**

---

## Q6.2 Recall@K 怎么理解？

**背诵版：**

假设一个问题一共有 4 个真正相关文档，Top-5 检索到了其中 3 个：

`Recall@5 = 3 / 4 = 0.75`

它重点回答：

**“应该找回来的证据，我找回了多少？”**

如果只有一个 gold document，也经常用 HitRate@K。

---

## Q6.3 RAG 的分块策略有哪些？

**背诵版：**

我一般分六类：

1. **Fixed-size chunk**：固定 token 数 + overlap，简单但容易切断语义；
2. **Recursive chunk**：先按章节、段落、句子逐级切；
3. **Semantic chunk**：根据 embedding / 语义突变点切；
4. **Structure-aware chunk**：利用标题、列表、代码块、表格结构；
5. **Parent-Child / Multi-granularity**：小 chunk 做召回，大 chunk 给模型；
6. **Modality-aware**：表格、图片、代码、PDF layout 单独处理。

实际项目里我不会只问“chunk size 多少”，而是通过 Recall@K、最终回答正确率和 token cost 一起调。

---

## Q6.4 怎么提高知识检索正确率？

**背诵版：**

我一般从“query、召回、排序、上下文”四层优化。

**Query：**
- query rewrite；
- multi-query；
- HyDE；
- 意图识别；
- metadata filter。

**Recall：**
- dense embedding；
- BM25；
- hybrid search；
- 多粒度索引。

**Ranking：**
- cross-encoder reranker；
- LLM reranker；
- MMR 去冗余。

**Context：**
- parent-child expansion；
- query-aware compression；
- 去重；
- 结构化拼接。

最后一定用 labeled query set 做 Recall@K / MRR / nDCG 和 end-to-end QA eval，不靠肉眼挑案例。

---

## Q6.5 怎么提升 RAG 最终回答正确率？

**背诵版：**

我会先定位到底是 retrieval 错还是 generation 错。

- Context Recall 低：检索没找到 → 改 embedding、query rewrite、hybrid search；
- Context Precision 低：召回噪声大 → rerank、metadata filter；
- Faithfulness 低：证据对但模型乱编 → prompt 强约束、引用、拒答；
- Answer Relevancy 低：模型答偏了 → prompt / query understanding；
- 上下文足够但 answer 仍错：考虑更强模型、结构化 reasoning 或 tool。

这比笼统说“换更大的模型”有效得多。

---

## Q6.6 知识库中的表格 / 图片怎么处理？

**背诵版：**

不能把 PDF 简单按纯文本抽取，否则表格行列关系和图片语义会丢失。

我的做法是：

**表格：**
1. layout-aware parser 找出表格；
2. 保留标题、行列名、单元格关系；
3. 转成 Markdown / HTML / row-based JSON；
4. 根据查询既可以检索整表，也可以检索行块；
5. 保留页码和表名 metadata。

**图片：**
1. OCR 提取文字；
2. VLM 生成 caption / structured description；
3. 保存原图位置和页面 metadata；
4. 必要时做 multimodal embedding；
5. 回答时把原图或结构化描述一起提供给多模态模型。

核心是：**不要把非文本信息强行压平成无结构字符串。**

---

## Q6.7 Prompt 层有哪些优化手段？

**背诵版：**

Prompt 优化不是“多写几句话”，我会系统化设计：

1. 明确 role 和 task；
2. 明确输入数据边界；
3. 把硬约束写成可检查规则；
4. 固定输出 schema；
5. 给高质量 few-shot；
6. 明确工具什么时候调用；
7. 明确证据不足时拒答；
8. 对长 prompt 做信息排序，避免关键约束 Lost in the Middle；
9. 建立 eval set，每次 Prompt 改动跑回归测试。

Prompt 必须和评测绑定，否则只是主观调参。

---

# 7. Agent、Skill、Harness、LangChain / LangGraph

## Q7.1 Agent 是什么？

**背诵版：**

我把 Agent 理解成：

**LLM + 状态 + 工具 + 决策循环 + 执行环境。**

普通 LLM 一次输入一次输出；Agent 会根据任务决定下一步动作，调用工具拿到 observation，再继续规划，直到完成任务或触发终止条件。

所以 Agent 的关键不是“能聊天”，而是**闭环执行**。

---

## Q7.2 ReAct 是什么？

**背诵版：**

ReAct 是 Reasoning + Acting。

核心循环是：

**Reason → Action → Observation → Reason → Action ...**

模型根据当前信息决定调用哪个工具，获得真实环境反馈之后再继续下一步。

它比纯 CoT 多了和外部世界交互的能力，比固定 workflow 又更灵活。

**来源：** ReAct, arXiv:2210.03629。

---

## Q7.3 ReAct 和 Plan-and-Execute 区别？

**背诵版：**

ReAct 是边想边做，每一步根据新 observation 再决定下一步。

Plan-and-Execute 是先生成一个相对完整的计划，再逐步执行，必要时 replan。

所以：

- 任务短、环境变化大：ReAct 更直接；
- 任务长、子任务多：Plan-and-Execute 更容易控制；
- 工业里经常混合：先粗规划，再在每个 step 内部 ReAct。

---

## Q7.4 LangChain 和 LangGraph 有什么区别？

**背诵版：**

LangChain 更偏上层 Agent / LLM 应用抽象，包括模型、工具、Retriever、Agent 等组件。

LangGraph 更偏底层 orchestration runtime，把复杂 Agent 表达成显式的有状态图，强调：

- state；
- node / edge；
- persistence；
- checkpoint；
- human-in-the-loop；
- durable execution。

简单 Agent 我会优先用高层框架；复杂长任务、分支、循环、恢复和人工审批明显时，我会考虑 LangGraph。

---

## Q7.5 Agent 项目一定要用 LangChain 吗？

**背诵版：**

不一定。

Agent 的本质是模型、工具和状态循环，完全可以自己实现。

是否用 LangChain 主要看它能不能减少工程成本：

- 模型 / tool abstraction；
- tracing；
- structured output；
- graph orchestration；
- memory / persistence；
- eval。

如果项目只有两三个固定工具，我反而倾向写轻量状态机，避免过度框架化。

---

## Q7.6 为什么现在会出现 Skill？

**背诵版：**

因为通用 Agent 的一个痛点是：每次都靠 prompt 临时告诉模型“这个任务怎么做”，知识不可复用、标准不一致。

Skill 把某类任务需要的：

- instructions；
- examples；
- scripts；
- reference files；
- templates；

封装成可发现、可复用的能力单元。

所以 Skill 的价值不是“多一个 prompt 文件”，而是：

**把人的 SOP 和工具能力产品化，让 Agent 在相关任务出现时自动加载。**

这对团队规范、重复流程和可维护性很重要。

---

## Q7.7 为什么现在会出现 harness 这个概念？

**背诵版：**

因为模型越来越强以后，系统瓶颈逐渐从“模型会不会回答”转移到：

- 有没有正确上下文；
- 能不能稳定调用工具；
- 状态怎么保存；
- 失败怎么恢复；
- sandbox 怎么隔离；
- 权限怎么控制；
- 长任务怎么 checkpoint；
- 怎么 tracing 和 eval。

所以业界常用一句话：

**Agent = Model + Harness。**

Harness 就是围绕模型的一整套执行脚手架，包括 context management、tool loop、memory、sandbox、retry、guardrail、observability 等。

---

## Q7.8 Skill 和 Harness 有什么区别？

**背诵版：**

Skill 是**“怎么完成某一类任务的可复用能力包”**。

Harness 是**“Agent 运行时周围的系统基础设施”**。

举例：

- code-review 的 SKILL.md：Skill；
- 文件系统、shell、sandbox、工具权限、状态、checkpoint、重试、trace：Harness。

一个 Agent Harness 可以动态加载多个 Skills。

---

## Q7.9 如何实现意图识别模块？

**背诵版：**

我一般用分层方案，而不是所有 query 都直接让大模型分类。

1. 对高确定性的关键词 / schema 用规则；
2. 中等规模意图可以用 embedding classifier / 小模型；
3. 复杂长尾再用 LLM structured output；
4. 输出不仅是 intent，还包括 confidence 和 slots；
5. 低置信度进入澄清流程；
6. 建 confusion matrix 看哪些 intent 最容易混淆。

如果 intent 最终只决定调用哪个工具，还可以直接把它设计成 constrained tool selection 问题。

---

## Q7.10 如何提升 Agent 工具调用正确率？

**背诵版：**

我会从五层做：

1. **Tool schema**：参数类型严格、字段少而清晰；
2. **Tool description**：明确什么时候该用、什么时候不能用；
3. **Tool selection**：工具太多时先路由 / candidate pruning；
4. **Validation**：调用前校验参数，调用后检查结果，不合法就 retry；
5. **Evaluation**：统计 tool selection accuracy、argument accuracy、execution success rate、task success rate。

如果只是不断调 prompt 而没有 tool-level eval，通常很难稳定。

---

## Q7.11 Agent 项目怎么上线部署？

**背诵版：**

我会把模型和 Agent runtime 分开考虑。

典型链路：

`API Gateway → Agent Service → Model / Tool Router → Tools / RAG / DB → State Store`

生产环境重点补齐：

- session / state persistence；
- timeout / retry；
- idempotency；
- tool 权限；
- sandbox；
- queue；
- rate limit；
- tracing；
- token / latency / cost 监控；
- offline eval + online metrics。

如果是长任务，还要 checkpoint 和 resume，避免一个 tool failure 让整个任务从头开始。

## Q7.12 如果 Agent 项目还没有正式上线，怎么回答？

**背诵版：**

不要包装成线上项目。

可以回答：

“这个项目目前完成的是工程验证和核心链路验证，还没有正式生产上线。我主要验证了工具调用、状态管理、部署配置和失败场景。没有上线的原因是 X，因此我把工作重点放在可复现的部署方案、测试和问题定位上。正式上线还需要补充监控、权限、容灾和线上流量评测。”

这种回答比虚构“已经上线”更可靠。

# 8. 原生多模态

## Q8.1 为什么多模态大模型开始强调原生多模态？

**背诵版：**

早期很多多模态模型是：

**预训练视觉 / 音频 Encoder + projector + LLM**

优点是模块化、数据效率高，但不同模态的能力很大程度上来自独立模块，跨模态交互和生成往往是后接的。

“原生多模态”更强调从训练阶段就把多种模态作为统一建模目标，进行更深的联合训练和端到端优化。

优势包括：

1. 跨模态表示更统一；
2. 能做更深的模态间交互；
3. 更适合 image-text-audio-video 混合序列；
4. 输入理解和输出生成可以统一优化；
5. 流式多模态交互更自然。

但“原生”不是严格等于“完全没有视觉 Encoder”。例如 Qwen2.5-Omni 仍有视觉 / 音频编码器，但整体是端到端多模态训练和推理。

所以我不会简单说“原生一定比拼接式好”，它是统一性和工程复杂度之间的另一种取舍。

# 9. AI Coding / Codex / Vibe Coding

## Q9.1 平时用什么 AI 编程工具？怎么回答比较好？

**背诵版：**

我不会只报工具名字，我会讲使用场景。

例如：

- 快速代码理解、解释 legacy code；
- 搜索调用链；
- 生成单元测试；
- 小范围重构；
- 修复 lint / type error；
- 根据 issue 生成 patch；
- 辅助 code review。

我会强调：**AI 生成代码必须经过测试、diff review 和人工检查，不会直接 merge。**

---

## Q9.2 AI Coding 为什么最近这么火？

**背诵版：**

因为能力从“代码补全”变成了“Agentic Software Engineering”。

现在 coding agent 不只是生成一个函数，而是可以：

- 读整个 repo；
- 搜索代码；
- 修改多个文件；
- 运行 shell；
- 执行测试；
- 根据测试失败继续修；
- 做长时间异步任务；
- 多 Agent 并行处理不同 issue。

所以提升最大的不只是单次生成质量，而是形成了**计划 → 修改 → 执行 → 反馈 → 再修改**的工程闭环。

---

## Q9.3 为什么 Codex 这类产品受关注？

**背诵版：**

我认为核心不是“代码模型突然会写更多语法”，而是三件事叠加：

1. 基础模型在 repo-level reasoning 和 tool use 上更强；
2. harness 提供 sandbox、文件系统、shell、测试和长任务执行环境；
3. 产品把异步任务、并行 agent、review / worktree 等工程流程整合起来。

因此 coding agent 的竞争已经从“谁能写出一个函数”，变成“谁能更可靠地完成真实软件工程任务”。

---

## Q9.4 国内外 AI Coding 的差距怎么看？

**背诵版：**

我不会用“国内落后一代”这种笼统结论。

我会拆成四层比较：

1. **Base coding model**：代码生成和推理；
2. **Repo understanding**：跨文件、跨模块理解；
3. **Harness**：sandbox、terminal、patch、test、retry、long-horizon；
4. **Product ecosystem**：IDE、GitHub / CI、权限、企业私有化、成本。

目前单模型能力差距在快速缩小，而实际使用体验越来越取决于 agent harness 和工程生态。

国外产品往往在端到端软件工程 workflow 上起步较早；国内工具在中文、本土模型、成本、私有化和国内研发工具链方面也有自己的优势。最后还是要用 SWE-bench 和企业内部真实任务集评估，不能只看营销榜单。

---

## Q9.5 AI 过度设计怎么办？

**背诵版：**

我会在 prompt 和 review 阶段明确最小改动原则：

- 不新增没有必要的抽象；
- 不擅自引入依赖；
- 不改 public API；
- 不做“顺手重构”；
- 改动必须围绕 acceptance criteria；
- diff 过大要拆 PR。

本质就是给 AI 加上 **YAGNI + minimal diff + measurable acceptance criteria**。

---

## Q9.6 AI 修改老代码应该怎么做？

**背诵版：**

第一步不是让 AI 直接改，而是先让它：

1. 读调用链；
2. 总结当前行为；
3. 找测试；
4. 明确兼容性约束；
5. 提出最小 patch plan。

然后补 characterization test，把老行为锁住，再做小 diff。

如果是高风险代码，还应该 feature flag / canary，而不是一次性替换。

---

## Q9.7 如何限制 AI 修改范围？

**背诵版：**

我会显式约束：

- 允许修改哪些文件；
- 禁止修改哪些目录；
- 是否允许加依赖；
- 是否允许改 schema / API；
- 最大改动范围；
- 必须通过哪些测试；
- 有歧义时先停止并询问。

同时在工具层做 filesystem permission / sandbox，不能只靠 prompt 约束。

---

## Q9.8 AI 生成代码之后如何验证？

**背诵版：**

顺序一般是：

1. format / lint；
2. type check；
3. unit test；
4. integration test；
5. regression test；
6. security / dependency scan；
7. benchmark，如果改动影响性能；
8. 最后人工看 diff。

特别是 AI 容易写出“看起来合理但边界错”的代码，所以测试必须覆盖异常输入和旧功能。

---

## Q9.9 如何避免 AI 破坏已有功能？

**背诵版：**

核心是 **regression protection**。

- 修改前跑 baseline tests；
- 老代码没有测试就先补 characterization tests；
- 每次只做小 patch；
- 对 public API、DB schema、配置单独检查；
- 用 feature flag / backward-compatible migration；
- 修改后跑全量回归。

不能只因为新功能测试通过就认为安全。

---

## Q9.10 AI Coding 的 Code Review 怎么做？

**背诵版：**

我不会只看代码风格，而是按风险检查：

1. correctness；
2. 边界条件；
3. exception handling；
4. 并发；
5. 数据一致性；
6. security；
7. performance；
8. backward compatibility；
9. test coverage。

AI 写的代码尤其要警惕“幻觉 API”“不存在的配置项”“silent error”和“为了通过测试硬编码”。

---

## Q9.11 怎么判断 AI 的架构建议是否合理？

**背诵版：**

我会让它接受五个问题：

1. 这个架构解决的核心约束是什么？
2. 最简单方案为什么不够？
3. failure mode 是什么？
4. latency / cost / consistency 的代价是什么？
5. 如果业务规模只有现在的十分之一，还需要这么复杂吗？

如果回答不了，大概率就是 over-engineering。

最终架构选择必须有 workload、SLA、数据规模和 benchmark 支撑，不是看图画得漂亮。

## Q9.12 你的 Vibe Coding 工作流是什么？

**背诵版：**

我更倾向叫 AI-assisted engineering，而不是完全 Vibe Coding。

我的流程是：

**Spec → AI 读代码 → Plan → 小范围修改 → 自动测试 → Diff Review → 人工确认 → Merge**

我允许 AI 提高开发速度，但需求定义、架构约束和最终验收必须由人负责。

# 10. 测试 / Agent 测试

## Q10.1 黑盒测试和白盒测试有什么区别？

**背诵版：**

**黑盒测试**不关心内部实现，只看输入输出是否符合需求。  
适合功能测试、接口测试、系统测试、用户验收。

常见工具：Postman、curl、Playwright / Selenium、JMeter / k6 / Locust、OWASP ZAP 等。

**白盒测试**关注内部逻辑和代码路径。  
典型是 unit test、branch coverage、static analysis、profiling。

常见工具：pytest / JUnit、coverage.py / JaCoCo、SonarQube、Sanitizer、Profiler。

面试时重点是先解释思想，工具只是例子。

---

## Q10.2 除了功能测试还有哪些测试？

**背诵版：**

主要是非功能测试：

- 性能：latency、throughput、QPS、FPS；
- 压力 / 容量；
- 稳定性 / soak test；
- 兼容性；
- 安全；
- 可用性；
- 容灾 / 恢复；
- 可扩展性；
- 安装升级；
- 玩家 / 用户体验。

生产系统往往真正难的是非功能性问题，不是“功能能不能跑通”。

---

## Q10.3 什么因素会影响 FPS？

**背诵版：**

FPS 是 CPU 和 GPU pipeline 共同决定的。

常见瓶颈：

**CPU：**
- 游戏逻辑；
- 物理；
- draw call；
- 脚本；
- 线程调度。

**GPU：**
- 分辨率；
- shader；
- polygon / geometry；
- overdraw；
- texture；
- ray tracing；
- 显存带宽。

还有：

- 内存；
- IO；
- VSync；
- 刷新率；
- thermal throttling；
- 后台进程。

不能只回答“模型精度”，因为 FPS 通常是整个渲染管线的结果。

## Q10.4 Agent / 自动化测试对游戏测试有什么价值？

**背诵版：**

我认为 Agent 的价值不是完全替代人工，而是把人工从重复测试里释放出来。

Agent 特别适合：

- 自动跑大量地图 / 关卡；
- 长时间压力和 soak test；
- 自动执行重复操作；
- 异常路径探索；
- 日志收集；
- 自动复现；
- 多配置组合测试。

而人工测试更适合：

- 操作手感；
- 画面主观质量；
- 游戏节奏；
- 情绪体验；
- 非预期玩法。

所以最佳方案是：

**Agent 扩大覆盖面，人工集中做主观体验和复杂判断。**

## Q10.5 Agent 应该怎么评测？

**背诵版：**

至少分四层：

1. **Tool level**
   - tool selection accuracy；
   - argument accuracy；
   - execution success。

2. **Trajectory level**
   - 是否走了合理路径；
   - 步数；
   - 是否重复调用；

3. **Task level**
   - task success rate；

4. **System level**
   - latency；

不能只用“最终回答看起来不错”评估 Agent。

# 11. 数据库 / 后端 / Web

## Q11.1 什么是数据库索引？

**背诵版：**

索引是为了减少查询扫描范围而维护的额外数据结构。

关系型数据库最常见的是 B+Tree 索引。  
没有索引可能需要全表扫描 O(N)；有合适索引后可以快速定位满足条件的数据。

代价是：

- 占磁盘；
- insert / update / delete 需要维护索引；
- 索引太多会降低写性能。

所以索引本质是**空间和写开销换查询速度**。

---

## Q11.2 什么字段应该建立索引？

**背诵版：**

我主要看查询模式，而不是单独看字段。

优先考虑：

- WHERE 高频过滤字段；
- JOIN key；
- ORDER BY / GROUP BY 高频字段；
- 高选择性字段；
- 唯一约束字段。

不适合盲目建索引的：

- 更新特别频繁；
- 低基数字段单独索引收益小；
- 大文本；
- 根本不参与查询。

联合索引必须根据真实 SQL 设计。

---

## Q11.3 最左匹配是什么？

**背诵版：**

假设有联合 B+Tree 索引：

`(a, b, c)`

索引按 a 排，再在相同 a 内按 b 排，再按 c 排。

因此查询一般可以有效利用：

- `a`
- `a,b`
- `a,b,c`

如果完全跳过最左边的 a，只查 b、c，通常无法利用这个联合索引的有序前缀。

所以叫最左前缀原则。

但现代数据库存在 skip scan 等优化，面试里讲的是 B+Tree 联合索引的基本原理，不要把“不能用”说得绝对。

---

## Q11.4 INNER / LEFT / RIGHT / FULL JOIN 区别？

**背诵版：**

- **INNER JOIN**：只保留左右两边匹配上的行；
- **LEFT JOIN**：左表全部保留，右表没匹配到补 NULL；
- **RIGHT JOIN**：右表全部保留；
- **FULL OUTER JOIN**：两边都全部保留，没匹配的另一边补 NULL。

记忆方法：

**INNER 求交集，LEFT 保左，RIGHT 保右，FULL 求并集式保留。**

---

## Q11.5 什么是分库分表？为什么需要？

**背诵版：**

当单库单表的数据量、QPS、存储或维护成本达到瓶颈时，可以把数据拆到多个库或表。

常见：

- vertical split：按业务模块拆；
- horizontal split：按 user_id / order_id hash 或 range 拆。

目的：

- 扩存储容量；
- 分散 QPS；
- 缩小单表索引；
- 降低单实例压力。

代价也很大：

- 跨分片 JOIN；
- 分布式事务；
- 全局 ID；
- pagination；
- resharding；
- hot key。

所以不是数据一多就应该分库分表。

---

## Q11.6 数据库事务是什么？

**背诵版：**

事务是一组操作作为一个逻辑单元执行，经典特性是 ACID：

- Atomicity：要么全成功，要么全失败；
- Consistency：事务前后满足业务约束；
- Isolation：并发事务之间隔离；
- Durability：提交后不会因为普通故障丢失。

面试继续追问时再讲隔离级别、MVCC、锁。

---

## Q11.7 数据库事务提交成功，但 MQ 消息发送失败怎么办？

**背诵版：**

这是典型的“数据库和消息系统双写一致性”问题。

我优先考虑 **Transactional Outbox / 本地消息表**：

1. 在同一个 DB transaction 里写业务数据和 outbox event；
2. transaction commit 后，由独立 relay / CDC 把 outbox 消息投递到 MQ；
3. 成功后标记已发送；
4. 消费端必须幂等。

这样不要求 DB 和 MQ 在一个分布式事务里，也能保证最终一致性。

如果基础设施支持，也可以用 MQ transactional message，但消费端仍然需要幂等。

---

## Q11.8 Cookie、Session、Token 有什么区别？

**背诵版：**

这三个不是同一个维度。

**Cookie** 是浏览器端保存并随 HTTP 请求发送的小数据容器。

**Session** 是一种会话状态机制，常见实现是：
浏览器 Cookie 保存 session_id，真实 session 数据存在服务端。

**Token** 是客户端持有的认证凭证，服务端根据 token 验证身份。Token 可以是 opaque token，也可以是 JWT。

所以：

- Cookie 是存储 / 传输机制；
- Session 是会话状态机制；
- Token 是认证凭证。

Token 完全可以放在 Cookie 里。

---

## Q11.9 GET 和 POST 区别？

**背诵版：**

HTTP 语义上：

- GET 用于获取资源，是 safe、幂等的；
- POST 用于提交数据或触发处理，协议语义上不保证幂等。

GET 更容易被缓存，参数常放 query string；POST body 可以承载复杂 payload。

但不要说“POST 比 GET 安全”，安全性主要取决于 HTTPS、鉴权和服务端实现。

---

## Q11.10 什么是幂等？

**背诵版：**

同一个操作执行一次和执行多次，对系统最终状态的效果相同，就是幂等。

例如用户创建订单时网络重试 3 次，不能创建 3 个订单。

后端常见做法：

- idempotency key；
- request_id；
- 数据库 UNIQUE constraint；
- 状态机；
- 分布式锁；
- 去重表。

最可靠的通常是“业务唯一键 + 数据库唯一约束”，不能只靠 Redis 锁。

---

## Q11.11 什么是幂等键？

**背诵版：**

幂等键是客户端或服务端为一次业务操作生成的唯一 ID。

例如：

`Idempotency-Key: 8d...`

服务端第一次收到时处理并保存结果；后续再收到相同 key，就直接返回第一次结果或者拒绝重复执行。

它解决的是网络重试、用户重复点击、消息重复消费等问题。

---

## Q11.12 前端如何防止重复提交？

**背诵版：**

前端可以：

- 点击后立即 disable；
- debounce / throttle；
- loading 状态；
- 提交成功前不允许再次点击；
- 生成 request id。

但前端只能改善体验，不能作为最终一致性保证。

---

## Q11.13 后端如何防止重复提交？

**背诵版：**

后端必须自己保证幂等：

1. 为请求生成 / 接收 idempotency key；
2. 数据库建立业务 UNIQUE constraint；
3. transaction 内检查和写入；
4. 重复请求返回第一次结果；
5. 消息消费者也按 event_id 去重。

即使前端已经禁按钮，后端也不能省。

---

## Q11.14 输入 URL 到页面展示经历了什么？

**背诵版：**

我按网络到浏览器渲染讲：

1. URL 解析；
2. DNS 解析域名；
3. 建立 TCP，HTTPS 还要 TLS handshake；
4. 浏览器发送 HTTP request；
5. CDN / 网关 / 服务端处理；
6. 返回 HTML；
7. 浏览器解析 HTML 构建 DOM；
8. 解析 CSS 构建 CSSOM；
9. DOM + CSSOM 得到 render tree；
10. layout；
11. paint；
12. composite；
13. JS 执行可能继续修改 DOM，触发 reflow / repaint。

---

# 12. 前端 / 并发 / 数据结构

## Q12.1 Vue3 ref 和 reactive 区别？

**背诵版：**

`ref` 可以包装基本类型，也可以包装对象；JavaScript 里通过 `.value` 访问。

`reactive` 主要用于对象，返回 Proxy，直接读写属性。

例如：

```js
const count = ref(0)
count.value++

const state = reactive({ count: 0 })
state.count++
```

使用上我更倾向：

- 基本类型优先 ref；
- 复杂对象可以 reactive；
- 需要整体替换对象时 ref 更自然。

还要注意 reactive 对象直接解构可能丢失响应式，需要 `toRefs` 等方式处理。

## Q12.2 进程、线程、协程区别？

**背诵版：**

**进程**是资源分配单位，有独立地址空间，隔离强，切换成本高。

**线程**是 CPU 调度执行单位，同进程线程共享地址空间，通信方便，但需要处理锁和数据竞争。

**协程**是用户态轻量任务，由 runtime / event loop 调度，切换成本低，适合大量 IO 并发。

一句话：

**进程隔离强，线程共享资源，协程轻量并发。**

## Q12.4 HashMap 原理是什么？

**背诵版：**

HashMap 本质是：

**hash → bucket → 处理 collision。**

先对 key 求 hash，然后根据容量映射到 bucket。

如果多个 key 落到同一 bucket，就需要链表、开放寻址或树结构解决冲突。

如果问 Java 8 HashMap：

- 底层是 array + linked list + red-black tree；
- resize 通常按 2 倍扩容；
- 默认 load factor 0.75；
- 链表达到一定长度且 table 足够大时会 treeify。

重点不是背常数，而是解释为什么 hash 能做到平均 O(1)，以及 collision / resize 为什么会让最坏情况变差。

# 13. 手撕算法

## Q13.1 如何判断 `()[]{}` 是否正确闭合？

**背诵版：**

典型栈。

遇到左括号压栈；遇到右括号，检查栈顶是不是对应左括号；不对应直接 false。最后栈为空才 true。

```python
def is_valid(s: str) -> bool:
    mp = {')': '(', ']': '[', '}': '{'}
    stack = []

    for ch in s:
        if ch in mp:
            if not stack or stack[-1] != mp[ch]:
                return False
            stack.pop()
        else:
            stack.append(ch)

    return not stack
```

时间 O(n)，空间 O(n)。

## Q13.2 除自身以外数组的乘积怎么做？

**背诵版：**

不能用除法时，用前缀积 + 后缀积。

先让 `ans[i]` 保存 i 左边所有数的乘积，再从右往左维护一个 suffix 乘上去。

```python
def product_except_self(nums):
    n = len(nums)
    ans = [1] * n

    prefix = 1
    for i in range(n):
        ans[i] = prefix
        prefix *= nums[i]

    suffix = 1
    for i in range(n - 1, -1, -1):
        ans[i] *= suffix
        suffix *= nums[i]

    return ans
```

时间 O(n)，额外空间 O(1)，不算返回数组。

## Q13.3 用梯度下降写 sqrt 怎么做？

**面试先说：**

严格来说这个问题没有数据集，所以更准确叫 Gradient Descent，不是真正 minibatch SGD。  
可以把 `sqrt(a)` 转成优化问题：

`min_x  1/2 (x² - a)²`

梯度：

`dL/dx = 2x(x²-a)`

```python
def sqrt_by_gd(a, lr=1e-3, eps=1e-8, max_iter=100000):
    if a < 0:
        raise ValueError("a must be non-negative")
    if a == 0:
        return 0.0

    x = 1.0  # 不能初始化为 0，否则梯度为 0

    for _ in range(max_iter):
        grad = 2 * x * (x * x - a)
        new_x = x - lr * grad

        if abs(new_x - x) < eps:
            return new_x

        x = new_x

    return x
```

**追问：为什么不用这个做生产 sqrt？**

因为 convergence 对学习率和输入尺度敏感。真正数值计算通常优先 Newton：

`x_{t+1} = 1/2 (x_t + a/x_t)`

收敛更快。

## Q13.4 四川麻将胡牌判断怎么设计？

**背诵版：**

如果面试只考标准牌型判断，我会用计数数组 + 回溯 / 记忆化。

把三门数字牌映射成 27 个计数。普通胡牌结构是：

**4 组面子 + 1 对将**

算法：

1. 总牌数必须满足 `n % 3 == 2`；
2. 枚举一个 count ≥ 2 的牌作为将，减 2；
3. 对剩余牌，从最小编号开始：
   - 如果 count ≥ 3，可以拿刻子；
   - 如果同花色连续三张都有，可以拿顺子；
4. 递归直到所有牌都消完；
5. 任意一个将方案成功就胡。

四川麻将具体规则可能还包括定缺、七对等，因此我会先确认题目规则。  
如果规定“定缺后才能胡”，还要额外检查手牌里不能存在缺门花色。

**优化：**

相同计数状态可以 memo，避免重复搜索。

# 14. 结合 RAG / Agent 项目的项目拷打模板

## Q14.1 用 1 分钟介绍一个 RAG 项目

**可直接背诵：**

我做过一个智能家电语音交互场景的 RAG 项目。这个场景的核心问题是用户表达非常口语化，比如“房间有点潮”，实际可能需要映射到“除湿模式”；直接让通用大模型回答容易出现泛化回答，甚至生成设备并不存在的功能。

我的工作主要分三部分：

第一是知识库构建。我按设备、功能、FAQ、场景做语义切片，并保留设备型号、功能类型、固件版本等 metadata。

第二是检索。我使用 dense embedding 做语义召回，并结合 rerank 提高长尾指令和模糊表达的命中率。

第三是生成约束。不同任务使用不同 prompt，要求模型严格根据设备知识回答，证据不足时不生成不存在的功能。

评估时我不会只看最终答案，而是把 retrieval 的 Recall@K 和 generation 的 faithfulness / answer correctness 分开看，通过 bad case 判断到底是知识没召回还是模型没有正确使用证据。

---

## Q14.2 为什么 RAG 项目选 bge-m3 这类 embedding？

**背诵版：**

我选择 embedding 不会只看公开榜单，而会看业务：

- 中文效果；
- 长文本支持；
- dense / sparse / multi-vector 能力；
- embedding 维度和检索成本；
- 领域数据上的 Recall@K。

bge-m3 的优势是多语言、长文本，以及支持 dense、sparse、multi-vector 的统一表示方式，所以适合作为 hybrid retrieval 的候选。

最终是否采用还是要在自己的 query-document 标注集上比较。

---

## Q14.3 RAG 项目最大的 bad case 怎么回答？

**背诵版模板：**

“我遇到最多的不是模型完全不会，而是 retrieval 拿到了语义相近但业务条件不匹配的文档，例如不同设备型号或固件版本的功能说明混在一起。

我后来把设备型号、功能类别、版本加入 metadata，先做结构化过滤，再做向量召回和 rerank。

这个优化的核心不是换更大模型，而是让检索空间先满足业务约束。之后我会分别看 metadata filter 前后的 Recall@K 和最终错误率。”

---

## Q14.4 如果问 Skill 项目为什么有价值？

**可直接背诵：**

Skill 的价值是把一个依赖人工经验的流程变成可复用、可验证的 Agent 工作流。

例如版本分析场景，人工需要反复查 Release Blog、CHANGELOG、源码和 KEP，容易遗漏，而且不同人整理口径不一致。

我把流程拆成固定的数据源获取、机器事实抽取、LLM 补写、质量校验和标准化交付。能脚本确定的事实不让 LLM 猜，只有自然语言解释交给模型。

这样做的重点不是“用了大模型”，而是通过 **deterministic pipeline + LLM** 提高可复现性。

## Q14.5 如果问 Agent / Skill 为什么没完全上线？

**可直接背诵：**

“我会区分功能验证和生产上线。这个项目完成了核心流程、配置和部署验证，但实际多机环境受底层运行条件限制，没有把它包装成已经生产上线。  
我的工作重点是把依赖条件、失败原因、可复现步骤和后续上线需要补齐的监控、容灾、权限控制整理清楚。  
我认为工程项目里，能准确说明为什么没有上线，以及缺什么才能上线，比直接说‘跑通了’更重要。”

# 15. 高频“为什么”题速记

## Q15.1 为什么 SFT 后还要 RL？
SFT 学 imitation，RL 直接优化 reward；SFT 给稳定起点，RL 探索和对齐最终目标。

## Q15.2 为什么需要 Skill？
把 prompt / SOP / scripts / references 封装成可复用能力，降低重复提示和执行差异。

## Q15.3 为什么需要 Harness？
模型本身不负责文件、工具、状态、权限、重试、sandbox、trace，这些决定 Agent 能否生产可用。

## Q15.4 为什么用 GQA？
相比 MHA 大幅减少 KV Cache，相比 MQA 保留更多 K/V heads，质量与速度折中好。

## Q15.5 为什么 FlashAttention 快？
减少 HBM ↔ SRAM 数据搬运，不 materialize 完整 N×N attention matrix。

## Q15.6 为什么 RAG 需要 reranker？
Embedding retrieval 擅长高召回但排序不一定精确，cross-encoder reranker 对 query-document 做更细粒度交互，提升 Top-K precision。

## Q15.7 为什么长 context 还需要 RAG？
context window 大不等于能可靠利用所有 token；长输入成本高且有 Lost in the Middle，RAG 可以主动筛掉无关信息。

## Q15.8 为什么 Agent 需要状态机 / LangGraph？
长任务有分支、循环、失败恢复和人工审批，显式 state 比纯 prompt loop 更可控。

# 18. 最后 10 分钟复习版

如果进面试前只有 10 分钟，至少记住下面这些：

**OneRec：** Semantic ID → session NTP → RM → iterative DPO。

**GRPO：** 同 prompt 多 rollout，组内 reward 标准化，不需要 critic。

**DAPO：** Clip-Higher + Dynamic Sampling + Token-level PG + Overlong Reward Shaping。

**GSPO：** sequence-level importance ratio / clipping，提升 RL 尤其 MoE 稳定性。

**SFT vs RL：** imitation vs optimize reward。

**RLVR：** 能客观 verifier 就尽量 rule reward；主观任务再 RM。

**Qwen3：**
- pretrain：General → Knowledge-intensive → Long-context；
- posttrain：Long-CoT SFT → reasoning RL → mode fusion → general RL。

**MHA → GQA → MQA：** KV heads 越来越少，cache 越来越小。

**MLA：** 低秩 latent 压缩 K/V cache。

**RoPE：** 对 Q/K 两两维度做位置相关旋转，相对位置自然进入点积。

**FlashAttention：** exact attention，tiling + online softmax，优化 IO，不改变 O(N²)。

**SWA：** 每个 token 只看局部窗口 O(Nw)。

**Linear Attention：** kernel + 结合律，避免 N×N attention matrix。

**RAG：** Recall@K / MRR / nDCG + Context Precision/Recall + Faithfulness。

**Agent：** Model + Tools + State + Loop。

**Skill：** 可复用任务 SOP / instructions / scripts。

**Harness：** context、tool loop、sandbox、memory、retry、trace、eval。

**AI Coding：** Spec → Plan → Small Diff → Test → Review。

**幂等：** 重复执行不改变最终结果；后端靠 idempotency key + unique constraint。

**事务已提交但消息失败：** Transactional Outbox + 消费端幂等。

**URL：** DNS → TCP/TLS → HTTP → DOM/CSSOM → layout → paint → composite。
