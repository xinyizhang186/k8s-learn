> 工程岗必考。LLM 应用和传统 Web 应用不同:成本高、延迟长、不稳定,工程化是分水岭。

## 题 1:LLM 应用高并发架构怎么设计? ⭐⭐⭐⭐⭐

### 【场景】
LLM 应用 QPS 100+,怎么扛?成本怎么控?延迟怎么降?

### 【答案要点】

**1. 整体架构**

```
[Client]
  ↓
[API Gateway / 负载均衡]  ← 限流(令牌桶)+ 鉴权 + 路由
  ↓
[业务服务]
  ├── Prompt 组装
  ├── [缓存层] Query 答案缓存 (Redis)
  ├── [模型路由] 简单→小模型 / 复杂→大模型
  ↓
[推理服务集群] vLLM / SGLang (多副本 + 负载均衡)
  ├── [Prefix Cache] 共享 system prompt
  ├── [连续 batching] 提吞吐
  └── [量化/TP] 降显存提速度
  ↓
[流式输出 SSE] → Client
```

**2. 关键优化点**

| 点 | 手段 |
|---|---|
| **限流** | 令牌桶(QPS + 并发数双限);按用户分级 |
| **缓存** | 答案缓存(语义去重 Query) + Embedding 缓存 + Prefix Cache |
| **模型路由** | 简单 → 小模型(便宜快);复杂 → 大模型 |
| **批处理** | 异步任务合并 batch(离线场景) |
| **流式** | SSE 流式输出,降首 token 体感 |
| **异步队列** | 非实时任务入队列(Kafka/RabbitMQ)异步处理 |
| **降级** | 超载 → 小模型 / 短输出 / 拒服务 / 排队 |

**3. 缓存层(重点)**
- **答案缓存**:相同 Query 答案缓存(Redis);用 Query Embedding 做语义去重(相似度 > 0.95 视为同 Query)
- **Prefix Cache**:同 system prompt 跨请求复用 KV Cache(vLLM/SGLang 支持)
- **Embedding 缓存**:相同文档 Embedding 不重算
- **TTL**:知识时效性决定(新闻 1h,知识库 24h)

**4. 模型路由**
- **简单分类问题** → 7B 小模型
- **复杂推理** → 70B / GPT-4
- **分类器**:用小模型或规则判断 Query 难度,路由到对应模型
- 节省成本 + 降低延迟(简单请求不占大模型)

**5. 容量规划**
- 单卡 A100 8B FP16:vLLM 连续 batch ~2000-4000 token/s
- QPS 100,平均输出 200 token:需 ~5-10 张 A100(看输入长度)
- 量化(INT4)省 2-4x 显存 → 提并发
- 弹性扩缩容:监控 QPS / 队列长度自动扩容

**6. 降级策略**
- L1(超载):排队 + 等待提示
- L2(严重超载):降配(短输出/换小模型)
- L3(故障):静态兜底答案 / 转人工 / 拒服务
- 监控:队列长度 / 显存 / P99 延迟 / 错误率

### 【加分追问】
- **Q: 答案缓存命中率怎么提?** A: ① 语义去重(Query Embedding 相似度)② 预热高频 Query ③ system prompt 变化部分抽离,只缓存答案主体 ④ TTL 别太短。
- **Q: 流式输出怎么实现?** A: SSE(Server-Sent Events)或 WebSocket;后端边生成边推 chunk;注意超时 / 断线重连 / 客户端取消。
- **Q: 怎么估算 LLM 应用成本?** A: 月均 QPS × 平均 token 数 × 模型单价;自部署算 GPU 折旧 + 电费;API 算 token 单价。监控每请求成本,异常告警。

## 题 2:LLM 应用成本怎么控? ⭐⭐⭐⭐⭐

### 【场景】
用 GPT-4 API,月成本 10 万,怎么降到 2 万?

### 【答案要点】

**1. 成本来源**
- API 调用:输入 + 输出 token 计费
- 自部署:GPU 折旧 + 运维 + 电费

**2. 优化手段(优先级排序)**

| 手段 | 节省 | 难度 |
|---|---|---|
| **缓存** | 50%+(高频场景) | 低 |
| **模型路由** | 30-50% | 中 |
| **小模型替代** | 50-80% | 中 |
| **Prompt 压缩** | 10-30% | 低 |
| **批处理** | 50% | 中 |
| **自部署开源** | 70-90% | 高 |

**3. 缓存(最有效)**
- 答案缓存:相同 Query 直接返,命中率 30-70%
- 语义去重:相似 Query(Embedding 余弦 > 0.95)用同答案
- Prefix Cache:同 system prompt,推理层 KV Cache 复用
- Embedding 缓存:文档 Embedding 别重算

**4. 模型路由**
- 简单 Query → 小模型(7B / GPT-4o-mini / Claude Haiku)
- 复杂 Query → 大模型(GPT-4 / Claude Sonnet)
- 路由器:小模型分类 / 规则(关键词/长度)
- 节省:60% 流量给小模型,成本降 50%+

**5. 小模型替代**
- 评估:用 GPT-4 跑评测集作基线,看 Qwen2.5-72B / DeepSeek-V3 / Llama-3-70B 能否达 90% 效果
- 自部署开源:Qwen2.5-72B INT4 单 A100 可跑,长期省 API 费
- 混合:简单用小模型,复杂用 API

**6. Prompt 压缩**
- 去冗余(精简 system prompt)
- 上下文裁剪(只送 Top 3 RAG,别贪多)
- 历史摘要(多轮压缩)
- 工具:LLMLingua(token 级压缩)

**7. 批处理**
- 非实时任务(夜间总结/批量分类)用 OpenAI Batch API(半价,24h 返)
- 自部署:夜间低峰填满 batch

**8. 监控**
- 每请求 token 数 + 成本埋点
- 按用户/接口/模型维度统计
- 异常告警(单用户成本飙升)
- 成本看板,周报

### 【加分追问】
- **Q: 模型路由怎么实现?** A: ① 规则(关键词/Query 长度)② 小模型分类(GPT-4o-mini 判难度)③ Embedding 分类器;路由准确率影响整体效果。
- **Q: 自部署开源真比 API 便宜吗?** A: 大流量(月均万级请求)是;小流量 API 更省(GPU 24h 闲置浪费)。算盈亏平衡点:GPU 月租 ÷ 单请求 API 成本。
- **Q: 缓存怎么处理时效性?** A: TTL(知识时效)+ 主动失效(知识库更新清缓存);用户敏感数据不入缓存。

## 题 3:监控埋点怎么做? ⭐�⭐⭐⭐

### 【场景】
LLM 应用上线后怎么监控?埋什么点?

### 【答案要点】

**1. 监控维度**

| 维度 | 指标 |
|---|---|
| **性能** | QPS / P50/P99 延迟 / TTFT / TPOT / 队列长度 |
| **资源** | GPU 利用率 / 显存 / KV Cache 命中率 |
| **业务** | 任务完成率 / 转人工率 / 点踩率 |
| **质量** | 输出合规率 / JSON 解析失败率 / 幻觉率 |
| **成本** | 每请求 token / 每用户成本 / 日总成本 |
| **稳定** | 错误率 / 重试率 / 超时率 / 限流率 |

**2. 关键指标埋点**

```python
# 每次请求埋点
{
    "request_id": "...",
    "user_id": "...",
    "model": "gpt-4o",
    "prompt_tokens": 1234,
    "completion_tokens": 567,
    "latency_ms": 2300,
    "ttft_ms": 800,        # 首 token 延迟
    "tpot_ms": 30,         # 每 token 延迟
    "cache_hit": false,
    "tokens_per_second": 246,
    "error": null,
    "cost_usd": 0.012,
    "user_feedback": "thumbs_up",  # 点赞/点踩
    "task_complete": true,         # 任务是否完成
    "tool_calls": 3,               # Agent 步数
    "timestamp": "..."
}
```

**3. 工具链**
- **指标**:Prometheus + Grafana(QPS/延迟/资源)
- **链路追踪**:LangSmith / Langfuse / Arize Phoenix(每步 trace)
- **日志**:ELK / Loki(请求/响应/错误)
- **告警**:异常率 / 成本飙升 / P99 飙升

**4. 质量监控(难)**
- 线上抽样送 LLM-as-Judge 打分
- 点踩率 / 转人工率作为质量代理指标
- 收集 bad case → 评估集 → 持续优化

**5. 实战经验**
- 把"请求→响应"全链路 trace(含 RAG/工具调用/多次 LLM 调用)
- trace ID 串联,便于排障
- 异常请求自动入 bad case 池
- 成本看板按用户/接口分维度统计

### 【加分追问】
- **Q: 怎么监控幻觉?** A: ① 线上抽样送 LLM-as-Judge 评忠实度 ② 用户点踩率 ③ 关键事实抽取校验 ④ 没有完美自动方案,人工 + 自动结合。
- **Q: LangSmith / Langfuse 怎么选?** A: LangSmith 是 LangChain 出品,集成深但闭源;Langfuse 开源可自部署,框架无关;按是否用 LangChain + 私有部署需求选。

## 题 4:模型灰度 / A/B 切换怎么设计? ⭐⭐⃞⭐

### 【场景】
换新模型(或新 Prompt),怎么安全上线?

### 【答案要点】

**1. 流程**
- 离线评估:golden set 跑新模型,指标不降才考虑
- 影子流量:新模型处理线上流量但不返回用户(只对比)
- 灰度:5% → 20% → 50% → 100%,逐步放量
- 监控:核心指标不降才继续,降了立即回滚

**2. 切换策略**

| 策略 | 做法 |
|---|---|
| **按用户分** | 随机 5% 用户用新版,体验一致 |
| **按请求分** | 随机 5% 请求(用户可能跨版本) |
| **按场景分** | 低风险场景先上(如客服闲聊) |
| **A/B 对比** | 50:50 对比业务指标 |

**3. 关键设计**
- 配置中心:模型/Prompt 版本可热切换(不发版)
- 双写:新旧模型同时跑(影子流量),对比质量
- 监控:核心业务指标 + 质量代理指标 + 成本
- 快速回滚:开关一键切回旧版

**4. 坑**
- 用户跨版本体验不一致(按用户分更稳)
- 新模型可能有"风格变化"导致用户感知跳变
- A/B 期间数据收集要分版本统计

### 【加分追问】
- **Q: 影子流量成本怎么控?** A: 只对低比例(5%)做影子;或只对低置信度样本影子;或离线用录制的真实 Query 重放,不占线上成本。
- **Q: 怎么对比两个模型质量?** A: ① 离线 golden set ② LLM-as-Judge 双盲比较 ③ 线上 A/B 业务指标 ④ 用户反馈(点踩率)。

## 题 5:多模型路由怎么设计? ⭐⭐⃞⭐

### 【场景】
有多个模型(本地 + API),怎么根据请求选模型?

### 【答案要点】

**1. 路由策略**

| 策略 | 做法 |
|---|---|
| **规则路由** | 关键词/长度/任务类型分流 |
| **分类器路由** | 小模型分类难度,路由到对应模型 |
| **成本优先** | 都用最便宜能搞定的模型 |
| **质量优先** | 都用最强模型 |
| **混合** | 简单小模型 + 复杂大模型 fallback |

**2. 实现**
- 路由器:小模型(GPT-4o-mini)或规则判断 Query 难度
- 简单("你好""天气")→ 小模型(7B / Haiku)
- 复杂(推理/代码/长文)→ 大模型(GPT-4 / 70B)
- 失败回退:小模型答不了 → 升级大模型

**3. 路由维度**
- 任务类型:闲聊/事实/推理/代码
- Query 长度:长输入用长上下文模型
- 实时性:实时用 API,非实时用自部署
- 成本:贵模型限流,便宜模型兜底

**4. 进阶**
- **学习路由**:用历史数据训练难度分类器
- **Mixture of Experts(MoE)**:模型内部路由(DeepSeek-V3 等)
- **多模型投票**:关键场景多模型投票

### 【加分追问】
- **Q: 路由错误怎么处理?** A: ① 小模型答错检测(置信度低)→ 升级大模型 ② 用户反馈(点踩)→ 重发大模型 ③ 路由器持续优化。
- **Q: 路由器本身成本怎么控?** A: 用最便宜模型(BERT 分类器 / GPT-4o-mini);规则路由零成本;路由器只在不确定时调用模型。

## 题 6:流式输出怎么实现? ⭐⭐⃞⭐

### 【场景】
用户提问后等几秒才出答案,体验差。怎么流式?

### 【答案要点】

**1. SSE(Server-Sent Events)**
- HTTP 长连接,服务端边生成边推
- 主流 LLM API 都支持(`stream: true`)
- 客户端 EventSource / fetch ReadableStream

**2. 实现**
```python
# 服务端
async def stream_generate(query):
    async for chunk in llm.stream(query):
        yield f"data: {json.dumps(chunk)}\n\n"

# 客户端
const eventSource = new EventSource("/chat?q=...");
eventSource.onmessage = (e) => { /* append chunk */ };
```

**3. 注意点**
- **超时**:LLM 慢,设长超时(分钟级);网关别提前断
- **断线重连**:客户端断网重连续生成(需 last-event-id)
- **取消**:用户取消要能中止生成(后端 abort)
- **错误**:中途出错怎么传(把 error 当 chunk 发)
- **代理**:中间代理(Nginx/CDN)要支持 SSE(buffer 关闭)

**4. 工程坑**
- nginx 默认缓冲,要 `proxy_buffering off`
- CDN 缓存破坏(流式不能缓存)
- 多副本负载均衡要支持长连接
- 客户端取消要传播到推理服务(避免浪费 token)

**5. WebSocket vs SSE**
- SSE:单向(服务端→客户端),简单,主流
- WebSocket:双向,适合交互(用户中途输入),复杂
- LLM 流式输出 SSE 足够

### 【加分追问】
- **Q: 流式输出降低延迟吗?** A: 不降总延迟,降"首字延迟"体感;用户看到字开始读,等感好。技术上总生成时间不变。
- **Q: 客户端取消怎么传播到推理?** A: 链路要支持取消信号传递:Client abort → 网关 → 业务服务 → 推理服务 abort;vLLM 支持请求取消(避免继续生成浪费 token)。

## 题 7:失败重试与幂等怎么设计? ⭐⭐⃞

### 【场景】
LLM API 经常失败(超时/限流/网络),怎么重试不重复扣费?

### 【答案要点】

**1. 重试策略**
- 指数退避:`1s, 2s, 4s, 8s`,加抖动(jitter)
- 最大次数:3-5 次
- 可重试错误:网络错误 / 429 限流 / 5xx 服务端错
- 不可重试:400 参数错 / 401 鉴权(重试无用)

**2. 幂等设计**
- 请求 ID:客户端生成唯一 ID,服务端去重
- LLM API 多数不支持原生幂等(同 ID 不同输出),靠业务层
- 业务幂等:记录"已处理"状态,重复请求返回上次结果

**3. 兜底**
- 重试耗尽 → 降级(小模型 / 缓存答案 / 默认回复 / 转人工)
- 熔断:连续失败超阈值 → 短路一段时间(防雪崩)
- 限流:自身限流保护后端(令牌桶)

**4. 异步重试**
- 非实时任务失败入队列,延迟重试
- 死信队列:多次失败入死信,人工处理

**5. 监控**
- 重试率:异常高 → 后端不稳
- 平均重试次数:评估重试策略有效性
- 熔断触发次数

### 【加分追问】
- **Q: LLM 输出非确定,怎么幂等?** A: LLM 本身不幂等(同输入可能不同输出);业务幂等 = 用 request_id 去重,重复请求返回上次结果(缓存),不让 LLM 重复执行。
- **Q: 429 限流怎么处理?** A: ① 退避重试(看 Retry-After header)② 降级到其他模型 / 自部署 ③ 限流前置(自身限流避免触发上游 429)。
