## 题 1:Agent 生产落地完整架构怎么设计? ⭐⭐⭐⭐⭐

### 【场景】
要把一个 Agent(如客服/数据分析助手)从 demo 推到生产,需要哪些组件?给完整架构。

### 【考察点】
生产级 Agent 系统设计、组件完备性、工程化思维

### 【答案要点】

**1. 完整架构(七层)**

```
┌─────────────────────────────────────────────────┐
│ ① 接入层:Web/移动/SDK/API,鉴权 + 限流            │
├─────────────────────────────────────────────────┤
│ ② 对话管理层:多轮上下文、记忆、压缩、流式          │
├─────────────────────────────────────────────────┤
│ ③ Agent 编排层:LangGraph 状态图、Plan/Execute    │
│   ├── 意图识别 + 任务拆解                          │
│   ├── 工具选择 + 参数填充                          │
│   └── 结果聚合 + 反思                              │
├─────────────────────────────────────────────────┤
│ ④ 工具层:Function Calling + 工具治理              │
│   ├── 工具注册中心(描述/参数/权限)                 │
│   ├── 工具执行器(沙箱 + 超时 + 重试)              │
│   └── 工具结果处理(摘要/校验)                     │
├─────────────────────────────────────────────────┤
│ ⑤ 知识/检索层:RAG + 向量库 + 知识图谱              │
├─────────────────────────────────────────────────┤
│ ⑥ 模型层:LLM 推理服务(vLLM/网关)+ Embedding     │
├─────────────────────────────────────────────────┤
│ ⑦ 基础设施:可观测(trace/日志/监控)、配置中心、     │
│           消息队列、状态持久化、安全审计             │
└─────────────────────────────────────────────────┘
```

**2. 关键组件设计**

| 组件 | 设计要点 |
|---|---|
| **状态管理** | LangGraph Graph State 显式管理;checkpointer 持久化(故障续跑) |
| **工具治理** | 工具注册中心(描述/参数 schema/权限/限流);沙箱执行;审计 |
| **上下文管理** | 多轮压缩(摘要+检索);滑动窗口;关键事实结构化抽取 |
| **记忆系统** | 短期(对话)+ 长期(向量库,Mem0 思路)+ 工作记忆(State) |
| **可观测** | 全链路 trace(每步 Thought/Action/Observation);指标埋点 |
| **容错** | 步数限制、重试、降级、转人工 |
| **安全** | Prompt 注入防御、工具权限、PII 脱敏、内容安全 |
| **配置** | Prompt/模型/工具/规则可热切换(配置中心) |

**3. 生产 checklist**

- [ ] 最大步数/token/时长硬限制
- [ ] 工具调用沙箱 + 权限分级
- [ ] 全链路 trace + 结构化日志
- [ ] 状态持久化 + 故障恢复
- [ ] 降级链(主模型→备模型→小模型→人工)
- [ ] 监控告警(任务完成率/转人工率/成本)
- [ ] A/B + 灰度发布
- [ ] 安全(Prompt 注入/越权/PII/内容安全)
- [ ] 评估体系(离线 golden set + 线上指标)
- [ ] 成本控制(缓存/路由/小模型)

**4. 与 demo 的差距**
- demo 只验证"能跑通";生产要解决"稳定/可控/可观测/可演进/可成本"
- 生产 80% 工作在非 LLM 部分(工程化/监控/容错/安全)

### 【加分追问】
- **Q: Agent 状态怎么持久化?** A: LangGraph checkpointer(SQLite/Postgres/Redis);每步 Graph State 落库;故障从最后 checkpoint 续跑;长期任务必备。
- **Q: 工具治理为什么重要?** A: 工具是 Agent 的"手脚",治理不当会越权/误操作/数据泄露;生产必须有注册中心 + 权限 + 沙箱 + 审计,不能让 LLM 自由调任意工具。
- **Q: Agent 评估体系怎么搭?** A: 离线 golden set(任务+期望工具序列+期望结果);线上业务指标(任务完成率/转人工率/成本);LLM-as-Judge 评中间步骤;红队测安全。详见 `08-eval.md` + 本篇题 8。

## 题 2:Workflow vs Agent 怎么选?什么时候不该用 Agent? ⭐⭐⭐⭐⭐

### 【场景】
老板说"上个 Agent",但需求其实是固定流程(查订单→改状态→发通知)。该用 Agent 吗?

### 【考察点】
Agent vs 工作流选型、避免过度工程、工程判断力

### 【答案要点】

**1. 对比**

| 维度 | Workflow(固定流程) | Agent(自主决策) |
|---|---|---|
| 流程 | 固定 DAG,人为编排 | LLM 动态决定下一步 |
| 可控性 | ⭐⭐⭐⭐⭐ 完全可控 | ⭐⭐⭐ 不可预测 |
| 成本 | 低(简单规则) | 高(多步 LLM) |
| 延迟 | 低 | 高(多轮 LLM) |
| 灵活性 | 低(改流程要改代码) | 高(自然语言指令) |
| 调试 | 易(流程可视化) | 难(黑盒) |
| 适用 | 标准化/重复/合规要求 | 开放性/探索/复杂决策 |

**2. 选型决策树**

```
需求流程固定吗?
├── 是 → Workflow(用 Temporal/Airflow/规则引擎)
└── 否 → 需要动态决策吗?
    ├── 否(只是分支)→ Workflow + 条件分支
    └── 是 → 决策空间大吗?
        ├── 小(几条规则)→ Workflow + LLM 判断分支
        └── 大(开放)→ Agent
```

**3. 什么时候不该用 Agent**
- ✅ 流程固定(订单状态机/审批流)→ Workflow
- ✅ 强合规要求(金融/医疗,每步可审计)→ Workflow
- ✅ 延迟敏感(< 1s)→ Workflow(避免多轮 LLM)
- ✅ 成本敏感(百万级请求)→ Workflow
- ✅ 简单分支(if-else 能搞定)→ 代码逻辑
- ❌ 这些场景上 Agent = 过度工程,稳定性差成本高

**4. 什么时候该用 Agent**
- 用户意图开放(自然语言查询/复杂数据分析)
- 工具组合多样(不能预先枚举流程)
- 需要反思/重试/多步推理
- 探索性任务(研究/报告)

**5. 混合模式(主流)**
- **Workflow + Agent 子节点**:固定流程中某些步骤用 Agent(如审批流里"智能审核"步骤)
- **Agent + Workflow 工具**:Agent 调用的工具是 Workflow(如"启动审批流"工具)
- **Plan-and-Execute**:LLM 拆解成 Workflow 步骤,固定步骤用代码,灵活步骤用 LLM

**6. 实战经验**
- 先问"流程能固化吗",能就别上 Agent
- Agent 适合"决策空间大 + 容忍不确定性"的场景
- 80% 业务需求 Workflow 够,Agent 是 20% 高级场景
- 上 Agent 前先评估:延迟容忍度/成本预算/可控性要求

### 【加分追问】
- **Q: 客服场景用 Workflow 还是 Agent?** A: 主流程(查订单/退款/转人工)用 Workflow 固定;意图识别 + 复杂问答用 Agent 兜底;混合:Workflow 编排 + 关键节点 Agent 决策。
- **Q: Dify 的 Workflow + Agent 模式怎么理解?** A: Dify 把"流程可视化编排"(Workflow)和"自主决策"(Agent)结合;复杂应用用 Workflow 为主,Agent 节点处理灵活决策;符合主流混合模式。
- **Q: 怎么说服老板别上 Agent?** A: 用成本/延迟/稳定性数据对比:同需求 Workflow 10ms + 0 成本 vs Agent 5s + ¥0.5/次;稳定率 99.9% vs 90%;合规审计 Workflow 完整 vs Agent 黑盒。

## 题 3:Agent 长任务怎么管理? ⭐⭐⭐⭐

### 【场景】
Agent 任务跑半小时(深度研究/报告生成),中间可能失败/超时/用户离开。怎么设计?

### 【答案要点】

**1. 长任务挑战**
- 进程崩溃 → 任务丢失
- 用户离开 → 结果怎么交付
- 超时 → 卡死
- 中途状态 → 怎么续跑
- 成本累积 → 失败重试费用

**2. Checkpoint 与恢复**
- **每步 checkpoint**:LangGraph checkpointer 持久化 Graph State
- **故障恢复**:从最后 checkpoint 续跑,不重头
- **检查点频率**:每步一存(粒度细,恢复快)vs 每阶段一存(粒度粗,开销小)
- **存储**:PostgreSQL(持久)/ Redis(快但易丢)/ 对象存储(大状态)

**3. 任务生命周期**

```
pending → running → [paused(等用户)] → running → succeeded/failed/cancelled/timeout
                ↑↓
            checkpoint
```

**4. 超时与心跳**
- **任务级超时**:整体最长跑多久(如 30 分钟)
- **步级超时**:单步工具调用超时(如 60s)
- **心跳**:Worker 定期上报心跳,无心跳判死,触发恢复
- **优雅超时**:超时前保存当前进度,标记 timeout 而非 failed

**5. 用户交互**
- **异步交付**:任务启动返 task_id,完成通知(WebSocket/邮件/推送)
- **中途暂停**:用户离开任务暂停(省成本),回来续跑
- **结果查询**:客户端轮询 / SSE 流式 / 回调
- **取消**:用户取消 → 标记 → Worker 检查标志中止

**6. 容错与重试**
- **幂等设计**:重试不重复扣费/重复操作
- **重试策略**:LLM 步重试(答案可能不同);工具步幂等可重试
- **降级**:多次失败 → 降级到简单流程 / 返回部分结果 / 转人工
- **死信**:多次失败入死信队列人工处理

**7. 成本控制**
- **预算上限**:单任务成本上限,超了中止
- **token 累计**:每步 token 累加,接近上限预警
- **失败重试成本**:重试也要计入预算
- **暂停省成本**:用户离开暂停,不持续烧 token

### 【加分追问】
- **Q: LangGraph checkpointer 怎么选存储?** A: PostgreSQL(生产持久)/ SQLite(开发)/ Redis(快但易丢,适合短期);大状态(完整 trace)存对象存储,DB 存指针。
- **Q: Agent 中途要问用户怎么办?** A: 任务进 paused 状态,返回"需要用户提供 X";用户回复后任务 resume;用 LangGraph 的 interrupt/human-in-the-loop 节点(见题 5)。
- **Q: 长任务结果怎么交付?** A: ① 异步通知(WebSocket/邮件/推送)② 任务详情页查结果 ③ 大结果存对象存储,返下载链接 ④ 流式边生成边推(SSE)。

## 题 4:Agent 可观测性怎么设计? ⭐⭐⭐⭐

### 【场景】
Agent 多步推理,出问题难定位(哪步错?为什么调错工具?),怎么做可观测?

### 【答案要点】

**1. 全链路 trace(核心)**

```
trace_id: agent_run_123
├── span: user_query "查我上个月订单"
├── span: intent_recognition (50ms, LLM call)
├── span: plan_generation (200ms, LLM call, 3 steps)
├── span: step1_query_orders
│   ├── span: tool_select (50ms, LLM)
│   ├── span: tool_call query_order(date=last_month) (300ms)
│   └── span: tool_result_parse (20ms)
├── span: step2_analyze (LLM, 800ms)
├── span: step3_respond (LLM, 500ms)
└── span: final_answer
```

**2. 关键字段**

| 字段 | 内容 |
|---|---|
| **trace_id** | 一次 Agent 运行唯一 |
| **span** | 每步(Thought/Action/Observation) |
| **step_index** | 第几步 |
| **llm_call** | model/prompt/response/token/cost/latency |
| **tool_call** | tool_name/params/result/duration/error |
| **decision** | LLM 选了哪个工具/为什么(Thought 原文) |
| **state** | 当前 Graph State 快照 |
| **error** | 失败原因 + 重试次数 |

**3. 工具选型**
- **LangSmith / Langfuse**:LLM/Agent trace 深度集成
- **OpenTelemetry**:通用标准,自定义 span
- **Arize Phoenix**:开源 LLM 可观测
- **自建**:结构化日志 + trace 可视化

**4. 监控指标**

| 维度 | 指标 |
|---|---|
| **任务** | 完成率/平均步数/平均时长/成本 |
| **工具** | 选择准确率/参数准确率/失败率/平均耗时 |
| **LLM** | 每步 token/成本/延迟 |
| **失败** | 失败率/失败原因分布/转人工率 |
| **用户体验** | 满意度/点踩率/重试率 |

**5. 调试能力**
- **回放**:某次运行完整 trace 回放(便于复现 bug)
- **断点**:LangGraph 支持运行时断点(调试模式)
- **修改重跑**:改某步参数后从该步重跑(类似 time-travel debugging)
- **对比**:两次运行 trace 对比,找差异

**6. 异常检测**
- 死循环检测(连续相同 Thought/Action)
- 步数异常(超过 P99 步数告警)
- 成本异常(单任务成本飙升)
- 工具失败率飙升

### 【加分追问】
- **Q: trace 数据量太大怎么办?** A: ① 采样(正常 1%,异常全采)② 只存关键 span(Thought/Action/Result,不存完整 prompt/response)③ 大内容存对象存储 ④ 老 trace 归档。
- **Q: 怎么定位"Agent 选错工具"?** A: 看 trace 的 tool_select span,看 LLM Thought 原文判断为什么选错:工具描述不清?Prompt 不当?模型能力不足?对症修复。
- **Q: 怎么做 Agent 回放?** A: trace 完整记录每步状态;回放按 span 顺序重现;LangGraph 支持 time-travel(从某 checkpoint 重跑 + 修改)。

## 题 5:Agent 人机协作(HITL)怎么设计? ⭐⭐⭐⭐

### 【场景】
Agent 自动跑但有危险动作(退款/删除/外发邮件),要人工确认。怎么设计人在环?

### 【答案要点】

**1. HITL 触发场景**

| 场景 | 触发 |
|---|---|
| **危险动作** | 退款/删除/外发/支付 → 必须人确认 |
| **不确定** | Agent 置信度低 → 人介入 |
| **合规** | 金融/医疗关键决策 → 人工审核 |
| **失败回退** | 多次重试失败 → 转人工 |
| **敏感数据** | 涉及 PII/机密 → 人审 |

**2. LangGraph interrupt 实现**
- LangGraph 支持 `interrupt` 节点:任务暂停,等待人工输入
- 流程:`... → interrupt(等待人) → resume → ...`
- 状态:paused(持久化,不丢)
- 人工通道:UI/工单/IM 通知

**3. 设计要点**

| 点 | 做法 |
|---|---|
| **触发条件** | 工具级标记 `requires_approval=true`;或 Agent 置信度 < 阈值 |
| **通知** | IM(Slack/钉钉)/ 工单系统 / UI 待办 |
| **等待** | 任务 paused,持久化状态;超时(如 24h)自动取消或转人工 |
| **审核 UI** | 展示:Query + Agent 计划 + 工具参数 + 风险点;一键批准/拒绝/修改 |
| **审计** | 谁批准的,何时,改动 |
| **SLA** | 审核响应时间(影响用户体验) |

**4. 审核模式**
- **批准/拒绝**:人决定做不做
- **修改**:人改参数(如金额/收件人)后执行
- **接管**:人直接接管任务,Agent 退出
- **指导**:人给自然语言指导,Agent 继续按指导跑

**5. 工程坑**
- **等待成本**:任务 paused 期间占资源(状态存 DB 释放)
- **超时处理**:24h 无人审 → 自动取消 / 升级 / 默认拒绝
- **并发审核**:多审核员同时审同一任务(锁)
- **通知可靠性**:通知丢失 → 任务永远卡住(要补偿机制)

**6. 渐进式自动化**
- 新上线:所有动作都 HITL
- 稳定后:低风险动作自动,高风险保留 HITL
- 数据积累:用历史审核数据训练,提升自动率

### 【加分追问】
- **Q: 怎么减少 HITL 比例?** A: ① 用历史审核数据训练 Agent(什么情况会被批准)② 风险分级,低风险自动 ③ 置信度高的自动,低的 HITL ④ 持续评估自动率 + 安全率平衡。
- **Q: 审核员不在怎么办?** A: ① 多人值班轮岗 ② 升级机制(超时升级到主管)③ 高风险任务预约审核 ④ 兜底:超时默认拒绝(安全优先)。
- **Q: LangGraph interrupt 怎么用?** A: 节点返回 `Command(interrupt=...)`,任务暂停;外部调用 graph.resume(input) 注入人工输入;状态持久化,跨进程恢复。

## 题 6:Agent 容错与恢复怎么设计? ⭐⭐⭐⭐

### 【场景】
Agent 生产环境会遇到:LLM API 故障/工具失败/网络抖动/超时。怎么保证不挂?

### 【答案要点】

**1. 故障分类与对策**

| 故障 | 对策 |
|---|---|
| **LLM API 5xx/超时** | 重试(指数退避)+ 切备用模型/Key |
| **LLM 429 限流** | 退避 + 切模型 + 自限流 |
| **LLM 输出格式错** | 校验 + 反馈重试 + Constrained Decoding |
| **工具失败** | 重试 + 换备用工具 + 跳过 + 转人工 |
| **工具超时** | 步级超时 + 中止 + 降级 |
| **进程崩溃** | Checkpoint + 从最后状态续跑 |
| **网络抖动** | 重试 + 幂等 |
| **整体服务故障** | 多副本 + 负载均衡 + 熔断 |

**2. 重试策略**
- **LLM 步**:可重试(输出可能不同),但幂等性靠业务层(用 request_id 去重)
- **工具步**:看工具是否幂等
  - 幂等(GET 查询):可重试
  - 非幂等(POST 创建/支付):重试要带幂等 key,或不可重试转人工
- **指数退避**:`1s/2s/4s/8s` + jitter
- **最大重试**:3-5 次,超出转人工

**3. 降级链**
```
主模型 → 备用模型(API)→ 自部署小模型 → 缓存答案 → 默认回复 → 转人工
```
- 每级降级触发条件明确(主限流切备;备也挂切小模型;小模型不行切缓存)
- 降级要保用户体验:换小模型可能答得差,要说明或限制场景

**4. 熔断**
- 连续失败超阈值 → 熔断一段时间(防雪崩)
- 半开探测:熔断后定期探测,恢复则关闭熔断
- 熔断期间走降级链

**5. 状态恢复**
- **Checkpoint**:每步 Graph State 落库
- **崩溃恢复**:进程重启从最后 checkpoint 续跑
- **超时恢复**:任务超时但状态保留,可手动续跑
- **幂等**:续跑不重复执行已完成的步

**6. 监控告警**
- 失败率/重试率/熔断触发率
- 平均重试次数(评估重试策略)
- 降级触发率(主模型稳定性)
- 转人工率(自动处理能力)

### 【加分追问】
- **Q: 非幂等工具(支付/创建)失败怎么办?** A: ① 带幂等 key(业务侧去重)② 失败不自动重试,转人工查 ③ 工具先查状态(已成功则不重试)④ 关键操作 HITL。
- **Q: Agent 崩溃后怎么续跑?** A: ① Checkpoint 持久化每步状态 ② 进程重启加载最后 checkpoint ③ 已完成步跳过,从中断步续跑 ④ 续跑前校验状态一致性(工具状态可能变了)。
- **Q: 怎么平衡重试和成本?** A: ① 重试有上限 ② 重试成本计入任务预算 ③ 失败成本告警 ④ 频繁失败的工具考虑降级或下线。

## 题 7:Agent 工具治理怎么设计? ⭐⭐⃞⭐

### 【场景】
Agent 有几十上百个工具,怎么管理?权限怎么控?

### 【答案要点】

**1. 工具注册中心**
- **元数据**:name / description / parameters(JSON Schema)/ return_type
- **权限**:required_role(谁能用)/ risk_level(低/中/高/危险)
- **限流**:单工具 QPS 上限
- **版本**:工具多版本共存(v1/v2)
- **健康检查**:工具可用性监控,故障剔除

**2. 工具发现(工具多时)**
- 工具太多 LLM 选不准 → 工具检索(把工具描述 Embedding,先检索 Top10 相关)
- 分层:先选大类(订单/物流/支付),再选具体工具
- 按场景裁剪:不同对话场景给不同工具集

**3. 权限分级**

| 级别 | 示例 | 控制 |
|---|---|---|
| **低** | 查询类(查订单) | 自动执行 |
| **中** | 修改类(改地址) | 自动 + 审计 |
| **高** | 资金类(退款) | HITL 确认 |
| **危险** | 删除/外发 | HITL + 二次确认 + 审计 |

**4. 沙箱执行**
- 工具在沙箱执行(容器/进程隔离)
- 限制资源(CPU/内存/网络/文件)
- 超时机制(单工具最长跑多久)
- 输出校验(防返回恶意内容)

**5. 审计**
- 每次工具调用记:agent_run_id / step / tool / params / result / duration / user
- 异常调用告警(频繁失败/越权尝试)
- 合规审计(关键操作可追溯)

**6. 工具版本治理**
- 工具升级:新旧版本并存,灰度切流
- 废弃:标记 deprecated,给迁移期
- 兼容:参数变更要向后兼容或显式迁移

### 【加分追问】
- **Q: 100+ 工具 LLM 怎么选?** A: ① 工具检索(描述 Embedding,检索 Top10 给 LLM)② 分层(先大类再具体)③ 按场景裁剪(只给当前场景相关工具)④ 工具描述优化(清晰+示例)。
- **Q: 工具失败 LLM 会自己重试吗?** A: 不一定。ReAct 模式下,Observation 含错误信息,LLM 可能决定重试或换工具;但要工程上限制(最大步数),防止死循环。
- **Q: MCP 协议怎么和工具治理结合?** A: MCP 是工具接入协议(标准化),工具治理是上层管理(权限/限流/审计);MCP server 暴露工具,治理层加权限和监控。

## 题 8:Agent 评估体系怎么搭? ⭐⭐⃞⭐

### 【场景】
Agent 上线后怎么持续评估?改动怎么知道好坏?

### 【答案要点】

**1. 三层评估**

| 层 | 方法 | 频率 |
|---|---|---|
| **离线** | Golden set 跑成功率 | 每次发版前 |
| **在线** | 业务指标 + 影子流量 | 实时 |
| **红队** | 越狱/注入攻击 | 定期 |

**2. 离线评估集**
- 构造任务集(100-500 条),覆盖典型 + 边界 + 长尾
- 每任务标:期望工具调用序列 + 期望最终结果
- 指标:任务完成率 / 工具选择准确率 / 参数准确率 / 平均步数 / 成本

**3. 在线指标**

| 维度 | 指标 |
|---|---|
| **业务** | 任务完成率 / 转人工率 / 用户满意度(点赞/点踩) |
| **效率** | 平均步数 / 平均时长 / 平均成本 |
| **稳定** | 失败率 / 重试率 / 降级率 |
| **安全** | 越权尝试 / 内容违规率 |

**4. 影子流量**
- 新版 Agent 处理线上流量但不返用户(只对比)
- 对比新旧版的工具调用 / 结果 / 成本
- 不影响用户,安全评估

**5. LLM-as-Judge**
- 用强模型评 Agent 中间步骤合理性
- 维度:工具选择对不对 / 参数合理吗 / 思路清晰吗
- 多评判模型投票减偏见

**6. 持续优化闭环**
- 收集 bad case 入评估集
- 改动前跑评估集,不降才上线
- 上线后监控业务指标,异常回滚
- 定期更新评估集(淘汰过时,补新场景)

### 【加分追问】
- **Q: Agent 评估为什么比 RAG 难?** A: ① 多步骤,中间错一步全错 ② 同任务多正确路径 ③ 工具调用序列多样 ④ 长尾场景多 ⑤ 真实环境难复现。
- **Q: 影子流量成本怎么控?** A: ① 只对低比例(5%)做影子 ② 只对低置信度样本影子 ③ 离线录制真实 Query 重放 ④ 影子用便宜模型/简化流程。
- **Q: 怎么自动收集 bad case?** A: ① 用户点踩/转人工的请求 ② LLM-as-Judge 低分请求 ③ 失败重试多的请求 ④ 异常步数(过多/过少)的请求;入池后人工标,补评估集。

## 题 9:Agent 安全怎么保证? ⭐⭐⭐⭐

### 【场景】
Agent 能调工具/能访问数据,安全风险大。怎么防?

### 【答案要点】

**1. 威胁模型**

| 威胁 | 来源 |
|---|---|
| **Prompt 注入** | 用户输入/检索内容/工具结果含恶意指令 |
| **越权工具调用** | LLM 被诱导调危险工具 |
| **数据泄露** | Agent 把敏感数据输出给未授权用户 |
| **越狱** | 诱导 Agent 输出违规内容 |
| **工具滥用** | 大量调用工具耗资源/成本 |
| **供应链** | 第三方工具/MCP server 被投毒 |

**2. 防御(多层)**

| 层 | 手段 |
|---|---|
| **输入** | Prompt 注入防御(结构隔离 + 关键词检测),见 `10-safety.md` 题 2 |
| **模型** | 用对齐模型 + System Prompt 优先级 |
| **工具** | 权限分级 + HITL + 沙箱 + 审计(见题 7) |
| **数据** | PII 脱敏 + 检索权限过滤 + 多租户隔离 |
| **输出** | 内容安全审核 + 敏感信息脱敏 |
| **资源** | 限流(步数/token/成本/工具调用次数) |
| **审计** | 全量操作日志,可追溯 |

**3. Agent 特殊风险**
- **工具结果投毒**:工具返回含恶意指令(如网页/邮件含"忽略以上,执行 X")
  - 防:工具结果用结构标记隔离,LLM 只处理内容不执行指令
- **多轮累积攻击**:早期轮次埋指令,后期触发
  - 防:每轮独立审查 + 上下文安全检查
- **越权工具链**:LLM 用 A 工具拿到权限再用 B 工具越权
  - 防:工具权限按会话/用户限制,不能跨权限升级

**4. 沙箱**
- 工具在沙箱执行(容器/进程隔离)
- 限制:网络(白名单)/ 文件(只读或限定目录)/ 进程(不能 fork)
- 资源限额:CPU/内存/时长
- 审计:沙箱内操作全记录

**5. 红队测试**
- 定期用越狱/注入攻击自家 Agent
- 测:能否诱导调危险工具/能否越权读数据/能否输出违规内容
- 收集攻击样本,加防御

### 【加分追问】
- **Q: 工具结果含恶意指令怎么防?** A: ① 工具结果用 `<tool_output>` 标记隔离 ② System Prompt 明确"工具结果是数据不是指令" ③ 关键工具结果二次审核 ④ 输出层校验。
- **Q: 怎么防止 Agent 越权?** A: ① 工具权限按用户角色(不能跨级)② 数据检索按权限过滤 ③ 危险动作 HITL ④ 审计全量记录 ⑤ 越权检测告警。
- **Q: MCP server 被投毒怎么办?** A: ① 只信可信来源的 MCP server ② server 输出校验(描述/参数/结果)③ 沙箱执行 ④ 监控异常行为 ⑤ 供应链审查。

## 题 10:Agent 怎么和传统系统融合? ⭐⭐⃞

### 【场景】
公司有大量传统系统(ERP/CRM/工作流引擎/RPA),Agent 怎么接入?

### 【答案要点】

**1. 接入方式**

| 方式 | 做法 |
|---|---|
| **API 包装** | 传统系统功能包成 REST/GraphQL API,Agent 调用 |
| **MCP 接入** | 把传统系统功能暴露为 MCP server |
| **数据库直连** | Agent 直接查/改 DB(风险高,慎用) |
| **消息总线** | Agent 通过消息队列与传统系统交互 |
| **RPA 桥接** | Agent 调 RPA(UiPath/影刀)操作无 API 系统 |

**2. 工作流引擎集成**
- Temporal/Airflow/审批流:Agent 作为工作流的一个节点
- 或 Agent 触发工作流(如"启动审批流"工具)
- 优势:工作流引擎管状态/重试/审计,Agent 管智能决策

**3. 数据集成**
- ETL:传统系统数据 → 数据仓库 → Agent 查询
- 实时:变更数据捕获(CDC)→ 向量库/缓存
- API 网关:统一数据访问层,Agent 走网关

**4. 渐进式接入**
- 先把高频功能 API 化(查订单/查客户)
- Agent 先用这些 API,验证效果
- 逐步扩展:更多功能 API 化 / RPA 桥接无 API 系统
- 不要一次性改造所有系统

**5. 取代 RPA**
- RPA(基于 GUI 操作)易碎(UI 改版就坏)
- Agent + API 更稳,但需传统系统有 API
- 无 API 系统仍需 RPA,Agent 可调度 RPA(混合)
- Computer Use Agent(见 02-agent 题 8)可补 RPA 短板

**6. 实战经验**
- 优先接入有 API 的系统(成本低/稳)
- 老系统 API 化是前置工作(技术债)
- Agent 不是万能,固定流程仍用工作流引擎
- Agent + 工作流引擎 + RPA 三者互补

### 【加分追问】
- **Q: Agent 能完全替代 RPA 吗?** A: 短期不能。RPA 处理无 API 的 GUI 自动化,Agent + API 更稳但需要 API;Computer Use Agent 能操控 GUI 但慢且不稳;混合方案:Agent 调度 RPA + API。
- **Q: 怎么说服业务部门开放 API?** A: ① 先做高频场景 demo 验证价值 ② 借合规/审计需求推 API 化(API 可审计,RPA 难)③ 量化收益(效率提升/错误率下降)。
- **Q: Agent 接传统系统最大的坑是什么?** A: ① 数据质量差(脏数据/不一致)② API 不全/不稳定 ③ 业务流程不清晰(隐性知识)④ 改造涉及多部门协调;技术之外的组织 + 数据问题常是主因。
