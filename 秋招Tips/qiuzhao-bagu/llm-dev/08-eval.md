## 题 1:大模型应用怎么评估? ⭐⭐⭐⭐

### 【场景】
做一个 RAG/Agent 应用,怎么知道效果好不好?没有标准答案的情况。

### 【答案要点】

**1. 评估难点**
- 输出开放性(同一问题多个正确答案)
- 主观性(回答好坏因人而异)
- 无单一指标(像准确率那样)

**2. 多层评估框架**

| 层 | 方法 | 指标 |
|---|---|---|
| **组件级** | 单独测检索/生成 | Recall@K、忠实度 |
| **端到端** | 任务完成率 | 业务指标 |
| **人工** | 抽检评分 | 满意度 |
| **A/B** | 线上对比 | 业务转化 |

**3. 自动评估**

| 方法 | 适用 | 备注 |
|---|---|---|
| **规则匹配** | 选择题/格式 | 简单,适用窄 |
| **LLM-as-Judge** | 开放问答 | 主流,有偏见 |
| **交叉验证** | 多 LLM 投票 | 减偏见 |
| **参考答案对比** | 有标准答案 | BLEU/ROUGE/BERTScore |
| **Embedding 相似度** | 答案相似 | 粗糙,作辅助 |

**4. LLM-as-Judge**
- 用强模型(GPT-4/Claude)当裁判,对输出打分
- 维度:准确性 / 相关性 / 流畅度 / 完整性 / 安全性
- Prompt 模板:给评分标准 + 示例
- 优点:自动化、可扩展
- 缺点:裁判模型有偏见/不能评比自己强的模型/成本高

**5. 人工评估**
- 双盲对比(A/B 两答案,人评哪个好)
- Likert 量表(1-5 分多维度)
- 适合最终验收 + 校准自动评估

**6. 持续评估**
- 构建 golden set(100-500 条人工标注)
- 每次改动跑 golden set,看回归
- 收集线上 bad case 补 golden set
- 评估也是产品,持续维护

### 【加分追问】
- **Q: LLM-as-Judge 可靠吗?** A: 对弱于自己的模型较可靠;评同级/更强模型有偏见;位置偏见(给两个答案,放前面的更易被选);用多裁判投票 + 位置轮换缓解。
- **Q: 怎么建 golden set?** A: ① 真实 Query 采样 ② 覆盖典型 + 边界 case ③ 人工标"好答案" ④ 定期更新(过时 case 淘汰,新 bad case 补)。
- **Q: 评估自动化怎么落地?** A: ① CI 跑 golden set ② LLM-as-judge 打分 ③ 阈值卡控 ④ 不通过 PR 不能合并。

## 题 2:RAG 怎么评估?RAGAS 是什么? ⭐⭐⃞⭐

### 【场景】
RAG 系统效果怎么量化?

### 【答案要点】

**1. RAGAS(RAG Assessment)框架**
- 开源 RAG 评估库,四指标:

| 指标 | 含义 | 测什么 |
|---|---|---|
| **Faithfulness(忠实度)** | 答案是否被上下文支持 | 幻觉 |
| **Answer Relevancy(答案相关度)** | 答案是否针对问题 | 跑题 |
| **Context Precision** | 召回的上下文有多少相关 | 检索精确率 |
| **Context Recall** | 应召回的是否都召回了 | 检索召回率 |

**2. 各指标计算**
- **Faithfulness**:把答案拆陈述句,逐句判断是否被上下文支持(NLI),得分=被支持句数/总句数
- **Answer Relevancy**:从答案反推出可能问题,与原 Query 算相似度
- **Context Precision/Recall**:需要标注"正确上下文",或用 LLM 判断召回块是否相关

**3. 评估流程**
```
Query → RAG → 答案 + 召回上下文
→ RAGAS 自动评估(LLM 当裁判)
→ 4 指标得分
```

**4. 实战**
- 构造评估集:100-500 条 Query + 期望答案 + 期望来源
- 改 RAG 任意环节(切分/Embedding/Rerank/Prompt)都跑 RAGAS
- 优化方向看指标:Faithfulness 低 → 减幻觉;Recall 低 → 改召回

**5. 其他评估**
- **TruLens**:类 RAGAS,多维度
- **DeepEval**:开源测试框架
- **LangSmith**:LangChain 系,trace + 评估

### 【加分追问】
- **Q: RAGAS 的 Faithfulness 怎么算?** A: LLM 把答案分解成原子陈述句;对每句用 LLM 判断"是否被上下文支持";得分 = 被支持句数 / 总句数。本质是 NLI(自然语言推理)。
- **Q: Context Recall 怎么测无标注数据?** A: 用 LLM 判断召回块是否"相关于回答 Query";或用强模型生成"应召回的内容",对比实际召回。

## 题 3:Agent 怎么评估? ⭐⭐⃞

### 【场景】
Agent 多步推理,怎么评估好不好?

### 【答案要点】

**1. 评估维度**

| 维度 | 指标 |
|---|---|
| **任务完成率** | 是否达成最终目标 |
| **工具选择准确率** | 选的工具对不对 |
| **参数准确率** | 工具参数对不对 |
| **效率** | 平均步数 / token 数 |
| **鲁棒性** | 工具失败后能否恢复 |
| **安全性** | 不越权 / 不危险动作 |

**2. 评估方法**

| 方法 | 做法 |
|---|---|
| **Golden Trajectory** | 人工标"应走的工具调用序列",对比实际 |
| **End-state Eval** | 只看最终结果对不对 |
| **LLM-as-Judge** | LLM 评中间步骤合理性 |
| **业务指标** | 线上任务完成率 / 转人工率 |

**3. benchmark**
- **AgentBench**:多任务 Agent 评估
- **ToolBench / API-Bank**:工具调用
- **GAIA**:通用 Assistant 评估
- **SWE-bench**:软件工程任务

**4. 实战**
- 离线:构造任务 + 标期望工具序列,跑成功率
- 在线:任务完成率 / 平均步数 / 用户干预率 / 成本
- 失败 case 分析:卡在哪步 / 工具错 / 参数错

### 【加分追问】
- **Q: Agent 评估为什么难?** A: ① 多步骤,中间错一步全错 ② 同一任务多种正确路径 ③ 长尾场景多 ④ 真实环境难复现。
- **Q: 怎么降低 Agent 评估成本?** A: ① 用模拟环境(沙箱)代替真实工具 ② LLM-as-judge 评中间步骤 ③ 聚焦核心场景,长尾灰度上线再评。

## 题 4:LLM-as-Judge 怎么用?有什么坑? ⭐⭐⃞

### 【场景】
用 GPT-4 当裁判评估模型输出,有什么注意点?

### 【答案要点】

**1. 用法**
- 给裁判模型:Query + 答案 + 评分标准
- 让其打分(1-5 / 0-10)+ 解释
- 多维度:准确性 / 相关性 / 流畅度 / 安全

**2. 常见偏见**

| 偏见 | 现象 | 缓解 |
|---|---|---|
| **自偏好** | 偏爱自己生成的答案 | 多裁判投票 |
| **位置偏见** | 倾向选第一个/最后一个 | 位置轮换 |
| **冗长偏见** | 偏向更长答案 | 评分标准明确"简洁" |
| **格式偏见** | 偏向格式整齐的 | 加格式约束 |
| **强度天花板** | 评不了比自己强的 | 用更强裁判 / 人工 |

**3. 改进**
- 多裁判投票(GPT-4 + Claude + Gemini)
- 位置随机化(A/B 顺序轮换)
- 给评分 rubric(详细标准 + 示例)
- 校准:用人工标注校准 LLM 评分
- 只对低置信度样本用人工复核

**4. 适合场景**
- ✅ 大规模自动初筛
- ✅ 评弱于裁判的模型
- ✅ A/B 对比(同裁判同标准)
- ❌ 评裁判自己(自偏好)
- ❌ 高主观 / 高风险场景(需人工)

### 【加分追问】
- **Q: LLM-as-Judge 成本怎么控?** A: ① 只评关键样本(线上低置信度) ② 用便宜模型先粗筛,GPT-4 复核 ③ 缓存评分(Query 相同复用)。
- **Q: 怎么校准 LLM 评分?** A: 抽 100 条人工标,看 LLM 与人工一致性(Kappa 系数);不一致的多是边界 case,加 rubric 改进。

## 题 5:A/B 测试怎么设计? ⭐⭐⃞

### 【场景】
改了 Prompt/模型/RAG 策略,怎么知道比旧版好?

### 【答案要点】

**1. A/B 流程**
- 假设:新版比旧版在某指标上更好
- 分流:随机分用户/请求 A/B 两组(50:50)
- 持续:至少 1-2 周(覆盖周期性)
- 指标:业务指标(任务完成率/满意度/转化率)+ 体验(延迟/成本)

**2. 指标设计**
- **主指标**:1 个核心(如任务完成率)
- **辅助指标**:成本/延迟/点踩率
- **护栏指标**:不能恶化(如安全/合规)

**3. 显著性**
- 样本量:用统计功效算(A/B 计算器)
- 显著性:p < 0.05(或更严 0.01)
- 别只看相对提升,看绝对值 + 置信区间

**4. 坑**
- **辛普森悖论**:总体好但分层差(分用户群看)
- **新奇效应**:新版短期好,长期平(延长观察)
- **流量不均**:分流不随机导致偏差
- **多变量**:同时改多变量无法归因(一次只改一个)

**5. 灰度策略**
- 5% → 20% → 50% → 100%,逐步放量
- 异常指标立即回滚
- 留观察期(长期效应)

### 【加分追问】
- **Q: A/B 样本量怎么算?** A: 看指标基线率 + 期望提升 + 显著性水平(α=0.05) + 功效(β=0.8);用在线计算器或 statsmodels 算。LLM 应用业务指标变化常较小,需大样本。
- **Q: 没有用户量怎么 A/B?** A: 离线评估集 + 线上小流量灰度;或交叉验证(同 Query 跑新旧两版,LLM-as-judge 判优劣)。
