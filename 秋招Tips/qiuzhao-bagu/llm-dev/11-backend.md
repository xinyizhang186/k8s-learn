# 11 · 后端开发(大模型应用后端工程)

> LLM 应用后端和传统 Web 后端不同:长连接、流式、成本敏感、模型多版本、向量数据。
> 本篇聚焦后端工程岗高频场景题,与 `09-engineering.md`(偏应用层并发/成本)互补,这里偏后端基础设施。

## 题 1:设计一个 LLM 网关(LLM Gateway) ⭐⭐⭐⭐⭐

### 【场景】
公司用多个模型供应商(OpenAI/Anthropic/自部署),后端服务都要调,要做统一网关:密钥管理、限流、计费、路由、缓存、审计。请设计。

### 【考察点】
网关架构、多模型抽象、密钥安全、计费、可扩展性

### 【答案要点】

**1. 整体架构**

```
[业务服务 A/B/C]
      ↓ 统一 OpenAI 兼容协议
[LLM Gateway]
  ├── 鉴权(业务 token + 权限)
  ├── 路由(模型选择 / 灰度)
  ├── 限流(令牌桶:QPS + TPM + 成本)
  ├── 缓存(语义缓存 + Prefix Cache)
  ├── 适配层(各家 API 协议转换)
  ├── 密钥管理(多 key 池 + 轮转 + 故障切换)
  ├── 计费埋点(token + 成本)
  └── 审计日志(请求/响应/合规)
      ↓
[OpenAI / Anthropic / 自部署 vLLM / ...]
```

**2. 关键模块**

| 模块 | 设计 |
|---|---|
| **协议适配** | 对外统一 OpenAI 兼容协议(`/v1/chat/completions`),内部转各家协议;LiteLLM/Kong AI Gateway 思路 |
| **密钥管理** | 多 key 池轮转(单 key 限流时切下一个);密钥存 Vault/KMS,不落代码;故障 key 自动剔除+告警 |
| **路由策略** | 按模型/任务/成本/地域路由;支持灰度(新版模型 5% 流量);A/B 对比 |
| **限流** | 多维度:QPS、TPM(tokens/min)、并发数、日成本上限;令牌桶实现 |
| **缓存** | 语义缓存(Query Embedding 相似度 > 阈值复用答案);Prefix Cache 推理层;按 TTL 失效 |
| **计费** | 每请求记 input/output token + 模型单价 → 成本;按业务/用户/模型维度统计;预算告警 |
| **审计** | 全量请求/响应(PII 脱敏)落库;支持合规审计;trace ID 串联 |

**3. 关键技术点**

- **流式透传**:SSE 长连接透传,网关不缓冲(nginx `proxy_buffering off`);支持中途取消
- **重试与熔断**:429/5xx 指数退避重试;连续失败熔断切备用模型/Key
- **超时分级**:流式首 token 超时 vs 总超时分开;长输出任务超时放宽
- **降级链**:主模型限流 → 备用模型 → 自部署小模型 → 缓存答案 → 静态回复
- **多区域**:跨区域容灾,DNS 故障切换

**4. 选型**
- 自研:灵活,适合大厂定制
- **LiteLLM**(开源):多供应商代理 + 密钥管理 + 计费,起步快
- **Kong AI Gateway**:基于 Kong,企业级
- **Cloudflare AI Gateway**:托管,零运维
- **Portkey**:商业 LLM 网关

**5. 工程坑**
- 流式 + 限流难:TPM 限流要预估输出 token(输入长度 × 1.5 估)
- 计费精度:各家计费口径不同(含不含系统 prompt / 工具调用 token),要统一
- 密钥泄露:日志/trace 别记录密钥;error message 别带 key
- 缓存失效:模型版本/Prompt 变 → 缓存失效

### 【加分追问】
- **Q: 语义缓存命中率怎么提?** A: ① 只对确定性任务缓存(创作类不缓存)② system prompt 抽离单独缓存 ③ TTL 按知识时效 ④ 预热高频 Query。
- **Q: 多 key 池怎么实现?** A: 加权轮询(按 key 配额)+ 健康检查(失败剔除)+ 自动恢复(超时后探测);Redis 存 key 状态。
- **Q: 网关会不会成单点?** A: 多副本无状态部署(状态存 Redis)+ 负载均衡;限流配额走 Redis 分布式令牌桶;缓存走 Redis 集群。

## 题 2:LLM 应用的异步任务编排怎么设计? ⭐⭐⭐⭐

### 【场景】
有长任务(文档总结/批量分类/Agent 多步),同步等不行,怎么做异步编排?

### 【答案要点】

**1. 异步任务模型**

```
[Client] POST /task → [网关] → [任务队列 Kafka/RabbitMQ]
                                          ↓
                              [Worker 集群](消费 + 调 LLM)
                                          ↓
                              [结果存储 DB/对象存储]
                                          ↓
[Client] GET /task/{id}/status ← 轮询 / WebSocket / 回调
```

**2. 关键设计**

| 点 | 做法 |
|---|---|
| **任务队列** | Kafka(高吞吐)/ RabbitMQ(灵活路由)/ Redis Stream(轻量) |
| **任务状态** | pending→running→succeeded/failed/cancelled;存 DB |
| **进度上报** | 长任务写进度到 Redis,客户端轮询或 SSE 推 |
| **结果存储** | 大结果存对象存储(S3/OSS),DB 存指针;小结果直接 DB |
| **超时** | 任务级超时 + 心跳(Worker 卡死检测) |
| **重试** | 幂等任务自动重试(指数退避);非幂等人工介入 |
| **死信** | 多次失败入死信队列,人工处理 |
| **取消** | 客户端取消 → 标记 → Worker 检查标志中止 LLM(避免继续浪费 token) |

**3. 工作流引擎选型**

| 引擎 | 特点 | 适用 |
|---|---|---|
| **Temporal** | 持久化工作流,代码即工作流,断点续跑 | 长任务/复杂流程(主流推荐) |
| **Celery** | Python 简单任务队列 | 中小规模 Python 栈 |
| **Airflow** | DAG 数据管道 | 离线批处理 |
| **LangGraph** | Agent 状态图,内置 checkpointer | Agent 工作流 |
| **自研** | Redis + Worker | 简单场景 |

**4. LLM 长任务特殊点**
- **流式中转**:LLM 流式输出 → 网关 SSE 推给客户端(不是 Worker 等完才返)
- **中途取消传播**:Client abort → Gateway → Worker → 推理服务 abort(避免浪费)
- **状态持久化**:Agent 多步,每步 checkpoint,故障可恢复续跑(Temporal/LangGraph checkpointer)
- **资源隔离**:长任务不阻塞短任务(分队列:realtime vs batch)

**5. 批处理优化**
- 离线任务用 OpenAI Batch API(半价,24h 返)
- 自部署:夜间低峰填满 batch
- 任务合并:同类型任务批处理(Embedding 批量算)

### 【加分追问】
- **Q: Temporal 比 Celery 强在哪?** A: ① 持久化(故障重启续跑)② 复杂流程编排(子工作流/定时/信号)③ 长任务支持(天/月级)④ 代码即工作流(易维护)。适合长流程 Agent。
- **Q: Agent 多步任务怎么不丢状态?** A: ① LangGraph checkpointer 持久化 Graph State ② 每步结果落 DB ③ 任务 ID + step ID 串联,故障从最后 checkpoint 续跑。
- **Q: 流式输出怎么和异步任务结合?** A: 任务启动返 task_id,Worker 边生成边写流到 Redis/Stream,客户端订阅 SSE 流式拉;或 WebSocket 长连接直推。

## 题 3:速率限制怎么设计? ⭐⭐⭐⭐

### 【场景】
LLM 应用要防滥用 + 保护后端 + 公平分配,怎么设计多维度限流?

### 【答案要点】

**1. 限流维度**

| 维度 | 限制 | 目的 |
|---|---|---|
| **QPS** | 每秒请求数 | 防瞬时洪峰 |
| **TPM** | tokens/min | 防 token 滥用(更准) |
| **并发** | 同时进行请求数 | 防长任务占满 |
| **日成本** | 单用户/租户日预算 | 防成本失控 |
| **模型分级** | 大模型严格,小模型宽松 | 资源分级保护 |

**2. 算法**

| 算法 | 思路 | 优劣 |
|---|---|---|
| **令牌桶** | 桶按速率生 token,请求消耗 | 主流,允许突发(burst) |
| **漏桶** | 固定速率漏水 | 平滑,无突发 |
| **滑动窗口** | 记录窗口内请求 | 精确,内存大 |
| **分布式令牌桶** | Redis Lua 原子操作 | 多副本一致 |

**3. 分布式限流实现(Redis)**
```
-- 令牌桶 Lua 脚本(原子)
-- key: rate_limit:{user_id}:{model}
-- 返回 1=允许,0=拒绝
local capacity = tonumber(ARGV[1])
local rate = tonumber(ARGV[2])  -- token/秒
local now = tonumber(ARGV[3])
local tokens = tonumber(redis.call('get', KEYS[1]..':tokens') or capacity)
local last = tonumber(redis.call('get', KEYS[1]..':last') or now)
-- 按时间补充 token
tokens = math.min(capacity, tokens + (now - last) * rate)
if tokens < 1 then return 0 end
tokens = tokens - 1
redis.call('set', KEYS[1]..':tokens', tokens)
redis.call('set', KEYS[1]..':last', now)
return 1
```

**4. 多级限流**
- L1 网关:全局 QPS(防 DDoS)
- L2 业务:用户级 QPS/TPM(防滥用)
- L3 模型:单模型并发(防后端过载)
- L4 成本:日预算(防成本失控)

**5. LLM 特殊**
- **TPM 限流难预估**:输出长度未知;用输入长度 × 1.5 估,超了中断
- **流式限流**:流式输出持续消耗 token,需边输出边计;超限中止流
- **分级用户**:VIP 高限额,免费用户严限;按订阅级别
- **熔断**:上游 429 时自身限流避免雪崩

**6. 限流响应**
- 429 + `Retry-After` header(告诉客户端多久后重试)
- 队列等待(非实时任务可排队)
- 降级(超限走小模型/缓存)

### 【加分追问】
- **Q: 令牌桶 vs 漏桶选哪个?** A: LLM 应用用令牌桶(允许突发,符合对话特点);漏桶适合严格平滑场景。
- **Q: TPM 怎么估输出 token?** A: 输入长度 × 1.5 粗估;或按历史平均输出长度;流式时边输出边累计,超限中止(但已生成的要计费)。
- **Q: 分布式限流一致性问题?** A: Redis 集群单 key 限流可能热点;按用户 hash 分片到不同 Redis 节点;或用 Redis Cluster。精度换可用性。

## 题 4:多租户隔离怎么设计? ⭐⭐⭐

### 【场景】
SaaS 化 LLM 应用,多企业客户,数据/资源/模型怎么隔离?

### 【答案要点】

**1. 隔离层次**

| 层 | 隔离内容 | 方案 |
|---|---|---|
| **数据** | 对话历史/记忆/RAG 知识库 | 行级过滤(tenant_id)/ 独立 schema / 独立库 |
| **模型** | 微调模型/LoRA 适配器 | 共享基模型 + 多 LoRA;或独立部署 |
| **资源** | GPU/配额 | 租户级配额(限流 + 资源池) |
| **密钥** | 各家 API key | 租户独立 key 池 |
| **日志** | 审计日志 | 租户独立存储 + 访问权限 |

**2. 数据隔离方案**

| 方案 | 隔离度 | 复杂度 | 适用 |
|---|---|---|---|
| **行级(tenant_id)** | 低 | 低 | 中小客户,SaaS 主流 |
| **独立 schema** | 中 | 中 | 中客户 |
| **独立库** | 高 | 高 | 大客户/合规要求 |
| **独立部署** | 极高 | 极高 | 大客户/私有化 |

**3. 向量库隔离**
- Milvus:collection 级隔离(每租户一个 collection)/ partition 级(轻量)
- pgvector:tenant_id 过滤(简单但性能差)/ 分表
- 注意:检索时强制 tenant_id 过滤,防越权

**4. 模型隔离**
- 共享基模型 + 多 LoRA:vLLM/PEFT 支持动态加载,请求带 tenant_id + LoRA ID
- 大客户独立部署:独立 GPU 池
- 不要用租户数据混训同一模型(会泄露)

**5. 配额与限流**
- 租户级配额:QPS/TPM/日成本上限
- 资源池:大租户独占 GPU,小租户共享
- 超额降级或拒服务

**6. 安全**
- 鉴权:JWT 带 tenant_id,服务端校验
- 越权检测:请求 tenant_id 与 token 一致
- 审计:全量操作日志,按租户分库
- 数据加密:静态加密 + 传输加密

### 【加分追问】
- **Q: 行级隔离性能问题?** A: 数据量大时 tenant_id 过滤慢;可分区表(PG declarative partitioning)/ 按租户分库;向量库用 collection 隔离。
- **Q: 共享模型多 LoRA 怎么不串数据?** A: 推理时权重只读不串;LoRA 适配器按租户独立;但若用租户数据微调基模型会泄露 → 只训 LoRA,基模型不动。
- **Q: 大客户要私有化部署怎么办?** A: 独立 K8s 命名空间 + 独立 GPU 池 + 独立数据;或独立集群;成本由客户承担。

## 题 5:向量库运维怎么设计? ⭐⭐⭐⭐

### 【场景】
向量库百万到亿级数据,怎么保证性能 + 可用 + 可演进?

### 【答案要点】

**1. 索引选型与调优**

| 索引 | 参数 | 影响 |
|---|---|---|
| **HNSW** | M(16-48), ef_construction(100-500), ef_search(50-200) | M/ef 高=精度高+内存大;ef_search 高=查准但慢 |
| **IVF** | nlist(聚类数), nprobe(探测簇数) | nlist 大=内存小+建索引慢;nprobe 大=查准但慢 |
| **DiskANN** | 内存索引 + 磁盘数据 | 超大规模 + 内存不足 |

调优:先建 golden set(每 Query 标正确答案),调参比 Recall@10 + 延迟。

**2. 容量规划**
- 显存/内存:向量数 × 维度 × 4 字节(FP32)/ 2 字节(FP16);HNSW 还要图结构开销 ~2-4x
- 例:1 亿向量 × 1024 维 × 2B(FP16) = 200GB 向量 + 400-800GB HNSW 图 → 集群部署

**3. 可用性**
- 多副本 + 负载均衡(Milvus/Qdrant 支持)
- 持久化:数据落对象存储(Milvus 用 MinIO/S3)
- 监控:QPS / 延迟 / 显存 / 索引大小 / 召回率

**4. 数据迁移与演进**
- **Embedding 模型升级**:换模型要全量重算向量;策略:双索引并行(旧+新),灰度切流,旧下线
- **索引重建**:在线重建 vs 离线重建 + 切流;大规模用滚动重建
- **schema 变更**:元数据字段加减,向量库支持 schema evolution(Milvus/Qdrant)

**5. 增删改**
- **新增**:直接插入,索引增量更新(HNSW 支持但慢;可批量重建)
- **删除**:逻辑删除(tombstone)高效;物理删除要重建索引
- **更新**:删除 + 插入(向量不可变);或重建

**6. 备份恢复**
- 定期快照到对象存储
- 恢复演练(定期测)
- 双写灰度(新库并行写,验证后切流)

**7. 监控指标**
- QPS / P99 延迟
- 召回率(定期跑 golden set)
- 索引大小 / 内存使用
- 写入延迟 / 增量索引状态
- 数据一致性(数量校验)

### 【加分追问】
- **Q: HNSW ef_search 怎么调?** A: 用 golden set 跑不同 ef_search,看 Recall@10 vs P99 延迟曲线,找拐点;线上可动态调(低负载高 ef,高负载低 ef)。
- **Q: 亿级向量怎么扩容?** A: Milvus 分布式分片(按向量 hash);Qdrant 分片 + 副本;或 DiskANN 磁盘索引。容量预估 + 提前扩容,别等满。
- **Q: Embedding 模型升级怎么无感切换?** A: ① 新模型建新索引 ② 双写(新旧都写)③ 双读对比(灰度)④ 切流到新 ⑤ 旧下线;周期 1-4 周。

## 题 6:消息队列在 LLM 应用怎么用? ⭐⭐⃞⭐

### 【场景】
LLM 应用哪些场景要用消息队列?怎么用?

### 【答案要点】

**1. 适用场景**

| 场景 | 用法 |
|---|---|
| **异步任务** | 长任务(总结/分类/Agent)入队,Worker 消费 |
| **削峰填谷** | 高峰请求入队,Worker 按节奏消费保护后端 |
| **事件驱动** | 文档更新 → 事件 → 重新 Embedding 入库 |
| **解耦** | 业务服务与 LLM 服务解耦,各自扩缩 |
| **广播** | 模型版本更新 → 多服务订阅刷新 |

**2. 选型**

| 队列 | 特点 | 适用 |
|---|---|---|
| **Kafka** | 高吞吐,持久化,日志型 | 大规模事件流 |
| **RabbitMQ** | 灵活路由,ACK 机制 | 任务队列,复杂路由 |
| **Redis Stream** | 轻量,低延迟 | 中小规模,简单场景 |
| **SQS**(AWS) | 托管,无运维 | 云上简单场景 |
| **Pulsar** | 计算存储分离,多租户 | 大规模复杂场景 |

**3. 关键设计**
- **幂等消费**:消息可能重复投递,消费端要幂等(去重 ID / 状态机)
- **顺序保证**:同任务多消息要同分区(Kafka partition key)
- **死信队列**:多次失败入死信,人工处理
- **背压**:Worker 处理不过来时,队列长度告警 + 限流入口
- **监控**:队列长度 / 消费延迟 / 失败率

**4. LLM 场景实例**
- 文档入库流水线:文档变更 → Kafka → Embedding Worker → 向量库
- 批处理:夜间 Batch API 任务入队,Worker 消费
- Agent 长任务:Agent step 完成发事件 → 下游订阅

### 【加分追问】
- **Q: Kafka vs RabbitMQ?** A: Kafka 高吞吐日志型(事件流/审计);RabbitMQ 灵活路由任务队列;LLM 应用任务队列常用 RabbitMQ,事件流用 Kafka。
- **Q: 消息丢了怎么办?** A: ① 生产端开启 ACK + 持久化 ② 消费端手动 ACK(处理完才确认)③ 死信队列兜底 ④ 关键业务双写 DB + 队列。

## 题 7:对话历史和记忆数据库怎么设计? ⭐⭐⃞⭐

### 【场景】
LLM 应用要存多轮对话历史 + 用户记忆 + 审计日志,怎么设计数据库?

### 【答案要点】

**1. 表设计(关系库)**

```
-- 对话表
conversations(id, user_id, tenant_id, title, created_at, updated_at, ...)

-- 消息表(每轮)
messages(
  id, conversation_id, role(user/assistant/tool),
  content, tokens_in, tokens_out, model, cost,
  tool_calls(JSON), tool_results(JSON),
  created_at, ...
)

-- 用户记忆(结构化)
user_memory(id, user_id, key, value, updated_at, source)

-- 审计日志
audit_logs(id, user_id, request, response_hash, model, tokens, cost, latency, created_at)
```

**2. 选型**
- **PostgreSQL**:主流,JSONB 存工具调用,pgvector 扩展存向量
- **MongoDB**:文档型适合消息(灵活 schema)
- **Redis**:热数据缓存(最近对话)+ Stream 存事件
- **对象存储**:大响应(完整 trace)存 S3,DB 存指针

**3. 读写优化**
- **读**:对话列表分页游标;消息按 conversation_id + created_at 索引
- **写**:高并发写用队列削峰 + 批量写;审计日志异步落库
- **归档**:老对话归档到对象存储 + 冷库;热库只留近期
- **分区**:按 tenant_id / created_at 分区,大表必备

**4. 向量 + 关系混合**
- 对话历史关系库 + 语义检索向量库
- 记忆 Mem0 思路:LLM 抽关键事实 → 向量库存
- 检索时:向量召回相关历史 + 关系库取最近 N 轮

**5. 隐私与合规**
- PII 脱敏后存
- 按租户/用户权限隔离
- 删除权(GDPR):用户删数据要级联清向量库 + 关系库 + 备份
- 保留期:审计日志按合规保留(6 月-2 年)

### 【加分追问】
- **Q: 用 MongoDB 还是 PG?** A: 消息灵活 schema 用 MongoDB 适合;但事务 + 关系 + 向量(pgvector)用 PG 一体化;看团队栈 + 是否要事务。
- **Q: 对话历史太长怎么存?** A: ① 摘要压缩老对话 ② 长对话分章节 ③ 大响应(完整 trace)存对象存储,DB 存指针 ④ 归档冷库。

## 题 8:配置中心怎么设计? ⭐⭐⃞

### 【场景】
LLM 应用的模型版本/Prompt/特性开关要能热切换,怎么设计配置中心?

### 【答案要点】

**1. 配置分类**

| 类型 | 内容 | 变更频率 |
|---|---|---|
| **模型配置** | 模型名/端点/API key/参数 | 中 |
| **Prompt 模板** | system/user 模板 | 高 |
| **特性开关** | 灰度功能开关 | 高 |
| **限流配额** | 用户/租户限额 | 中 |
| **业务规则** | 话术/路由规则 | 中 |

**2. 设计要点**
- **热更新**:不重启服务生效(配置中心推送 / 客户端拉)
- **版本管理**:配置变更可回滚(版本号 + diff)
- **灰度发布**:配置按用户/租户/流量灰度
- **审计**:谁改了什么,何时,为何
- **多环境**:dev/staging/prod 隔离

**3. 实现选型**
- **Apollo**(携程开源):配置中心,功能全
- **Nacos**(阿里):配置 + 注册中心
- **Consul**:配置 + 服务发现
- **etcd**:K8s 用,分布式 KV
- **自研**:DB + 推送 + 客户端 SDK

**4. LLM 特殊**
- Prompt 版本化:每 Prompt 入 Git,语义版本
- 模型路由配置:规则可热切换(主模型故障切备用)
- 特性开关:新功能(如多模态/Agent)按用户灰度
- A/B 配置:实验配置按流量分桶

**5. 工程实践**
- 配置变更触发回归测试(golden set)
- 监控配置变更后的业务指标
- 关键配置(限流/路由)变更需审批
- 配置中心自身高可用(多副本 + 持久化)

### 【加分追问】
- **Q: 配置中心宕机怎么办?** A: 客户端缓存配置 + 本地 fallback;配置中心多副本 + 持久化;故障时用本地缓存继续服务(只读)。
- **Q: Prompt 频繁变更怎么管理?** A: Prompt 入 Git 版本控制 + 配置中心热推送;变更走 PR + 回归测试;A/B 灰度上线。

## 题 9:链路追踪与日志怎么设计? ⭐⭐⭐⭐

### 【场景】
LLM 应用一次请求涉及多服务(网关→业务→RAG→LLM→工具),怎么追踪排障?

### 【答案要点】

**1. 全链路 trace**

```
trace_id: abc123
├── span1: gateway (12ms)
├── span2: business_service (50ms)
│   ├── span2.1: rag_retrieve (80ms)
│   │   ├── embedding (10ms)
│   │   └── vector_search (60ms)
│   ├── span2.2: rerank (40ms)
│   ├── span2.3: llm_call (1500ms)
│   │   ├── ttft (800ms)
│   │   └── generation (700ms)
│   └── span2.4: tool_call (200ms)
└── span3: response (5ms)
```

**2. 关键字段**
- **trace_id**:全链路唯一
- **span_id**:每段唯一,父子关系
- **业务字段**:user_id / tenant_id / conversation_id / request_id
- **LLM 字段**:model / prompt_tokens / completion_tokens / cost / ttft / tpot
- **RAG 字段**:retrieval_count / rerank_scores / context_ids
- **Agent 字段**:step / tool_name / tool_params / tool_result
- **错误字段**:error / status_code / retry_count

**3. 工具选型**

| 工具 | 特点 |
|---|---|
| **LangSmith** | LangChain 系,LLM trace 深度集成 |
| **Langfuse** | 开源,框架无关,自部署 |
| **Arize Phoenix** | 开源,LLM 可观测 |
| **OpenTelemetry** | 通用标准,对接 Jaeger/Tempo |
| **SkyWalking / 阿里 ARMS** | 国产 APM |

**4. 日志设计**
- **结构化日志**:JSON 格式,便于检索
- **级别**:INFO(请求/响应)/ DEBUG(中间步骤)/ WARN(重试/降级)/ ERROR(失败)
- **采样**:全量存成本高,正常请求采样 1-10%,错误/慢请求全存
- **PII 脱敏**:日志落库前脱敏(手机/身份证/银行卡)

**5. 监控看板**
- 实时:QPS / P99 延迟 / 错误率 / 成本
- 链路:trace 视图,慢请求/错误请求一键查
- 业务:任务完成率 / 转人工率 / 点踩率
- 成本:每请求成本 / 每用户日成本

**6. 告警**
- 错误率飙升
- P99 延迟飙升
- 成本异常(单用户成本飙升)
- 队列堆积
- 模型 API 故障

### 【加分追问】
- **Q: trace 数据量大怎么办?** A: ① 采样(正常 1%,异常全采)② 只存 trace 元数据 + 关键 span ③ 老 trace 归档冷库 ④ 完整请求/响应存对象存储,DB 存指针。
- **Q: Langfuse vs LangSmith?** A: LangSmith 闭源但与 LangChain 集成深;Langfuse 开源可自部署,框架无关;私有部署 + 框架灵活选 Langfuse。
- **Q: 怎么定位慢请求?** A: trace 找最长 span;LLM 慢看 ttft(预填慢)还是 tpot(decode 慢);RAG 慢看 embedding 还是向量检索;对症优化。

## 题 10:灰度发布与回滚怎么设计? ⭐⭐⃞

### 【场景】
LLM 应用改了模型/Prompt/RAG 策略,怎么安全发布?出问题怎么回滚?

### 【答案要点】

**1. 发布策略**

| 策略 | 做法 | 适用 |
|---|---|---|
| **蓝绿** | 两套环境,切流 | 资源充足,快速回滚 |
| **金丝雀** | 小流量验证 → 逐步放量 | 主流,稳妥 |
| **特性开关** | 按用户/租户开关 | 功能灰度 |
| **滚动** | 逐实例替换 | K8s 默认 |

**2. 金丝雀流程**
- 1% → 5% → 20% → 50% → 100%,每阶段观察 1-24h
- 监控:错误率 / P99 延迟 / 业务指标(任务完成率)/ 成本
- 异常立即回滚(流量切回旧版)

**3. 回滚设计**
- **配置回滚**:模型/Prompt 版本一键切回(配置中心)
- **代码回滚**:K8s `kubectl rollout undo` / 蓝绿切换
- **数据回滚**:迁移类变更要可逆(双写灰度 + 切流 + 旧库保留)
- **缓存清理**:Prompt/模型变了,清相关缓存

**4. LLM 特殊**
- **模型版本**:新旧模型并行(影子流量对比),灰度切流
- **Prompt 版本**:配置中心热切换,异常秒回滚
- **RAG 索引**:新旧索引并行,切流后旧下线
- **微调模型**:新模型影子流量,质量验证后才切流

**5. 自动化**
- 灰度进度自动化(指标达标自动放量)
- 异常自动回滚(错误率/延迟超阈值)
- 发布卡点(回归测试不通过不能发)

**6. 实战经验**
- 关键变更(模型/核心 Prompt)灰度周期长(1-7 天)
- 监控核心业务指标,不只看技术指标
- 留观察期(发布后 24-72h 监控长期效应)
- 回滚演练(定期测回滚流程是否可用)

### 【加分追问】
- **Q: 灰度期间数据不一致怎么办?** A: ① 双写(新旧模型都处理,只返新版结果)② 灰度用户数据标 version,回滚只回滚这部分 ③ 关键业务数据变更要可逆设计。
- **Q: 模型回滚后已生成的内容怎么办?** A: 已生成的结果不撤回(用户已看到);但缓存清掉,后续请求走旧模型;若已下发给用户的内容有质量问题,人工跟进。
- **Q: 怎么知道灰度版本比旧版好?** A: ① 业务指标(任务完成率/满意度)显著优 ② LLM-as-Judge 离线评估 ③ 用户反馈(点踩率)④ 不显著则继续灰度或回滚。
