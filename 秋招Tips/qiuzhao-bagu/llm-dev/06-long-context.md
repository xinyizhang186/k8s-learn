# 06 · 长上下文

> 长上下文模型(128K/1M)普及,但工程坑多。Lost-in-Middle、KV Cache 爆炸、成本是高频考点。

---

## 题 1:长文本怎么处理? ⭐⭐⭐⭐

### 【场景】
用户上传 100 页 PDF 问问题,模型上下文装不下,怎么办?

### 【答案要点】

**1. 三种思路**

| 方案 | 做法 | 适用 |
|---|---|---|
| **RAG** | 切块→向量检索 Top-K→拼 prompt | 知识库问答,主流 |
| **Map-Reduce** | 分块各自总结→合并总结 | 长文档摘要 |
| **长上下文** | 直接全塞(128K/1M 模型) | 单文档分析,成本高 |
| **Refine** | 顺序处理块,逐块 refine 答案 | 流式长文档 |

**2. 选型决策**
- 知识库问答(找特定信息)→ **RAG**(精准+省成本)
- 长文档总结(需全局视角)→ **Map-Reduce** 或长上下文
- 单文档问答(< 128K)→ **长上下文**(简单)
- 超长文档(> 128K)→ **RAG** 或 Map-Reduce

**3. Map-Reduce 摘要**
- Map:每块单独总结(LLM 调用 N 次,可并行)
- Reduce:把所有块总结合并成最终摘要
- 进阶:Refine(顺序,每块基于前文 refine,信息保留更好但慢)
- 注意:多次 LLM 调用成本累加

**4. 长上下文直接塞**
- 模型:GPT-4o(128K)、Claude 3.5(200K)、Gemini 1.5(1M)、Qwen2.5(128K)、DeepSeek-V3(128K)
- 坑:Lost in the Middle + 成本高 + 延迟高
- 优化:把重要信息放头尾;压缩冗余

**5. 实战组合**
- 长文档先 Map-Reduce 摘要 → 摘要 + 关键段 RAG → 生成
- 多文档 RAG:每文档先摘要,再跨文档检索

### 【加分追问】
- **Q: 100 页 PDF 大概多少 token?** A: 中文 1 页 ~800-1500 token,100 页 ~8-15 万 token;128K 模型勉强装下,但 prefill 慢 + 贵。
- **Q: Map-Reduce 摘要会丢信息吗?** A: 会。多次摘要累计信息损失;Refine 顺序处理能保更多信息但慢;关键信息要结构化抽取。

## 题 2:上下文 128K 还是装不下怎么办? ⭐⭐⃞⭐

### 【场景】
文档 200K token,128K 上下文装不下。怎么办?

### 【答案要点】

**1. 策略**

| 方法 | 做法 |
|---|---|
| **RAG** | 切块检索只送相关 Top-K |
| **分层摘要** | 先 Map-Reduce 摘要到 < 128K,再处理 |
| **分段处理 + 合并** | 分 N 段各自处理,结果合并 |
| **更长上下文模型** | Gemini 1.5 Pro(1M)、Claude 3.5(200K) |
| **Agent 多步检索** | Agentic RAG,按需多次检索 |

**2. RAG 优先**
- 大部分场景 RAG 最优:精准 + 省成本
- 把 200K 文档切块,向量检索 + Rerank 选 Top 5-10 块
- 配 Rerank 提精度

**3. 分层摘要**
- 第一层:每章节摘要 → 章节摘要集
- 第二层:章节摘要再摘要 → 全局摘要
- 用全局摘要 + 章节摘要检索回答

**4. Agentic RAG**
- Agent 根据问题决定检索哪段、检索几次
- 比单次 RAG 更精准,适合复杂多跳问题
- 代价:多轮 LLM 调用慢且贵

**5. 切换模型**
- Gemini 1.5 Pro:1M token 上下文
- Claude 3.5 Sonnet:200K
- 注意:长上下文成本和延迟显著上升

### 【加分追问】
- **Q: 1M 上下文为什么不普及用?** A: ① 成本高(1M 输入几十美元一次)② prefill 慢(分钟级)③ Lost-in-Middle ④ 大部分场景 RAG 更省更好。

## 题 3:Lost in the Middle 是什么?怎么解? ⭐⭐⭐⭐

### 【场景】
长上下文模型,中间位置的信息容易答错,怎么回事?

### 【答案要点】

**1. 现象**
- 论文 Liu 2023:模型对长上下文头尾信息召回好,中间位置精度骤降
- 即使上下文窗口足够,关键信息放中间也可能被忽略

**2. 原因**
- 注意力机制对位置敏感(位置编码衰减)
- 训练数据中重要信息多在头尾(system prompt 头、答案尾)
- 长上下文 attention 分散

**3. 缓解方法**

| 方法 | 做法 |
|---|---|
| **重排** | 把最相关内容放头尾,次相关放中间 |
| **Rerank + 重组装** | 检索 Top-K 后 Rerank,按分数排头尾 |
| **关键信息前置** | system prompt + 最重要上下文放头 |
| **减小上下文** | 只送 Top 3-5,别贪多 |
| **多轮检索** | Agentic RAG,按需检索减少上下文 |
| **长上下文训练模型** | 新模型(YaRN/RoPE 扩展)对此有改进 |

**4. 实战**
- RAG Top5:Rerank 后按 [1,3,5,2,4] 顺序(分数高在头尾)或 [1,2,3,4,5] 头部优先
- system prompt 永远在最前
- 评估:Needle-in-a-Haystack 测不同位置召回率

### 【加分追问】
- **Q: 新模型还有 Lost in the Middle 吗?** A: 改善但未消除。GPT-4/Claude 较好,但长上下文 + 中间位置仍有精度下降。要测。
- **Q: 怎么测自家模型的 Lost-in-Middle?** A: Needle-in-a-Haystack:在长文本不同位置插入特定事实,看模型能否找到;绘制位置-召回率热力图。

## 题 4:长上下文模型怎么选型? ⭐⭐⃞

### 【场景】
需要处理长文档,选哪个长上下文模型?

### 【答案要点】

**1. 主流长上下文模型**

| 模型 | 上下文 | 备注 |
|---|---|---|
| **Gemini 1.5 Pro** | 1M / 2M | 最长,Google |
| Claude 3.5 Sonnet | 200K | Anthropic,长文档强 |
| GPT-4o | 128K | OpenAI |
| Qwen2.5-Turbo | 1M | 阿里,中文长文本 |
| DeepSeek-V3 | 128K | 开源 |
| Llama-3.1 | 128K | 开源,可自部署 |

**2. 选型维度**
- 长度:够用即可,别盲目追长(越长越贵)
- 中文效果:Qwen / DeepSeek 中文强
- 开源 vs 闭源:私有部署用 Llama/DeepSeek/Qwen
- 成本:Gemini 1M 输入几美元一次;128K 模型便宜
- Lost-in-Middle 实测

**3. 长上下文扩展技术**
- **RoPE/ALiBi 位置编码扩展**:训练时短,推理时插值外推
- **YaRN**:RoPE 扩展方法,128K→1M
- **LongRoPE**:微软,扩展到 2M
- **训练**:长上下文 SFT + 长文档数据

**4. 实战**
- 单文档 < 128K:任意主流模型
- 超长(> 200K):Gemini 1.5 Pro 或 RAG
- 私有部署:Llama-3.1-8B/70B + YaRN 扩展,或 DeepSeek-V3

### 【加分追问】
- **Q: 上下文越长越好吗?** A: 不是。① 成本线性增 ② prefill 延迟增 ③ Lost-in-Middle ④ 大部分任务 RAG 更优。够用即可。
- **Q: 开源模型怎么扩上下文?** A: 用 YaRN/LongRoPE 等位置编码外推 + 少量长上下文 SFT;不重新全参预训练。

## 题 5:KV Cache 压缩有哪些方法? ⭐⭐⃞

### 【场景】
长上下文 KV Cache 太大,显存/带宽爆。怎么压?

### 【答案要点】

**1. 方法分类**

| 方法 | 思路 |
|---|---|
| **量化** | KV Cache INT8/FP8,减半 |
| **Sliding Window** | 只保留最近 N token(Mistral) |
| **Eviction** | 丢弃低重要性 KV(H2O/Loki) |
| **Token Merge** | 合并相似 token KV |
| **Compression** | KV 压缩成更小表示(CacheGen) |
| **Offload** | KV 放 CPU/SSD,需要时加载 |

**2. 量化**
- KV Cache INT8:几乎无损,显存减半
- FP8:新硬件(H100)原生,几乎无损
- INT4:有损,近年技术改善

**3. Sliding Window**
- Mistral:固定窗口(如 4096),只看最近 + 部分历史
- 适合长文档总结/流式,不适合长程依赖

**4. Eviction**
- H2O:基于 attention score 丢低重要性 KV
- 适合长生成场景,需调保留比例

**5. 多查询注意力(MQA/GQA)**
- 减少 KV 头数(见 03-inference-deploy 题 2)
- Llama-3 用 GQA,KV Cache = MHA 的 1/4
- 模型架构层面优化

**6. 实战**
- 优先量化 + GQA(模型选型时定)
- Sliding Window 适合长生成
- Eviction 是研究热点,工程化谨慎

### 【加分追问】
- **Q: KV Cache 压缩对精度影响?** A: 量化(INT8/FP8)几乎无损;Eviction 压缩有损,需评估;Sliding Window 改变模型行为(只看局部)。
- **Q: 为什么 GQA 是从架构层省 KV?** A: 训练时就定 KV 头数 < query 头数,模型学会共享;不可后期改,选模型时定。

## 题 6:长文档摘要方案怎么设计? ⭐⭐⃞

### 【场景】
做法律合同/财报摘要,文档 200 页,怎么稳定输出高质量摘要?

### 【答案要点】

**1. 方案选型**

| 方案 | 适用 | 优劣 |
|---|---|---|
| **直接塞** | 文档 < 上下文窗口 | 简单,但贵 + 可能 Lost-in-Middle |
| **Map-Reduce** | 超长文档 | 全局视角,但多次调用信息损失 |
| **Refine** | 长文档保信息 | 顺序 refine 信息保留好,慢 |
| **RAG + 摘要** | 找特定信息 | 精准但全局视角弱 |

**2. Map-Reduce 流程**
```
长文档 → 切块(章节/段) → 每块独立摘要(Map,并行)
       → 摘要合并 → 全局摘要(Reduce)
```
- 注意:块大小要语义完整(按章节/段)
- Reduce 多层:块摘要 → 章节摘要 → 全局摘要

**3. Refine 流程**
```
块1 → 摘要1
块2 + 摘要1 → 摘要2(refine,信息累积)
块3 + 摘要2 → 摘要3
... → 最终摘要
```
- 信息保留比 Map-Reduce 好,但顺序慢,不能并行

**4. 结构化摘要**
- 不只输出文本,输出结构化 JSON:`{摘要,关键条款,金额,日期,风险点}`
- 利于下游使用 + 评估

**5. 质量提升**
- Prompt:明确摘要要求(长度/重点/格式/受众)
- 多模型投票:多个模型摘要取并集
- 人工抽检评估

**6. 评估**
- ROUGE/BLEU(与人工摘要比)
- LLM-as-judge(完整性/准确性/简洁性)
- 关键信息抽取率(摘要是否覆盖关键事实)

### 【加分追问】
- **Q: 摘要怎么避免丢关键信息?** A: ① 结构化抽取关键事实(金额/日期/条款)② Refine 顺序累积 ③ 多模型投票 ④ 关键事实单独提取 + 摘要双输出。
- **Q: 法律摘要精度要求高怎么办?** A: ① 结构化提取条款 + 数值 ② 关键条款原文保留 + 摘要 ③ 人工抽检 ④ 多 pass(第一遍粗摘要 → 第二遍补漏)。
