# 工作簿与数据契约

## `版本分析`

采用三层结构，不得直接从第 1 行开始放列头：

1. 第 1 行：合并 `A:E`，标题为 `kubernetes v<from>-v<to> Release Note/ChangeLog解读`。
2. 第 2 行：合并 `A:E`，章节标题 `关键特性分析`。
3. 第 3 行：关键特性 5 列表头。
4. 特性数据行：以每个版本官方发布博客目录为最小覆盖基线，不是精选摘要；按版本号从高到低排列，同一版本内按 `孵化成熟特性:<version>`、`增强特性：<version>`、`新增特性：<version>` 分类。博客 Stable、Beta、Alpha 小节逐项覆盖，Spotlight 与同名正文去重。
5. 空一行后增加合并章节标题 `关键变更风险分析`，再放风险表头和风险数据。

关键特性固定 5 列：

| 列 | 内容 |
|---|---|
| 分类 | 严格限定三类（含版本后缀）：`孵化成熟特性:<version>`、`增强特性:<version>`、`新增特性:<version>`。禁止使用 `关键特性`、`highlight` 或其他任何分类值。Spotlight 小节中未标注 Stable/Beta/Alpha 前缀的特性归入 `孵化成熟特性`。 |
| 特性名称 | 只允许使用 `release-catalog.json` 中由 Kubernetes 正式发行版博客标题提取的 `name` 原文。不得从 KEP、CHANGELOG、`kube_features.go` 或模型知识命名；不得翻译、缩写、改大小写、改复数、补充括号或改成 FeatureGate 名。分析项必须携带对应 `catalog_id`，构建器按该 ID 写入官方名称并忽略生成文本中的改名。 |
| 特性功能介绍 | 富文本结构：粗体 `现状：` + 受影响对象、典型场景、旧行为、实际限制及其后果（需充分展开，描述具体影响而非概括性一句话）；换行后粗体 `本特性增强：` + 目标版本、阶段/默认状态、核心机制、关键 API/配置、适用范围、依赖和边界、实际收益（需解释机制价值和采用前提，不可仅复述阶段和默认值） |
| 特性价值领域 | 只给出最主要的一种短标签，如 `DFX:安全`、`DFX:性能`、`功能：存储`、`功能：调度`、`功能：网络`、`DFX:可观测性`、`DFX:可靠性` 等；禁止多项逗号并列 |
| 特性功能价值分析 | 清晰简洁、准确明确地给出独立判断：先写直接收益（谁获得什么具体好处），再写受益场景，最后写采用前提或残余风险。禁止重复功能介绍；禁止只写“提升效率”“增强稳定性”等泛化表述；禁止模糊推断或缺乏证据的收益假设。 |

`特性功能介绍` 与 `特性功能价值分析` 的主体证据必须是该版本正式发行博客。博客信息不足时，才可补充同项 KEP、官方文档或固定 Tag 资料；补充来源不得改变博客定义的特性主体、版本归属或发布状态。

当目录项包含 `sub_features`（发布博客正文中明确列出多个子特性及其 KEP 编号，如 "DRA features in Alpha"、"DRA features in beta"、"Workload Aware Scheduling (WAS) features"）时，`enhancement` 文本应逐项展开每个子特性：每行一个子特性，格式为 `子特性名称（KEP #<id>，<SIG>）<中文功能描述>，升级为 <阶段> 并默认<启用/关闭>。`，行间用换行分隔。子特性名称从 KEP 标题映射获取，中文功能描述由阶段 3 将 `sub_features[].description`（英文源码注释）翻译为中文或根据 FeatureGate 名称编写中文功能性描述；阶段和默认值从 `machine-facts.json` 中该 KEP 对应的 FeatureGate 的 `after` 状态获取。`current_problem` 仍描述该组特性共同解决的旧行为限制。所有 `enhancement` 文本必须使用中文撰写，不得保留英文源码注释原文。

风险区固定 5 列：`分类 | 变更名称 | 风险详细描述 | 风险涉及领域 | 技术or商业影响`。风险分类使用 `特性剔除:<version>`。覆盖发布博客弃用、移除和明确升级阻断项；不得把风险描述留空，也不要把全部 FeatureGate 变化复制到此 Sheet。`技术or商业影响` 列（对应 `analysis.json` 中风险条目的 `value_analysis` 字段）必须严格按以下三类格式之一填写，禁止自由发挥或其他表述：
- 参数或特性弃用：`关键参数/特性弃用，产品需审视是否使用<具体特性/参数名>字段，及时适配`
- 特性整体弃用：`关键特性弃用，产品需审视是否使用<具体特性名>，及时适配`
- 特性版本弃用：`关键特性版本弃用，产品需审视是否使用<具体特性名>，及时适配`

其中 `<具体特性/参数名>`、`<具体特性名>` 替换为风险条目对应的特性名称或被弃用的参数/字段名；按风险类型选择对应格式，不得混用、不得增删格式中的固定词句。

## 视觉与尺寸

- `版本分析` 的总标题、章节标题、列头和所有实际数据单元格都必须有完整四边细线；合并标题只要求左上主单元格保留外框。
- `版本分析` 总标题无底色、黑色粗体 16pt；章节标题使用浅橙色底黑字；列头使用 `D9E1F2` 浅蓝底黑字，与参考工作簿保持一致。`特性变更` 表头使用 `1F4E79` 深蓝底白字。
- 正文使用微软雅黑 11-12pt，自动换行；`版本分析` 正文顶部对齐，`特性变更` 正文顶部对齐。行高按中文双宽字符、显式换行和列宽估算，优先保证全文可见；`版本分析` 特性行高 76-260pt，风险行高 42-140pt，`特性变更` 行高 28-92pt。整体紧凑但不拥挤。
- `版本分析` 的前三列保持紧凑：分类约 16、特性名称约 40、特性功能介绍约 88 个 Excel 列宽单位；允许名称和介绍换行，必须通过动态行高完整展示。价值分析列约 60，避免整张表横向过度膨胀。

## `特性变更`

固定 14 列。第 1 列保留本 Skill 增加的版本范围，其余 13 列与参考工作簿一致：

1. 版本变更阶段：格式为 `v<prior_version>->v<to_version>`，其中 `<to_version>` 为当前分析版本，`<prior_version>` 为该 FeatureGate 在 `kube_features.go` 源码版本化历史中、分析版本之前的最近一个版本化 spec 的版本号，每个条目的 `prior_version` 不一定相同。例如某 gate 最近的 spec 版本为 v1.32，则显示 `v1.32->v1.37`；另一 gate 最近的 spec 版本为 v1.35，则显示 `v1.35->v1.37`。若该 gate 在分析版本首次引入（无更早的 spec），则 `prior_version` 等于 `to_version`，显示如 `v1.37->v1.37`。该值由 `machine-facts.json` 的 `prior_version` 字段唯一确定。
2. 变更类型：只使用 `Added`、`Changed`、`Deprecated`、`Removed`
3. 特性名称
4. 特性阶段变化
5. 默认值变化
6. 默认值锁定
7. 是否兼容：写 Excel 布尔值，不写“兼容/有条件兼容”文本
8. 兼容分析：无影响时写 `特性默认关闭，无影响` 或 `开关状态不变，无影响`；高影响行留空并在后续列展开
9. 分析结论
10. 排查方法
11. 参考资料
12. 详细说明
13. 建议开启？
14. 补充说明

阶段和布尔变化使用紧凑箭头格式，例如 `Alpha->Beta`、`->true`、`true->`；没有锁定变化且范围内未显式设置时留空。前 6 列来自目标 tag 范围事件机器事实，后续列来自官方证据和审慎推理。`Removed` 只用于 CHANGELOG 或源码明确证明目标版本已移除的补充事件，不能仅因相邻 tag 端点差异就写入主表。

`machine-facts.json` 的每个变更事件包含从目标 tag `kube_features.go` 注释自动提取的 `gate_description` 和 `kep_url` 字段，用于自动生成 `排查方法` 和 `详细说明`：

- `gate_description`：源码注释中 `owner:`/`kep:` 行之后的功能描述文本（英文），阶段 3 须翻译为中文后使用。
- `kep_url`：源码注释中的 `kep:` URL，规范化为 `https://kep.k8s.io/<id>`。

`排查方法` 和 `详细说明` 必须使用中文撰写，不得直接插入英文 `gate_description` 原文。`gate_description` 的英文内容仅作为理解 FeatureGate 功能的参考，阶段 3 须将其翻译或改写为通顺的中文功能描述。

`排查方法` 从机器事实按以下规则生成中文内容：

1. 用中文描述该 FeatureGate 的功能（从 `GATE_CN` 或 `GATE_NAME_CN_FALLBACK` 字典获取 `cn_desc`；若为空，根据 FeatureGate 名称推断中文功能描述）。
2. 根据 `change_type` 和 `before`/`after` 状态描述具体的行为变化（不得使用通用模板如"开启后该特性自动生效"）：
   - `Added` + `default=true`：写"vX 新增并默认启用，升级后自动激活"
   - `Added` + `default=false`：写"vX 新增，默认关闭，需手动启用"
   - `Deprecated`：写"该门控已弃用，默认关闭/启用，建议关闭并迁移"
   - `default` 从 false 变 true：写"默认值由关闭变为启用，升级后自动激活"
   - 升级为 GA：写"升级为 GA 并默认启用，该特性已锁定不可关闭"
3. 根据 FeatureGate 名称中的关键词推断排查对象并写出具体检查方法。

`详细说明` 从机器事实按以下规则生成中文内容，必须详细、准确、可读性强地描述当前特性的功能机制：

1. 以功能描述为主体：从 `GATE_CN` 或 `GATE_NAME_CN_FALLBACK` 字典获取 `mechanism`（功能机制描述）；若为空则使用 `cn_desc`（中文功能概述）。描述须解释该特性是什么、改变了什么、如何工作，是本列的核心内容。
2. **必须包含四个内容维度**，缺一不可：
   - **功能定义**：该特性是什么，解决什么问题（一句话概述特性的核心能力）；
   - **行为变化**：该特性改变了什么（旧状态→新状态的具体行为差异，不只是阶段名）；
   - **核心机制**：该特性如何工作（机制原理、关键 API/配置字段名、处理流程），须给出具体技术细节而非泛化描述；
   - **适用范围或依赖边界**：该特性在什么条件下生效，依赖哪些组件或前置条件。
3. 末尾附一句简短的阶段过渡说明（旧状态→新状态），不得展开为升级建议或兼容性判断——这些属于 `分析结论` 和 `排查方法` 列。
4. 禁止复述"升级到 vX 后该特性默认启用，确认相关组件兼容性后可直接升级"等升级影响模板话术，禁止只复述阶段和默认值，此类信息已在 `分析结论` 列覆盖。

当 `gate_description` 为空时，`排查方法` 和 `详细说明` 仍需基于 FeatureGate 名称、阶段变化和默认值变化编写中文功能性描述，不得留空或只写"待核实"。

内容采用稀疏且分级的规则：

- `兼容分析` 有内容时，`分析结论`、`排查方法`、`参考资料`、`详细说明`、`建议开启？`、`补充说明` 全部留空，避免重复解释无影响项。
- `兼容分析` 为空时，填写排查方法、参考资料、详细说明、分析结论和补充说明。高影响行展开受影响对象、迁移动作和回退条件。
- `排查方法` 须包含 gate 专属功能描述 + 具体行为变化（Added/Changed/Deprecated 各有专属描述）+ 具体检查对象。禁止使用"开启后该特性自动生效"等通用模板。
- `详细说明` 必须详细、准确、可读性强地描述当前特性的功能机制——包含功能定义、行为变化、核心机制、适用范围或依赖边界四个维度；以特性功能描述为主体（机制说明），末尾附一句简短阶段过渡；禁止复述升级影响模板话术，禁止只复述阶段和默认值。
- `分析结论` 须给出明确的升级决策（如"确认兼容性后直接升级"/"建议关闭并迁移"/"不可回退"），禁止只复述阶段和默认值。
- `建议开启？` 仅允许 `开启`、`关闭` 或空白。默认开启/由 false 变为 true 的高影响项写 `开启`；Deprecated/Removed 写 `关闭`；其余留空。
- `补充说明` 只保留最关键的一条适用边界、依赖或后续动作，优先一整句，建议不超过 90 个字符。
- 参考资料优先放单个 KEP 或最直接的官方页面，不在单元格中堆叠源码、CHANGELOG 和多个重复 URL。

## `analysis.json`

内部使用英文键，避免不同工具对中文键处理不一致：

```json
{
  "version_analysis": [
    {
      "catalog_id": "release-blog:1.36:feature:example",
      "version": "1.36",
      "category": "关键特性",
      "category_group": "孵化成熟特性:1.36",
      "feature_name": "Example",
      "name_source": "official_release_blog",
      "primary_source": "https://kubernetes.io/blog/<formal-release-blog>/",
      "supplemental_sources": [
        {
          "url": "https://kep.k8s.io/<id>",
          "supports": ["enhancement", "value_analysis"],
          "reason": "正式发行博客未说明具体机制或适用边界"
        }
      ],
      "current_problem": "此前的具体限制或风险",
      "enhancement": "本版本引入或毕业的具体机制",
      "feature_summary": "可选的纯文本备份",
      "value_domain": "DFX:稳定性",
      "value_analysis": "...",
      "sub_features": [
        {"kep_id": "5729", "kep_url": "https://kep.k8s.io/5729", "sig": "SIG Scheduling / SIG Node"}
      ],
      "sources": ["https://kubernetes.io/blog/..."],
      "status": "ready"
    }
  ],
  "feature_changes": [
    {
      "id": "1.35-to-1.36:ExampleGate",
      "compatibility": true,
      "compatibility_analysis": "...",
      "conclusion": "...",
      "check_method": "...",
      "sources": ["https://..."],
      "details": "...",
      "recommendation": "开启/关闭/空字符串",
      "notes": "...",
      "status": "ready"
    }
  ]
}
```

`extract_feature_changes.py` 会创建骨架，并将不可改写的字段保存在 `machine-facts.json`。`build_report.py` 按 `id` 合并二者。

## 文本长度建议

- `current_problem`：150-300 个中文字符，必须出现受影响对象、典型旧行为、具体限制、实际后果，以及该限制对运维或安全的影响。需充分展开影响说明而非概括性一句话。参考长度：150-220 字。
- `enhancement`：180-350 个中文字符，必须出现目标版本、阶段/默认状态、阶段演进历史（如"v1.32 引入 alpha、v1.33 升级 beta"）、核心机制（解释如何工作）、关键 API/配置、实际收益说明（用户为何关注）。不得仅复述阶段和默认值。参考长度：180-250 字。
- 价值分析：70-180 个中文字符，必须包含直接收益和采用前提或残余风险。
- 兼容分析/结论：25-160 个中文字符。
- 排查方法：至少包含一个明确动作和一个对象。
- 详细说明：80-260 个中文字符，必须详细、准确、可读性强地描述当前特性——包含功能定义、行为变化、核心机制、适用范围或依赖边界四个维度，以特性功能机制描述为主体，末尾附一句简短阶段过渡，禁止复述升级影响模板话术，禁止只复述阶段和默认值。

这些是可读性建议，不是要求机械凑字。缺少官方证据时宁可简洁或标记待核实，不得用泛化收益和推测性实现细节扩充篇幅。
