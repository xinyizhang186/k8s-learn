# 中文质量标准与迭代精炼

质量顺序固定为 `准确性 > 可读性 > 完整度 > 样式`。任何扩写、润色或排版都不得覆盖来源不确定性，也不得改变机器事实。

## 适用范围

- 阶段 3a（`gen_analysis.py`）自动生成全部 `feature_changes` 的 `排查方法`、`详细说明`、`分析结论`、`建议开启`、`补充说明`，以及多特性版本分析条目的 `enhancement`。这些文本由规则引擎从机器事实自动生成，LLM 不参与。
- 阶段 3b（LLM）只为版本分析的单特性条目和风险条目写中文 `current_problem`、`enhancement`、`value_domain`、`value_analysis`（风险条目写 `feature_summary` 和 `value_analysis`——`value_analysis` 填入"技术or商业影响"列，须遵守三类格式限定）。以下标准主要适用于阶段 3b。

## 明确质量标准

### 准确

- `版本分析.feature_name` 是正式发行博客目录的只读机器字段，只能由 `catalog_id` 解析；写作阶段不生成、不翻译、不润色名称。
- `版本分析.primary_source` 是同一 `catalog_id` 的正式发行博客 URL；先用博客正文成文，信息不足时才增加可审计的 `supplemental_sources`。
- 人名、版本、阶段、默认值、锁定状态、KEP 编号、API/Kind 与官方证据一致。
- 一段文字不混写两个不同特性。
- 不把计划、毕业条件或讨论稿写成已经实现的事实。
- 不使用"全面提升""显著优化"等无证据结论。
- **所有文本必须使用中文**，不得保留英文源码注释原文。技术标识符（如 FeatureGate 名、API 字段名、KEP 编号）保留英文。

### 可读

- 首句说明原问题或使用场景，次句说明本版本变化，末句说明用户收益或限制。
- 每句只承载一个主要判断；优先主动语态。
- 中文解释机制，英文保留技术标识符。
- 避免发布历史堆砌、KEP 模板内容和逐字机翻。
- "现状"按"受影响对象/场景 -> 旧行为 -> 限制 -> 实际后果"组织；"本特性增强"按"目标版本与阶段/默认状态 -> 核心机制 -> 关键 API/配置 -> 适用条件或边界"组织。
- 扩展内容只补充能够帮助读者理解或采用的事实。优先增加对象、机制、依赖和边界，不增加发布口号、重复收益、无证据的内部实现或同义改写。
- "价值分析"清晰简洁、准确明确地给出独立判断：先写直接收益（谁获得什么具体好处），再写受益场景，最后写采用条件或残余风险。禁止重复功能描述、禁止"提升效率""增强稳定性"等泛化表述、禁止模糊推断。
- 单个分句只表达一个主要判断；分句过长时按"事实、影响、边界"拆开，不堆叠多层从句。

### 中文写作示例

**好的 `current_problem`（充分展开影响，含受影响对象、旧行为、限制和后果）：**
> 此前修改 Pod 的 CPU、内存等资源配额（requests/limits）需要重建整个 Pod，这会中断工作负载，对有状态应用和批处理任务影响尤其明显。管理员只能通过删除再创建 Pod 来调整资源，无法在不影响运行中工作负载的情况下进行垂直伸缩，导致服务抖动和连接丢失。

**不好的 `current_problem`（过于简短，缺少后果和影响对象）：**
> 此前修改 Pod 资源需要重建 Pod。

**好的 `enhancement`（解释机制、价值、阶段历史和采用前提）：**
> v1.36 将 KubeletFineGrainedAuthz 特性升级为 GA（v1.32 引入 alpha、v1.33 升级 beta 默认启用），以更精细、最小权限的方式控制 kubelet HTTPS API 访问，替代对 nodes/proxy 宽泛权限的依赖。该特性默认启用且已锁定，适合监控和可观测性场景。

**不好的 `enhancement`（只复述阶段，缺少机制和价值）：**
> v1.36 将 KubeletFineGrainedAuthz 提升为 GA，默认启用且已锁定。

**好的 `value_analysis`（含采用前提和残余风险）：**
> 无中断垂直弹性伸缩，避免重建 Pod 中断工作负载；采用前需确认容器运行时版本支持。

**不好的 `value_analysis`（空泛）：**
> 提升资源利用效率，增强稳定性。

**好的风险条目 `value_analysis`（"技术or商业影响"列，符合三类格式之一）：**
> 关键特性版本弃用，产品需审视是否使用 DynamicResourceAllocation，及时适配

**不好的风险条目 `value_analysis`（自由发挥，不符合格式）：**
> 该特性已弃用，建议尽快迁移到新 API，否则升级后可能不兼容。

**好的 `排查方法`（由 gen_analysis.py 自动生成，包含具体检查对象和判断依据）：**
> 检查 CRD 资源的 status.observedGeneration 字段及 conditions 中的 observedGeneration。开启后该特性自动生效，排查可将 observedGeneration 与 metadata.generation 对比，若 observedGeneration < generation 说明控制器尚未处理最新 spec 变更。

**不好的 `排查方法`（过于笼统，没有具体检查对象）：**
> CRD observed generation 跟踪。开启后该特性自动生效，排查可检查相关组件配置和 API 行为。

**好的 `详细说明`（由 gen_analysis.py 自动生成，详细、准确、可读性强，包含四个维度）：**
> 该特性在 CRD 的 status 和 conditions 中跟踪 observed generation，解决 CRD 控制器处理状态与 spec 不同步的问题（功能定义）。此前 CRD 的 status 中未记录控制器已处理的 spec generation 值，客户端无法判断 spec 变更是否已被 reconcile（行为变化）。开启后，CRD 的 status.observedGeneration 字段记录控制器已处理的 spec generation 值，conditions 中的 observedGeneration 同步更新，客户端可将其与 metadata.generation 对比，若 observedGeneration < generation 说明控制器尚未处理最新 spec 变更，避免基于过期状态做决策（核心机制）。适用于所有使用 CRD 的自定义控制器，需 Kubernetes v1.37+ 集群（适用范围）。该 FeatureGate 此前不存在，提升为 Beta，默认启用。

**不好的 `详细说明`（模板化，复述升级影响，缺少功能定义/行为变化/适用范围维度，无特性专属功能描述）：**
> 该 FeatureGate 此前不存在。该特性此前处于 Beta，默认关闭，提升为 GA，默认启用。升级到 v1.37 后该特性默认启用，确认相关组件兼容性后可直接升级。

### 可行动

- 排查方法写成"检查对象 + 方法/命令 + 判断依据"。（阶段 3a 自动生成，LLM 不参与）
- 兼容分析明确受影响对象，而非泛称"可能有风险"。
- 建议开启必须考虑阶段、默认值和锁定状态，最终只输出 `开启`、`关闭` 或空白。
- 兼容分析有内容时停止该行写作并清空后续字段；兼容分析为空时，分析结论使用"清理旧门控配置 / 验证后升级 / 迁移后升级"等动作句。
- 补充说明只写一条边界、依赖或后续动作，删除与结论、排查方法和详细说明重复的内容。

### 可追溯

- 每项至少一个官方 URL；高风险结论最好同时有源码事实和说明性来源。
- URL 必须与本特性同名、同版本或同 KEP，不能复用不相关来源。
- 不用其他发布博客替代当前版本正式发行博客；补充来源必须说明支撑字段和博客信息缺口。

## 迭代循环

### 第 0 轮：事实卡片

先为每项记录 3-7 个原子事实，不写完整中文：主体、变化、机制、影响对象、限制、来源。

### 第 1 轮：完整草稿

按工作簿字段生成短文本。机器事实不改。不要在此轮追求华丽表达。

### 第 2 轮：验证驱动修改

运行 `validate_analysis.py`，按问题 ID 精确修改。优先级：事实冲突、缺来源、主体/版本错配、歧义或不可行动、重复和冗长。

### 第 3 轮：读者视角精炼

只处理仍影响理解的句子：消除歧义、合并重复、补充必要条件。不要整表重写。

## 何时停止

停止条件按顺序判断：

1. 是否仍有明确事实错误？有则继续。
2. 是否仍有无来源的关键判断？有则继续研究或标"待核实"。
3. 是否仍有读者无法执行的升级建议？有则定向修改。
4. 新一轮是否只改变措辞而不改善事实、清晰度或行动性？是则停止。
5. 连续两轮问题数不下降，或达到 3 轮？停止并暴露剩余不确定性。

不要用无限重采样解决证据不足。证据不足应改变状态，不应增加想象。

## 常见失败模式

- 把正式发行博客标题替换成 FeatureGate 名、KEP 名、中文翻译、简称或"更规范"的自拟名称。
- 将 FeatureGate 字符串翻译或截断。
- 按关键词把特性配到错误 KEP。
- 用"此前 Kubernetes 不支持"作为所有问题的模板开头。
- 价值分析重复功能描述，没有用户收益。
- 排查方法只有"检查配置"，没有配置对象和判断依据。
- 详细说明复制 KEP README 或发布博客原文。
- 通过增加文本长度掩盖不确定性。
- 为满足长度建议机械添加"提高效率、增强稳定性"等空泛句子。
- 对多个高影响 FeatureGate 复用同一结论、排查方法或详细说明；字段齐全但没有特性专属信息仍视为失败。
- 高影响行只引用 `kube_features.go` 或 CHANGELOG；源码证明机器状态，功能机制必须再由同项 KEP、发布博客或官方文档支持。
- **在中文文本中保留英文源码注释原文**（如 `gate_description` 的英文内容），导致可读性差。
- **特性变更"排查方法"中使用通用模板**（如"开启后该特性自动生效"），缺少 gate 专属的行为变化描述。
- **特性变更"详细说明"复述升级影响模板话术**（如"升级到 vX 后该特性默认启用，确认相关组件兼容性后可直接升级"），而非以特性功能机制描述为主体。
- **特性变更"详细说明"缺少四个维度**（功能定义、行为变化、核心机制、适用范围或依赖边界），只复述阶段和默认值或只写一句话概述，不够详细、准确、可读。
- **特性变更"分析结论"只复述阶段和默认值**，缺少明确的升级决策和影响判断。
- **版本分析"特性功能介绍"过短**（current_problem 或 enhancement 不足 150 字），缺少影响对象、旧行为、后果、机制和价值说明。
- **风险条目"技术or商业影响"（`value_analysis`）不符合三类格式**（关键参数/特性弃用、关键特性弃用、关键特性版本弃用），自由发挥或缺少"产品需审视是否使用...及时适配"固定结构。

## 自动化质量自检（阶段 3 完成后执行）

在 `gen_analysis.py` 和 LLM 补写完成后、运行 `validate_analysis.py` 之前，执行以下自检：

### 特性变更自检
1. 每个非兼容行的 `排查方法` 是否包含 gate 专属的检查对象（不得为"相关组件配置和 API 行为"等通用描述）。
2. 每个非兼容行的 `详细说明` 是否详细、准确、可读性强地描述了当前特性，包含四个维度：功能定义（该特性是什么）、行为变化（改变了什么）、核心机制（如何工作，关键 API/配置字段）、适用范围或依赖边界？是否以特性功能机制描述为主体？是否复述了"升级到 vX 后该特性默认启用"等升级影响模板话术？是否只复述阶段和默认值？不达标则补充缺失维度并删除模板话术。
3. 每个非兼容行的 `分析结论` 是否给出明确的升级决策（不得只复述"vX 默认启用"）。
4. 所有文本是否为中文（不得包含英文 gate_description 原文）。

### 版本分析自检
1. 每个特性的 `current_problem` 是否至少 150 字，包含受影响对象、旧行为、限制和后果。
2. 每个特性的 `enhancement` 是否至少 180 字，包含版本、阶段、机制、API/配置和收益。
3. 每个特性的 `value_analysis` 是否至少 70 字，清晰简洁、准确明确地给出直接收益、受益场景和采用前提/残余风险，无"提升效率"等泛化表述。
4. 每个风险条目的 `value_analysis`（填入"技术or商业影响"列）是否符合三类格式之一：
   - `关键参数/特性弃用，产品需审视是否使用<具体特性/参数名>字段，及时适配`
   - `关键特性弃用，产品需审视是否使用<具体特性名>，及时适配`
   - `关键特性版本弃用，产品需审视是否使用<具体特性名>，及时适配`
   不符合则按风险条目的弃用类型改写为对应格式。
5. 是否有多个特性使用相同或高度相似的文本（不得复用模板句）。

## 文本质量复查清单（阶段 4.5 执行）

阶段 4（`validate_analysis.py`）通过后，LLM 逐项复查 `analysis.json` 中全部条目的文本质量，对不足项定向扩写。复查不是整表重写，而是按以下清单逐项检查并补充。

### 版本分析复查清单

对每个 `version_analysis` 条目，逐项检查：

| 字段 | 检查项 | 不达标时的动作 |
|---|---|---|
| `current_problem` | >= 150 字？包含受影响对象？包含旧行为？包含限制？包含后果？ | 补充缺失的维度，从博客正文提取具体细节 |
| `enhancement` | >= 180 字？包含目标版本？包含阶段演进历史？包含核心机制（如何工作）？包含关键 API/配置？包含实际收益？ | 补充缺失维度，从博客正文和 KEP 提取机制细节 |
| `value_domain` | 只包含一个短标签？未用逗号并列多项？ | 保留最主要的一项，删除其余 |
| `value_analysis` | >= 70 字？清晰简洁、准确明确？包含直接收益（谁获得什么具体好处）？包含受益场景？包含采用前提或残余风险？无"提升效率""增强稳定性"等泛化表述？ | 补充采用前提或残余风险；改写泛化表述为具体收益 |
| `feature_summary`（风险） | >= 100 字？包含弃用/移除原因？包含影响范围？包含迁移方案？包含时间线？ | 补充缺失维度 |
| `value_analysis`（风险） | 符合三类格式之一？`关键参数/特性弃用，产品需审视是否使用<...>字段，及时适配` / `关键特性弃用，产品需审视是否使用<...>，及时适配` / `关键特性版本弃用，产品需审视是否使用<...>，及时适配` | 按弃用类型改写为对应格式 |

**复查示例（版本分析）**：

复查前 `current_problem`（不达标，仅 42 字）：
> Pod 与宿主机共享用户 ID 映射，存在提权风险。

复查后 `current_problem`（达标，152 字）：
> Pod 此前与宿主机共享用户和组 ID 映射，容器内的 root 用户在宿主机上也是 root。容器逃逸后攻击者可能获得节点的管理员权限，对多租户环境构成严重安全威胁。管理员缺少标准化的容器隔离机制来缓解容器逃逸漏洞的影响。

复查前 `enhancement`（不达标，仅 73 字）：
> v1.36 将 User Namespaces 支持提升为 GA（KEP-127），允许容器 root 用户映射到宿主机非特权用户。默认启用且已锁定。

复查后 `enhancement`（达标，185 字）：
> v1.36 将 Pod 用户命名空间支持升级为 GA（KEP-127，v1.25 引入 alpha、v1.30 升级 beta、v1.33 默认启用）。该特性允许容器 root 用户通过 user namespace 映射到宿主机上的非特权用户，即使进程逃逸容器也不具备对底层节点的管理权限。通过 spec.hostUsers=false 启用，不影响现有 Pod 除非手动指定。提供长期 API 稳定性保证，适合多租户环境和敏感基础设施。

### 特性变更复查清单

对每个非兼容 `feature_changes` 条目，逐项检查：

| 字段 | 检查项 | 不达标时的动作 |
|---|---|---|
| `check_method` | 是否有冗余描述（如 behavior 和 check_hint 重复）？是否包含 gate 专属检查对象？ | 删除冗余，补充专属检查对象 |
| `details` | >= 100 字？是否详细、准确、可读性强？是否包含四个维度：功能定义（该特性是什么）？行为变化（改变了什么）？核心机制（如何工作，关键 API/配置字段）？适用范围或依赖边界？是否以功能机制描述为主体？是否复述了"升级到 vX 后该特性默认启用"等升级影响模板话术？是否只复述阶段和默认值？ | 补充缺失维度，删除模板话术和纯阶段复述 |
| `conclusion` | 是否包含 gate 专属功能描述？是否给出明确升级决策（不只是"默认启用"）？ | 补充功能描述和升级决策 |
| `notes` | 是否简洁（<= 90 字）？是否与 conclusion 不重复？ | 压缩或删除重复 |

**复查示例（特性变更）**：

复查前 `check_method`（不达标，冗余）：
> kubelet 重启时改变 pod 状态。该门控已弃用，默认关闭，该门控已弃用，开启会恢复 kubelet 重启导致 pod 状态变化的旧行为。

复查后 `check_method`（达标，无冗余）：
> kubelet 重启时改变 pod 状态。该门控已弃用，默认关闭，开启会恢复 kubelet 重启导致 pod 状态变化的旧行为。

复查前 `conclusion`（不达标，无 gate 专属信息）：
