# AgentENV：快速上手、学习路线与面试要点

> 调研日期：2026-08-31  
> 范围：AgentENV 官方 `latest` 文档、GitHub 主仓库与 Releases。  
> 版本提示：tagged release 与 `main/latest` 请分开理解。

## 1. 最小目标

不要一开始钻全部 Storage 源码。先完成：

```text
能部署
→ 能 Pull Template
→ 能 Start Sandbox
→ 能 Exec
→ 能 Snapshot
→ 能 Resume
→ 能用 E2B SDK 调用
```

然后再进入 OverlayBD、ublk、Scheduler。

## 2. 阶段一：跑起来

Host：

```text
Linux >= 6.8
/dev/kvm
ublk
Docker 或 native install
```

检查：

```bash
uname -r
ls -l /dev/kvm
lsmod | grep ublk
```

按官方 Quick Start 安装 Runtime。

## 3. 阶段二：Template

目标：

```bash
aenv pull ubuntu:24.04
```

理解：

```text
OCI Image
→ AgentENV Template
→ OverlayBD layers
```

然后再构建一个预装 Python/测试工具的 Template。

## 4. 阶段三：Sandbox 生命周期

实际完成：

```text
start
ls
exec
connect
upload/download
pause
resume
delete
```

记录每个操作耗时和状态变化。

## 5. 阶段四：Snapshot 实验

建议 Demo：

1. 启动 Ubuntu Template；
2. 创建文件；
3. 启动后台进程；
4. 修改环境；
5. 创建 Snapshot；
6. 删除/暂停原 Sandbox；
7. 从 Snapshot 启动；
8. 检查文件、进程、环境；
9. 对比 cold start 与 snapshot resume。

这一步最能直观看懂 AgentENV 的价值。

## 6. 阶段五：E2B

设置：

```bash
export E2B_API_URL=http://127.0.0.1:8000
export E2B_SANDBOX_URL=$E2B_API_URL
export E2B_API_KEY=$AENV_API_KEY
```

使用 E2B Python/TypeScript SDK 创建 Sandbox 并执行命令。

要证明的是：

> 上层 Agent 使用熟悉的 E2B interface，底层 Runtime 替换成自托管 AgentENV。

## 7. 阶段六：Network Policy

测试 Sandbox 是否可以访问：

```text
公网
127.0.0.1
10.0.0.0/8
169.254.0.0/16
指定 allowlisted domain
```

理解 always-denied、allowOut、denyOut 与 Internet 开关。

## 8. 阶段七：Proxy

Sandbox 内：

```bash
python -m http.server 8080
```

再从 Host/Gateway 通过 Sandbox Proxy 访问。

继续测试：

- HTTP；
- private token；
- SSE；
- WebSocket。

## 9. 阶段八：源码阅读

只跟主链：

```text
HTTP Create
→ src/api
→ src/orchestrator
→ src/sandbox
→ Firecracker
```

再进入：

```text
src/image
→ storage/overlaybd

→ src/snapshot
```

## 10. 阶段九：分布式

用 Docker Compose 模拟：

```text
Gateway
Scheduler
Node A
Node B
```

观察：

- placement；
- sandbox binding；
- Gateway forwarding；
- Redis；
- node failure。

最后再部署 K8s。

# 面试 Q&A

## Q1：AgentENV 是什么？

**答：**  
AgentENV 是面向 AI Agent 的自托管 Sandbox Runtime。每个 Sandbox 使用 Firecracker microVM 获得独立 Linux Kernel，底层用 OverlayBD + ublk 做 OCI 镜像块级按需加载，并利用磁盘/内存增量 Snapshot 实现快速启动、Pause/Resume 和 Fork；上层提供 E2B-compatible API，并支持 Gateway + Scheduler 多节点部署。

## Q2：为什么不用普通 Docker？

**答：**  
一是隔离边界不同，容器共享 Host Kernel，而 Agent 会执行模型生成的不可信代码；二是 AgentENV 把 VM memory snapshot、rootfs incremental snapshot 和 fork 当作一等原语，更适合 RL rollout、benchmark reset 和大量并行环境。

## Q3：为什么启动能快？

**答：**  
常用路径不是重新完整 boot Linux，而是从 Firecracker Snapshot 恢复；rootfs 和 memory 都可以分层、按需读取，再结合 local cache、Page Cache sharing、background download 和 warm pool，减少关键启动路径上的工作量。

## Q4：OverlayBD 做什么？

**答：**  
它把 rootfs 和 Snapshot 组织成块级分层存储。读取从最新 Layer 向旧层查找，写入当前 upper；创建 Snapshot 时 seal upper 并 restack，因此既能按需读取 OCI Image，也适合保存增量文件系统变化。

## Q5：ublk 做什么？

**答：**  
ublk 把 AgentENV 用户态存储后端呈现为 Linux Block Device，Firecracker 只需要看到普通虚拟磁盘，不需要知道底层数据来自 OCI Registry、对象存储还是 Snapshot。

## Q6：为什么 Memory Snapshot 能提高密度？

**答：**  
多个从同一 Snapshot 恢复的 Sandbox 会读取相同只读 memory artifact，这些页可以利用 Host Page Cache 共享；只有各 Sandbox 修改后的脏页需要独立持有，因此同质 workload 的实际 Host memory 可能显著低于 Guest 配置内存总和。

## Q7：Kubernetes 与 AgentENV Scheduler 是否重复？

**答：**  
不重复。Kubernetes 管的是 AgentENV Node/DaemonSet 这一层；AgentENV Scheduler 管每个 microVM Sandbox 到哪个 Node 的 placement 与 binding，调度粒度不同。

## Q8：AgentENV 与 E2B 的关系？

**答：**  
AgentENV 提供 E2B-compatible API，因此可以把 E2B SDK 的 endpoint 指向自托管 AgentENV。E2B 兼容主要解决上层 API 生态，AgentENV 的差异化重点在 Firecracker、存储、Snapshot 和自托管分布式 Runtime。

## Q9：最重要的安全点是什么？

**答：**  
不仅是 microVM 隔离，还包括 management API、Sandbox ingress、envd 和 egress 四个面。AgentENV 将 API Key、Traffic Access Token、envd Access Token 分开，并提供 node-level always-denied CIDR。生产还需要外部 TLS、镜像供应链和 Snapshot Secret 保护。

## Q10：有哪些生产风险？

**答：**  
强依赖 Linux/KVM/ublk 和高权限 Host 操作；PVM/P2P 仍带 Experimental 属性；Snapshot 可能包含内存 Secret；大规模部署还需要验证 Cache、Object Store、Scheduler HA、Redis、Node failure、p99 启动时延和多租户安全。

## 11. 可用于项目描述的技术总结

```text
调研并复现 AgentENV Agent Sandbox Runtime：基于 Firecracker microVM 构建独立内核沙箱，
结合 OverlayBD + ublk 实现 OCI 镜像块级按需加载，并通过磁盘/内存增量 Snapshot 支持
快速启动、Pause/Resume 与 Fork；完成 E2B-compatible API 接入，并分析 Gateway/Scheduler
多节点调度、Redis binding、网络 egress 策略及 P2P Artifact 传输机制。
```
