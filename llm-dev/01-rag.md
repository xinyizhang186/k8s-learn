# 01 · RAG 检索增强生成

> RAG 是大模型应用最常见形态,几乎每场秋招必考。掌握完整架构 + 排障思路 + 选型对比。

---

## 题 1:设计一个企业知识库问答 RAG 系统 ⭐⭐⭐⭐⭐

### 【场景】
公司有 10 万份内部文档(规章制度、技术 wiki、产品手册、历史工单),要做一个员工问答助手,要求答案准确、可溯源、不泄密。请给出完整架构。

### 【考察点】
RAG 全链路架构、组件选型、数据安全意识

### 【答案要点】

**1. 整体架构(五层)**

```
[用户提问]
   ↓
① Query 改写 / 意图识别 (LLM)
   ↓
② 多路召回 (向量检索 + 关键词 BM25 + 知识图谱可选)
   ↓
③ Rerank 重排 (Cross-Encoder 模型)
   ↓
④ 上下文组装 + 引用标注 (拼 Prompt)
   ↓
⑤ 生成 + 答案校验 (LLM + 置信度过滤)
   ↓
[答案 + 来源链接]
```

**2. 数据离线流水线(建库)**
- 文档解析:PDF/Word/HTML 用 Unstructured / PyMuPDF / MarkItDown 抽文本 + 表格 + 图片
- 切分(Chunking):语义切分 > 固定长度切分;按标题层级递归切,每块 256–512 token,重叠 10–20%
- Embedding:BGE-M3 / text-embedding-3-large / GTE,中文用 BGE 系列性价比高
- 向量库:Milvus(亿级,分布式)/ Qdrant(中等,易用)/ PG+pgvector(小规模,运维简单)
- 元数据:每块带 doc_id/章节/权限标签/更新时间,检索时按权限过滤

**3. 在线检索增强**
- Query 改写:多轮对话用 LLM 把"它多少钱"改写成"iPhone 15 价格";HyDE(让 LLM 先假设答案再检索)
- 多路召回:向量(语义)+ BM25(关键词,补向量漏掉的专有名词)+ 知识图谱(实体关系)
- Rerank:bge-reranker-v2-m3 / Cohere Rerank,Cross-Encoder 精排 Top50→Top5
- 上下文组装:按相关度排序拼,超长用 Map-Reduce 摘要;每块带 `[1][2]` 引用编号

**4. 生成与校验**
- Prompt:只允许基于引用内容回答,不确定就说不知道;输出 `答案 + 引用编号列表`
- 置信度:检索 Top1 分数 < 阈值 → 触发兜底(转人工 / 拒答 / 多轮澄清)
- 引用回链:答案每个论断标注来源块,前端可点击跳转原文

**5. 工程化**
- 离线增量更新:文档变更触发重新切分 + Embedding,版本化管理
- 缓存:Query Embedding 缓存 + 答案缓存(语义去重)
- 监控:召回率指标(无结果率)、引用命中率、用户点踩率
- 权限:检索时按用户角色过滤元数据,做到"不越权召回"

### 【加分追问】
- **Q: 文档有表格怎么办?** A: 用多模态模型(如 Qwen-VL)把表格转成结构化 JSON/Markdown 再入库;或用 ColPali 这类 late-interaction 模型直接对文档页向量检索,不切分。
- **Q: 怎么评估 RAG 效果?** A: 用 RAGAS——faithfulness(忠实度)、answer_relevancy(答案相关度)、context_precision/recall(上下文精确召回)。见 `08-eval.md`。
- **Q: 知识图谱怎么加?** A: 抽实体关系三元组(LLM 抽 + 人工校),存 Neo4j;检索时实体链接 + 子图召回,与向量结果融合。即 GraphRAG(见题 8)。

## 题 2:RAG 检索效果差,怎么排查优化? ⭐⭐⭐⭐⭐

### 【场景】
上线后发现:用户问"年假怎么请",RAG 召回不到正确文档,或者召回了但模型答非所问。给一个系统化的排障方法。

### 【考察点】
RAG 全链路排障能力、指标体系、优化手段

### 【答案要点】

**1. 先定位问题在哪个环节(分桶诊断)**

| 现象 | 环节 | 排查 |
|---|---|---|
| 召回的文档不对 | 检索阶段 | 看 Top10 召回,人工标答是否在内 |
| 召回对了但答错 | 生成阶段 | 单独给 LLM 正确文档看能不能答对 |
| 多轮才问清楚 | 意图阶段 | Query 改写是否合理 |

**2. 检索环节优化(召回率低)**

- **Chunk 策略**:块太大(语义稀释)/太小(信息断裂)→ 试语义切分(按句号/段落/标题)
- **Embedding 模型**:换更强的(BGE-M3 > BGE-large-zh);中英混合用多语言模型;领域文档考虑微调 Embedding
- **Query 改写**:加 HyDE(LLM 假设答案再检索)、Query 扩展(同义词/相关词)、多轮改写
- **多路召回**:向量 + BM25 + 关键词,加权融合(RRF, Reciprocal Rank Fusion)
- **元数据过滤**:用结构化字段(部门/时间)先粗筛,再向量精排
- **倒排+向量混合**:Hybrid Search,业界主流

**3. 排序环节优化(Rerank)**

- 加 Cross-Encoder Rerank(bge-reranker),召回 Top50→重排→Top5
- Rerank 模型比双塔 Embedding 准,但慢;只对 Top50 做可接受

**4. 生成环节优化(答非所问)**

- **Prompt 工程**:明确"只基于提供内容回答,不编造";要求输出引用编号
- **上下文过长**:Top5 太多信息淹没 → 减到 Top3 + Rerank
- **Lost in the Middle**:把最相关的放头尾,中间放次相关
- **模型能力不足**:换更强模型,或微调(见 `05-finetuning.md`)

**5. 数据问题**

- 文档本身没答案 → 用"拒答"评估指标,引导用户改问
- 文档过时 → 离线更新流水线 + 时间戳过滤
- 专有名词向量模型不认识 → 加领域词典/微调 Embedding

**6. 持续优化闭环**
- 收集 bad case → 人工标注 → 离线评估集 → A/B 测各优化点 → 上线
- 指标:Recall@K、MRR、答案忠实度、点踩率、无答案率

### 【加分追问】
- **Q: 怎么自动找 bad case?** A: 用一个强模型当"评测员",对线上 Query+答案打分,低分的入 bad case 池;或对同义 Query 做一致性检查(同义问法答案应该一致)。
- **Q: Recall@K 怎么测?** A: 人工标注每条 Query 的正确文档集,看 Top-K 召回里是否命中;或用 LLM 判断召回块是否"相关"。

## 题 3:Chunk 切分策略怎么定? ⭐⭐⭐⭐

### 【场景】
知识库文档长短不一(产品手册 200 页,工单 3 行),切分策略直接影响召回质量。怎么设计?

### 【答案要点】

**1. 切分目标**:每块语义完整、长度适中、可独立检索

**2. 三种切分策略**

| 策略 | 方法 | 适用 |
|---|---|---|
| **固定长度** | 按字符/token 数切,带 overlap | 简单但破坏语义,作 baseline |
| **规则切分** | 按段落/标题/Markdown 结构递归切 | 主流,LangChain RecursiveCharacterTextSplitter |
| **语义切分** | 用 Embedding 计算相邻句子相似度,断在相似度骤降处 | 最优,但慢;工具 SemanticChunker |

**3. 参数经验值**
- 块大小:256–512 token(中文 200–400 字),太小信息不全,太大语义稀释
- Overlap:10–20%(块间重叠),保证边界信息不丢
- 按标题层级:先按 H1/H2 切,过大再按段落切

**4. 进阶策略**
- **父子块(Parent-Child)**:小块检索(精准),大块送生成(上下文全);Milvus/Qdrant 支持
- **滑动窗口 + 摘要**:每块带前文摘要,补全局上下文
- **表格/代码特殊处理**:不切分,整块入库,或转 Markdown 结构化
- **ColPali / late-interaction**:文档页级向量,不切分直接检索,适合复杂版式 PDF

**5. 评估**
- 同一查询集,跑不同切分策略,比 Recall@5 和答案忠实度
- 看 bad case:切错(语义断裂)/切粗(信息淹没)哪种多

### 【加分追问】
- **Q: 切分后怎么知道好不好?** A: 构建 golden set(每 Query 标正确块),算 Recall@K;或人工抽检召回块是否"可独立回答"。
- **Q: 长文档(200 页)怎么办?** A: 先按章节切(用标题树),每章节再递归切;每块带章节路径元数据,便于上下文组装和权限过滤。

## 题 4:Embedding 模型与向量库怎么选型? ⭐⭐⭐⭐

### 【场景】
公司要选型,向量库百万级文档,Embedding 模型要中文,预算有限。怎么选?

### 【答案要点】

**1. Embedding 模型选型**

| 模型 | 维度 | 中文 | 备注 |
|---|---|---|---|
| **BGE-M3** | 1024 | ⭐⭐⭐⭐⭐ | 开源 SOTA,多语言,支持稠密+稀疏+多向量 |
| BGE-large-zh-v1.5 | 1024 | ⭐⭐⭐⭐ | 开源,稳定,中文主流 |
| GTE-large-zh | 1024 | ⭐⭐⭐⭐ | 阿里达摩,开源 |
| text-embedding-3-large | 3072 | ⭐⭐⭐ | OpenAI 闭源,效果好但要调 API + 隐私 |
| M3E | 768 | ⭐⭐⭐ | 早期开源,已被 BGE 超越 |

**选型维度**:① 中文效果(MTEB 中文榜)② 部署方式(开源本地 vs API)③ 维度(影响存储)④ 推理速度 ⑤ 是否支持指令(instruction-aware,如 BGE 带 query 指令前缀)

**2. 向量库选型**

| 库 | 规模 | 特点 | 适用 |
|---|---|---|---|
| **Milvus** | 亿级 | 分布式,功能全(HNSW/IVF/DiskANN),生态成熟 | 大规模生产 |
| **Qdrant** | 千万级 | Rust 写,易用,支持过滤+混合检索 | 中等规模,易运维 |
| **Weaviate** | 千万级 | 内置 hybrid search + schema 灵活 | 中等规模 |
| **pgvector** | 百万级 | PostgreSQL 插件,SQL 友好,事务+过滤强 | 小规模,已有 PG |
| **Elasticsearch** | 千万级 | hybrid(向量+BM25)成熟,运维重 | 已有 ES 栈 |
| **Chroma** | 十万级 | 轻量,Python 友好 | 原型/小项目 |

**3. 选型决策树**
- 数据量 < 100 万 + 已有 PG → pgvector(运维简单,SQL+向量一体)
- 数据量百万–千万 + 注重易用 → Qdrant
- 数据量亿级 + 分布式 → Milvus
- 已有 ES 栈 + 想要 hybrid 一步到位 → Elasticsearch 8.x

**4. 索引选型**
- HNSW:查询快(O(log n)),内存大,百万级首选
- IVF_FLAT/IVF_PQ:内存友好,精度略降,大规模用
- DiskANN:磁盘索引,超大规模 + 内存不足时

**5. 注意点**
- Embedding 维度对齐向量库配置
- 元数据过滤要在检索时下推,别检索后再过滤(性能差)
- 距离度量:多数模型用 Cosine,选模型时确认其训练用的度量

### 【加分追问】
- **Q: BGE-M3 的三种向量是什么?** A: 稠密(语义)+ 稀疏(关键词,类 BM25)+ 多向量(ColBERT 风格 token 级);可单独用也可融合,叫 Multi-Vector Retrieval。
- **Q: 微调 Embedding 值得吗?** A: 通用 Embedding 在垂直领域(医疗/法律术语)效果差时值得;用 LLMERA/sentence-transformers 的 SetFit/contrastive learning 微调,需构造正负样本对。

## 题 5:RAG vs 长上下文,怎么选? ⭐⭐⭐⭐

### 【场景】
现在模型支持 128K/1M 上下文,直接把文档全塞进去,还需要 RAG 吗?

### 【答案要点】

**1. 对比表**

| 维度 | RAG | 长上下文 |
|---|---|---|
| 数据规模 | 无上限(检索库可亿级) | 受限于上下文窗口 |
| 成本 | 低(只送 Top-K) | 高(全送,token 多) |
| 延迟 | 快(prompt 短) | 慢(prefill 长输入贵) |
| 准确率 | 取决于召回质量 | 取决于 Lost-in-Middle |
| 实时性 | 索引更新即生效 | 每次重送最新文档 |
| 可溯源 | ⭐ 可标注引用 | 难标引用 |
| 适用 | 大知识库、动态数据 | 单文档分析、小知识 |

**2. 结论**
- 文档量小(< 几十篇)且固定 → **长上下文**简单直接
- 文档量大 / 动态更新 / 需要溯源 → **RAG** 必选
- 实际工程:**两者结合**——RAG 召回 Top10 后,每块带更大上下文(父子块),用长上下文模型生成

**3. 长上下文的坑**
- **Lost in the Middle**:中间位置信息容易被忽略 → 把最重要的放头尾
- **成本**:128K 输入约 $1-2/次(GPT-4o),贵;1M 上下文更贵
- **延迟**:prefill 长输入显著慢,首 token 延迟高
- **精度下降**:上下文越长,关键事实提取精度下降

**4. 趋势**
- Agentic RAG:Agent 主动决定检索几次、检索什么(见 `02-agent.md`)
- Long-context + RAG 融合:用长上下文模型做 RAG 的 Rerank/生成,容忍更长上下文

### 【加分追问】
- **Q: Long-context 模型出现后 RAG 会被淘汰吗?** A: 不会。RAG 解决的是"知识规模 + 实时性 + 成本 + 溯源",长上下文只解决"单次上下文长度"。两者互补。
- **Q: Needle-in-a-Haystack 测什么?** A: 测长上下文模型在长文本中找特定事实的能力;实测发现中间位置召回率低,即 Lost in the Middle。

## 题 6:RAG 怎么减少幻觉? ⭐⭐⭐⭐

### 【场景】
RAG 上线后模型还是会编造答案,引用对了但内容超出文档。怎么办?

### 【答案要点】

**1. 幻觉来源**
- 检索召回错(给了无关文档)→ 模型瞎编
- 召回对了但模型过度发挥 → 加了文档没有的内容
- 模型本身能力差,理解错文档

**2. 减幻觉手段**

| 手段 | 做法 |
|---|---|
| **Prompt 约束** | "只基于引用内容回答,不在文档中的内容请回答'我不知道';每句答案后标引用编号" |
| **引用回链** | 要求输出 `答案 + 来源块 ID`,前端校验引用块是否真包含该论断 |
| **后置校验** | 用另一个 LLM 做"忠实度检查"(NLI 风格):对每句答案判断是否被上下文支持 |
| **置信度过滤** | 检索 Top1 分数低 → 拒答/转人工;答案与引用相似度低 → 重生成 |
| **少样本示例** | Prompt 里给 2-3 个"正确引用回答"示例,带正反例 |
| **降温** | temperature=0/0.1,降低随机性 |
| **模型选型** | 用指令遵循好的模型(GPT-4 系/Qwen2.5);或微调(见题 7) |

**3. 评估幻觉**
- **RAGAS faithfulness**:把答案拆成陈述句,逐句判断是否被上下文支持,得分 = 被支持句数 / 总句数
- 人工抽检:抽 100 条答案,人工标"是否编造"
- 对比测试:同 Query 跑新旧 Prompt,看幻觉率

**4. 进阶:Self-RAG / CRAG**
- **Self-RAG**:模型自己决定要不要检索、检索结果是否相关、答案是否被支持
- **CRAG(Corrective RAG)**:检索后评估召回质量,差则触发 web 检索兜底,好则精炼后生成

### 【加分追问】
- **Q: 忠实度检查用大模型可靠吗?** A: 比人工便宜但不是 100% 准;用强模型(GPT-4)评弱模型输出较稳;可作为线上低置信度样本的离线筛选。
- **Q: 微调能减幻觉吗?** A: 能。用"正确引用回答"数据 SFT,让模型学会"只引述不编造"的风格;但治本还是召回要准 + Prompt 要约束。

## 题 7:多路召回 + Rerank 怎么做? ⭐⭐⭐⭐

### 【场景】
单一向量检索召回率不够,想加 BM25 和知识图谱,结果怎么融合?要不要 Rerank?

### 【答案要点】

**1. 多路召回架构**

```
Query → ① 向量检索 (Top 50)
      → ② BM25 关键词检索 (Top 50)
      → ③ 知识图谱子图召回 (可选)
      → ④ RRF/加权融合 (Top 100 → Top 50)
      → ⑤ Rerank Cross-Encoder (Top 50 → Top 5)
      → ⑥ 上下文组装 + 生成
```

**2. 融合方法**
- **RRF(Reciprocal Rank Fusion)**:最常用,无需分数对齐。`score(d) = Σ 1/(k + rank_i(d))`,k 通常 60。简单稳定。
- **加权融合**:各路分数归一化后加权求和;需调权重,分数尺度不一致是难点。
- **学习排序(LTR)**:用小模型对召回结果打分,效果最好但需要标注数据。

**3. Rerank**
- **作用**:双塔 Embedding 是离线近似(查询和文档独立编码),精度有上限;Cross-Encoder 把"查询+文档"一起编码,精度高但慢
- **模型**:bge-reranker-v2-m3(中文开源)、Cohere Rerank(闭源 API)、Jina Reranker
- **位置**:多路召回之后、生成之前;只对 Top 50 重排,可接受延迟
- **效果**:比单纯向量召回 Recall@5 提升显著(常提升 10-20%)

**4. 实战注意**
- 多路召回要"互补":向量补语义,BM25 补专有名词,图谱补关系;同质召回多路没意义
- Rerank 模型和 Embedding 模型要匹配(中文场景都用中文模型)
- 缓存 Rerank 结果(Query 相同复用)

### 【加分追问】
- **Q: RRF 为什么 k=60?** A: 经验值,来自原始论文;作用是平滑 Top 排名的影响,避免 Top1 主导;k 影响不大,常用 60。
- **Q: Rerank 加多少延迟?** A: bge-reranker 对 50 个候选约 50-200ms(GPU);CPU 部署更慢;可按 QPS 决定要不要加或缓存。

## 题 8:GraphRAG 是什么?适用什么场景? ⭐⭐⭐

### 【场景】
听人提 GraphRAG,它和普通 RAG 有什么区别?什么时候用?

### 【答案要点】

**1. 普通 RAG 的局限**
- 文档块独立检索,丢失跨文档的全局关系
- "总结性"问题(如"公司主要产品线有哪些")无法靠单块回答
- 实体多跳关系(如"A 的经理的部门")无法跨块推理

**2. GraphRAG 思路**
- 离线:用 LLM 抽文档中实体 + 关系三元组,构建知识图谱(节点=实体,边=关系)
- 离线:用社区发现算法(Leiden)把图切成社区,LLM 给每个社区生成摘要
- 在线检索:
  - **Local Search**:实体链接 → 子图召回(实体+邻居)+ 向量召回融合
  - **Global Search**:遍历所有社区摘要,做 Map-Reduce 回答全局问题
- 来源:微软 GraphRAG(2024 开源)

**3. 适用场景**
- ✅ 跨文档关系推理(人物关系、组织架构、供应链)
- ✅ 全局总结性问题("近一年产品的主要问题是什么")
- ✅ 多跳问答
- ❌ 简单事实查找(普通 RAG 更快更便宜)
- ❌ 文档间无关系(白建图)

**4. 代价**
- 离线建图成本高(LLM 抽三元组 + 社区摘要,token 消耗大)
- 图维护难(文档更新要重抽)
- 工程复杂度高

**5. 取舍**
- 先做普通 RAG,有跨文档/全局问题需求再上 GraphRAG
- 或用混合方案:向量召回为主,图谱辅助实体关系补充

### 【加分追问】
- **Q: GraphRAG 离线成本怎么估?** A: 主要花在 LLM 抽三元组 + 社区摘要上;10 万文档可能要数千元 API 费用。微软开源版可调模型,但仍是成本重头。
- **Q: LightRAG /nano-graphrag 是什么?** A: GraphRAG 的轻量化实现,减少 LLM 调用,适合中小规模。
