> 微调是大模型开发核心技能。秋招高频:SFT/DPO/RLHF 选型、LoRA 原理、数据构造、过拟合。

## 题 1:SFT vs RLHF vs DPO 怎么选? ⭐⭐⭐⭐⭐

### 【场景】
公司要微调一个客服模型,有 1 万条人工对话。SFT、RLHF、DPO 选哪个?

### 【答案要点】

**1. 三者对比**

| 方法 | 数据 | 目标 | 复杂度 | 效果 |
|---|---|---|---|---|
| **SFT** | 指令-答案对 | 监督学习模仿答案 | 低 | 基础能力 |
| **RLHF** | 偏好对 + RM | 强化学习对齐人类偏好 | 高(需 RM + PPO) | 对齐好 |
| **DPO** | 偏好对(chosen/rejected) | 直接偏好优化,无需 RM | 中 | 与 RLHF 接近 |
| **ORPO** | 偏好对 | SFT + 偏好一体 | 中 | 新趋势 |

**2. SFT(Supervised Fine-Tuning)**
- 数据:`(instruction, response)` 标准答案
- 目标:让模型学会按指令作答,格式/风格对齐
- 适用:基础能力对齐(让模型会做某类任务)
- 局限:只能学"正确答案",无法处理"两个都行但 A 更好"

**3. RLHF(Reinforcement Learning from Human Feedback)**
- 三阶段:① SFT → ② 训 Reward Model(偏好对打分)→ ③ PPO 强化学习
- 适合:对齐人类偏好(无害/有用/诚实),ChatGPT 路线
- 缺点:流程长、训练不稳、需 Reward Model、超参敏感

**4. DPO(Direct Preference Optimization)**
- 直接用偏好对优化,省 Reward Model
- 损失:让模型给 chosen 答案的概率高于 rejected
- 2023 论文,效果接近 RLHF,工程简单,主流首选(2024 起大部分开源模型用 DPO/IPO/KTO)
- 缺点:对数据质量极敏感

**5. 选型决策**

| 场景 | 选 |
|---|---|
| 有标准答案,让模型学格式/风格 | **SFT** |
| 有偏好数据,要选"更好的" | **DPO** |
| 极致对齐(安全/无害),资源充足 | **RLHF**(复杂场景) |
| 一体化简单 | **ORPO** |

**6. 客服场景具体选**
- 1 万条人工对话:若是"问→答"标准对 → SFT
- 若是"问→两个回答,人标 A 比 B 好" → DPO
- 实战:SFT 先打底 → DPO 对齐偏好(常用组合)

**7. 数据要求**
- SFT:1k-100k 条高质量指令对;质量 > 数量
- DPO:1k-50k 条偏好对(chosen/rejected);差异要明显
- 数据质量决定上限,垃圾数据微调出垃圾模型

### 【加分追问】
- **Q: DPO 真的能替代 RLHF 吗?** A: 大部分场景可以。DPO 效果接近 RLHF,工程简单;但 RLHF 在复杂奖励设计 / 多目标对齐有优势。2024 起主流开源模型多用 DPO/IPO/KTO。
- **Q: KTO/IPO 是什么?** A: DPO 变体。IPO(Identity Preference Optimization)解决 DPO 过拟合偏好噪声;KTO(Kahneman-Tversky Optimization)只需"好/坏"标签不需成对偏好,数据更易获取。
- **Q: SFT 之后再 DPO 是惯例吗?** A: 是。SFT 学基础能力(格式/任务),DPO 对齐偏好(更安全/更友好)。组合 SFT→DPO 是主流 pipeline。

## 题 2:LoRA / QLoRA 原理是什么? ⭐⭐⭐⭐⭐

### 【场景】
全参微调 7B 模型显存不够,听说 LoRA 能省显存。原理是什么?

### 【答案要点】

**1. LoRA(Low-Rank Adaptation)**
- 思想:不更新原权重 W(d×k),加两个小矩阵 A(d×r) B(r×k),r 远小于 d/k
- 前向:`h = Wx + BAx`,只训练 A、B(参数量 d·r + r·k ≪ d·k)
- 推理可合并:`W' = W + BA`,零额外延迟
- 论文 Hu 2021,主流 PEFT 方法

**2. 为什么有效**
- 论文假设:微调权重更新 ΔW 是低秩的
- 实测 r=8/16 已够大部分任务,r=64/128 用于复杂任务
- 节省显存:只训 A、B,不需存 W 的梯度/优化器状态

**3. 参数量对比(7B 模型)**
- 全参:7B 参数 × (参数 + 梯度 + 优化器状态) ≈ 7B × 12 字节(FP32 优化器)≈ 84GB
- LoRA r=8:~20M 可训参数,显存几乎等于推理 + 少量梯度,单 4090 可训 7B

**4. QLoRA(Quantized LoRA)**
- 把原权重量化 INT4 存储,只训 LoRA 参数(FP16)
- 7B INT4 ≈ 3.5GB 权重,单 16GB 显卡可训
- 论文 Dettmers 2023,平民微调神器

**5. LoRA 选型参数**
- **r(秩)**:8/16 通用,64/128 复杂任务;越大效果越好但过拟合风险
- **alpha**:LoRA 缩放系数,常设为 r 的 2 倍(α=2r)
- **target_modules**:`q_proj,k_proj,v_proj,o_proj`(attention)常用;加 `gate_proj,up_proj,down_proj`(FFN)更强
- **dropout**:0.05-0.1,防过拟合
- **learning rate**:1e-4 比 SFT 高一个数量级(只训小矩阵)

**6. LoRA 合并**
- 训练完可把 A·B 合并到 W:`W_merged = W + (α/r)·BA`
- 合并后单模型文件,推理无额外开销
- 也可不合并,运行时动态加载多 LoRA(vLLM/PEFT 支持)

**7. 局限**
- 复杂任务(风格/领域大变)可能不够,需全参
- 多任务多 LoRA 切换有管理成本

### 【加分追问】
- **Q: LoRA r 怎么选?** A: 经验:r=8-16 通用任务;r=64+ 复杂任务(代码/数学);实测在评测集调,先小后大。
- **Q: LoRA 和全参效果差多少?** A: 大部分任务差距小(<2%);强领域迁移/风格重塑可能差距明显。LoRA 是性价比首选,效果不够再上全参。
- **Q: 多 LoRA 怎么同时服务?** A: vLLM/PEFT 支持多 LoRA 动态加载;请求带 LoRA ID,推理时加对应 A·B;适合多租户/多任务。

## 题 3:微调数据怎么构造? ⭐⭐⭐⭐⭐

### 【场景】
有原始对话日志,怎么变成微调数据?质量怎么保证?

### 【答案要点】

**1. SFT 数据构造**

- **格式**:`{"instruction": "...", "input": "...", "output": "..."}`
- **来源**:
  - 人工编写(质量最高,成本高)
  - 改写开源数据(Alpaca/Belle/FLAN)
  - 真实日志清洗(去噪/脱敏)
  - 强模型生成(Self-Instruct / Evol-Instruct)
- **质量 > 数量**:1k 高质量 > 10k 噪声
- **多样性**:覆盖任务类型/难度/长度;避免同质

**2. Self-Instruct(数据扩充)**
- 用强模型(GPT-4)根据种子任务生成更多任务 + 答案
- 流程:种子 → 模型生成新指令 → 模型答 → 过滤(重复/低质)
- 适合快速扩充,注意质量过滤

**3. 偏好数据(DPO)构造**
- **格式**:`{"prompt": "...", "chosen": "好答案", "rejected": "差答案"}`
- **来源**:
  - 人工标注(A/B 中选更好的)
  - 模型生成多个 + 人工排序
  - 规则构造(好答案 vs 故意错误的)
  - Distillation(强模型答案 chosen,弱模型 rejected)
- **关键**:chosen/rejected 差异要明显,微弱差异学不到

**4. 数据清洗**
- 去重(精确/语义去重)
- 去毒(敏感/有害内容过滤)
- 长度过滤(太长/太短)
- 格式校验(JSON 合法)
- 人工抽检(随机抽 5% 看质量)

**5. 数据配比**
- 通用能力(指令跟随/对话)30-50%
- 领域任务 50-70%
- 防遗忘:配比要平衡,单一任务比例过大会灾难性遗忘

**6. 数据量参考**
- SFT:1k-50k 高质量;少量精品 > 大量噪声
- DPO:1k-20k 偏好对
- 越大模型所需数据越多(7B 5k 起步;70B 几万)

### 【加分追问】
- **Q: 强模型生成的数据算"蒸馏"吗?有版权问题吗?** A: 算知识蒸馏,法律上多数大模型 ToS 禁止用其输出训练竞品;开源模型(LLaMA 系)较宽松。商用需查 ToS。
- **Q: 数据少(只有几百条)能微调吗?** A: 能,但要防过拟合:小 lr + 早停 + LoRA(参数少);或先用 Few-shot / RAG 替代,数据积累够再微调。
- **Q: 怎么判断数据够不够?** A: 看 loss 曲线(训练 loss 降但验证 loss 不降=过拟合);加数据收益递减时停。

## 题 4:微调过拟合 / 灾难性遗忘怎么避免? ⭐⭐⭐⭐

### 【场景】
微调后模型在新任务上好,但通用能力下降(原来会做数学题现在不会了)。怎么办?

### 【答案要点】

**1. 灾难性遗忘(Catastrophic Forgetting)**
- 现象:微调后,模型原能力(通用对话/推理)下降
- 原因:新数据分布与原训练分布差异大,权重大幅偏移

**2. 防遗忘手段**

| 手段 | 做法 |
|---|---|
| **混入通用数据** | 微调集里混 10-30% 通用指令数据(Alpaca/FLAN) |
| **LoRA** | 只训低秩矩阵,原权重不动,减少遗忘 |
| **小学习率** | 1e-5 ~ 5e-5(SFT),1e-4 ~ 5e-4(LoRA);别太大 |
| **少 epoch** | 1-3 epoch,过拟合与遗忘双重风险 |
| **早停** | 监控验证集 loss,不降就停 |
| **正则化** | weight decay / dropout |
| **回放(Rehearsal)** | 训练集混入少量预训练数据 |

**3. 过拟合识别**
- 训练 loss 持续降,验证 loss 上升 = 过拟合
- 模型在新数据上完美,但分布外样本变差
- 输出风格僵化(只会模板回答)

**4. 评估**
- 微调前后跑通用 benchmark(MMLU/C-Eval),确认不掉
- 跑领域测试集,确认提升
- 人工抽检输出风格(是否变得机械)

**5. 最佳实践**
- 先 LoRA 微调试水,够用就不上全参
- 数据混入通用 + 领域(7:3 或 5:5)
- 学习率小,epoch 少,早停
- 评估时同时跑领域 + 通用,双指标看

### 【加分追问】
- **Q: LoRA 也会灾难性遗忘吗?** A: 也会,但程度比全参轻(原权重冻结,只调低秩更新);仍需混入通用数据 + 评估通用能力。
- **Q: 多任务微调怎么做?** A: ① 混合数据集训练 ② 多 LoRA(每任务一个,推理时切换)③ 多任务统一格式;混合数据最简单,配比按任务重要性调。

## 题 5:多轮对话怎么微调? ⭐⭐⃞⭐

### 【场景】
单轮 SFT 简单,多轮对话(用户→助手→用户→助手...)怎么训?

### 【答案要点】

**1. 数据格式**
- 多轮: `[{"role":"user","content":"Q1"},{"role":"assistant","content":"A1"},{"role":"user","content":"Q2"},{"role":"assistant","content":"A2"}]`
- 只对 assistant 的内容算 loss,user 内容不计

**2. 训练方式**

| 方式 | 做法 | 优劣 |
|---|---|---|
| **整体拼接** | 多轮拼成一个序列,只 mask user 部分 | 简单,主流 |
| **拆成多轮单样本** | (Q1,A1),(Q1+A2,Q2,A2)... | 数据增广,但 Q 重复 token 多 |
| **角色 mask** | user 部分不计 loss,assistant 部分计 | 主流 |

**3. 注意**
- 上下文长度:多轮易超长,要截断 / 摘要
- 数据质量:多轮易出现"无意义回答",要清洗
- 多样性:覆盖不同轮数(1/3/5/10 轮)
- 评估:多轮一致性(同话题不同轮答案一致)

**4. 偏好数据(多轮 DPO)**
- 整个多轮对话作为 prompt,对最终 assistant 输出做偏好对
- 或对中间某轮做偏好(更细粒度)

**5. 实战**
- 用 ShareGPT 格式
- 框架:LLaMA-Factory / Axolotl / TRL 都支持多轮
- 评估:多轮一致性 + 任务完成率

### 【加分追问】
- **Q: 为什么只对 assistant 算 loss?** A: 模型要学的是"怎么回答",不是"怎么提问";对 user 算 loss 会让模型学着生成用户问题,跑偏。
- **Q: 多轮数据从哪来?** A: ① 真实客服日志(脱敏)② 强模型自模拟 ③ 开源 ShareGPT/WildChat;真实数据质量好但要清洗 + 脱敏。

## 题 6:RAG vs 微调,怎么选? ⭐⭐⭐⭐

### 【场景】
客服领域知识更新快,用 RAG 还是微调?

### 【答案要点】

**1. 对比**

| 维度 | RAG | 微调 |
|---|---|---|
| 知识更新 | 实时(改库即可) | 慢(要重新训) |
| 成本 | 低(检索+生成) | 高(训练 + 部署) |
| 幻觉 | 低(有引用) | 可能更严重(无引用) |
| 风格/格式 | 靠 Prompt | 微调强 |
| 领域术语 | 靠检索 | 内化 |
| 计算 | 推理时检索 | 训练时投入 |

**2. 选型决策**
- **知识更新频繁** → RAG(改库即生效)
- **风格/格式要统一** → 微调(学风格)
- **领域术语难理解** → 微调 Embedding + 生成模型
- **长尾知识** → RAG(不可能都训进去)
- **低成本快速验证** → RAG(无需训练)

**3. 实战组合**
- **RAG + 微调** 是主流:微调让模型学会"用知识库的答案风格",RAG 提供实时知识
- 先 RAG 跑通 → 效果不够再微调生成模型
- 微调 Embedding:领域术语向量模型不认识时单独微调

**4. 微调 RAG 各组件**
- **Embedding 微调**:用领域数据 contrastive learning,提升召回
- **生成模型微调**:学"基于引用回答"风格 + 领域话术
- **Rerank 微调**:领域数据微调 cross-encoder
- 三个都可微调,看瓶颈在哪

### 【加分追问】
- **Q: 什么场景微调完还得上 RAG?** A: 知识时效性强(新闻/股价/库存)→ 微调学风格,RAG 提供实时事实;微调内化不了所有事实。
- **Q: 微调会让模型忘掉 RAG 给的上下文吗?** A: 不会,微调只是改生成风格/能力;RAG 上下文仍会被读到。但若微调让模型"过度自信"不爱引用上下文,要注意 Prompt + 训练数据设计。

## 题 7:全参微调显存怎么算? ⭐⭐⭐

### 【场景】
全参微调 7B 模型,要多少显存?

### 【答案要点】

**1. 显存组成**
```
显存 = 模型权重 + 梯度 + 优化器状态 + 激活 + KV Cache(可选)
```

**2. 各部分估算(7B FP16 + AdamW)**
- 权重:7B × 2 字节 = 14GB(FP16)
- 梯度:7B × 2 字节 = 14GB(FP16)
- 优化器状态:AdamW 有 momentum + variance,各 FP32 = 7B × 8 字节 = 56GB
- 激活:与 batch/seq_len 相关,小 batch 可忽略
- **合计:~84GB**(FP16 权重 + FP32 优化器)

**3. 优化方案**
- **混合精度(AMP)**:权重 FP16,优化器 FP32(混合精度训练标配),~84GB
- **ZeRO**:切优化器状态/梯度/权重到多卡
  - ZeRO-1:切优化器状态 → ~56GB(7B 单卡仍难)
  - ZeRO-2:切优化器+梯度 → ~30GB
  - ZeRO-3:切全部 → 单卡只放一部分
- **8-bit Adam**:优化器状态 INT8 → 减半优化器显存
- **LoRA/QLoRA**:不训原权重,极大省显存(见题 2)

**4. 实际**
- 7B 全参微调:2-4 张 A100 80G 可行(用 ZeRO-2/3 + AMP)
- 70B 全参:8+ 张 A100,或 DeepSpeed ZeRO-3 + offload
- 单卡平民:LoRA/QLoRA,4090 24G 可训 7B

**5. 训练框架**
- **DeepSpeed**:ZeRO + offload,主流大模型训练
- **Megatron-LM**:TP+PP,大厂大规模
- **FSDP**(PyTorch原生):类 ZeRO-3,易用
- **TRL / LLaMA-Factory**:封装好的微调工具

### 【加分追问】
- **Q: AdamW 优化器为什么占 8 倍参数显存?** A: FP32 存 momentum + variance 两个状态,各 4 字节 = 8 字节/参数;加上权重 FP16 (2B) + 梯度 FP16 (2B) = 12 字节/参数。
- **Q: ZeRO-3 offload 到 CPU 慢吗?** A: 慢,但能跑;CPU 内存便宜,适合没钱买多卡但训大模型。GPU↔CPU 通信是瓶颈。

## 题 8:微调效果怎么评估? ⭐⭐⃞

### 【场景】
微调完怎么知道效果好没好?只看 loss 不够。

### 【答案要点】

**1. 多层评估**

| 层 | 方法 | 指标 |
|---|---|---|
| 训练 | loss/eval loss | 收敛 |
| 通用 | benchmark | MMLU/C-Eval,防遗忘 |
| 领域 | 领域测试集 | 任务准确率 |
| 风格 | LLM-as-judge / 人工 | 友好度/格式 |
| 业务 | A/B 上线 | 任务完成率/满意度 |

**2. 通用 Benchmark**
- 中文:C-Eval/CMMLU/GSM8K(数学)
- 英文:MMLU/HellaSwag/GSM8K
- 用 lm-eval-harness / OpenCompass 跑
- 微调前后对比,确保不掉

**3. 领域测试集**
- 自建:100-500 条领域问答 + 标准答案
- 自动评估:LLM-as-judge(GPT-4 评分)或规则匹配
- 人工抽检:随机 100 条看质量

**4. LLM-as-Judge**
- 用更强模型(GPT-4)对微调模型输出打分
- 多维度:准确率/相关性/流畅度/有用性
- 注意评判模型自身偏见
- 多个评判模型投票更稳

**5. 业务指标**
- 灰度上线 5% 流量
- 对比:任务完成率/点踩率/转人工率/平均轮数
- 统计显著才推全量

### 【加分追问】
- **Q: 自动评估不可靠怎么办?** A: ① 多 LLM 投票 ② 关键场景人工抽检 ③ 业务指标兜底(任务完成率是硬指标)。
- **Q: 微调后通用能力降了还能上吗?** A: 评估降幅:降 <2% 可接受;降 5%+ 要回炉(混通用数据重训或 LoRA)。业务指标优先,通用 benchmark 作参考。
